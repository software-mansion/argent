# Failure Scenarios: Recovery Steps

When a debugger tool fails, use **`debugger-status`** first to diagnose. Note: `debugger-status` and `debugger-log-registry` do **not** fail when the debugger is simply unreachable — they return `{ status: "not_connected", reason, detail, guidance }` (the `detail` field carries the same error text other tools throw), and `debugger-log-registry`'s answer may add a `note` about the console history a dead session left. Match the error, `reason`, or situation below and act as specified. Do not retry the same failing tool repeatedly without following the recovery steps.

Wait for Metro to be ready, then retry `debugger-connect` or `debugger-status` once — not in a loop. If you cannot determine the project root, ask the user. A non-Metro server occupying the port lands here too — the `got:` text shows what answered.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

| **App not connected**              | Error (or `not_connected` `detail`) contains: `Metro at port 8081 has no CDP targets — is a React Native app connected?`                           | `debugger-status` / `debugger-log-registry` return `{ status: "not_connected", reason: "no_app_connected", guidance }` here instead of erroring; other debugger tools still throw. 1) Confirm the app is running on the device. 2) If an app was connected and has since died, read `debugger-log-registry`'s `note`: when that session left a log file the note names it. | **CDP endpoint unreachable**       | `debugger-status` / `debugger-log-registry` return `reason: "cdp_unreachable"`                                                                     | The runtime's CDP endpoint did not answer. On Metro, confirm the app is running (`launch-app` / `restart-app`) and call `debugger-connect`, then retry once.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Was connected, then tool fails** | Any debugger tool fails with a connection or disconnect error after it was working                                                                 | The app may have crashed or been closed — or still be running, with another debugger having taken it: Metro's inspector proxy allows one per device and closes the incumbent when React Native DevTools, Radon IDE or `chrome://inspect` attaches. There is no tool that reports who holds the debugger, and any debugger call you make takes it back — that is the same eviction, pointed the other way — so ask the user before you `restart-app`, which on a live app someone is using force-quits it. A session whose runtime died holding console logs keeps its log file: call `debugger-log-registry` **first** and read the `note` in the answer — it names the file the dead session left, which is where the pre-crash output is, and see **Reading the note** below before you relaunch. Then relaunch the app — `restart-app` on iOS / Android / Vega, or `boot-device` with `electronAppPath` for a Chromium target, which `restart-app` declares no platform for — and call `debugger-connect` again; if nothing read the note earlier, that connect answer carries it — for a runtime that went away, and for a teardown whose record replaced an earlier one nobody read — and on Chromium only if the relaunch kept the same CDP port — the record is filed under the device id, which is that port, and `boot-device` picks a free one unless you pass `electronPort`. A session someone else tore down is spent there in silence unless its record replaced an earlier one nobody read; either way that teardown deleted the file of the session it ended. **If you connected with a `logicalDeviceId`** (which `debugger-connect` asks for once two devices share a port), reconnect with that same id. |

## Reading the note

A crashed session's console log is named by the `note` `debugger-log-registry` and `debugger-connect` hand out, and the first read spends it. The file itself outlives the note: kept logs sit in `~/.argent/tmp` as `argent-logs-<port>-<start-ms>-<pid>-<n>.log` until a debugger session finds them a day old, so if the record was already spent, list that directory and grep the newest file whose start time predates the death of the session you want. A live session's file sits there too. `debugger-log-registry` reporting `connected` names one in `file`, but on a shared Metro that may be a session your own call just minted rather than the one doing the logging, so treat it as one candidate to check rather than one to strike off. The start time is what orders those files, but for identifying whose session one is, only the port says anything — Metro's on iOS / Android / Vega, the CDP port on Chromium — and two devices on one port share both it and the tool-server's pid, so the name cannot tell their logs apart: check the contents before believing one is the crashed app's.

- **Read it before relaunching.** The next crash on this device and Metro port can reclaim the kept file of any earlier one it replaces, not only the one just before it.
- **The answer may still carry the dead session's own entries**, if the teardown has not landed yet — then just read `file`.
- **No note usually means that session logged nothing** — the record is filed only for a session that ended holding console history. Whoever reads it first spends it, so a concurrent agent's `debugger-connect` may have taken it — and on iOS / Android / Vega the record is per Metro port, so ask with the port that session used — on Chromium it is keyed by device id alone, and a `not_connected` answer with no note says which of the two it looked under. On `reason: "reconnecting"` it means neither: the record is held for the retry that guidance asks for, so ask again before concluding anything.
- **A note saying no log file was left behind** (an explicit teardown deletes it, and a writer that never opened one — an unwritable `~/.argent/tmp` — leaves none to keep), **or that a kept one has since been reclaimed**, means that session's entries are gone, and settles that session only. Where a session before it went unread, the note says so in a sentence of its own — how many, whether one of their files went with it, and whether anything they left is still in `~/.argent/tmp` under no name. Where it sends you there, or carries no such sentence at all, an earlier crash can still have left a file that no note names any more, so fall back to the listing this section opens with before concluding the output is unrecoverable. Where the sentence is there and says nothing of a file, or names the take and sends you nowhere, there is nothing of theirs left to find.
- **Once the app is back and logging**, `debugger-log-registry` reports the new session instead, and the note moves to the next `debugger-connect`. That connect reports one for a session whose runtime went away — the app itself, or the route to it, so a `restart-app`, a Metro restart, a dropped transport and Metro handing the debugger slot to another client all qualify — and for a teardown whose record replaced an earlier one nobody read, since nothing else ever reports that loss. A session someone else tore down that replaced nothing is consumed there in silence.
- **A Metro relaunch does not reissue the ids.** The app derives its `logicalDeviceId` from the device and the bundle, so Metro echoes back the same one and a record filed under it stays reachable. A Chromium relaunch does reissue: the device id is the CDP port and `boot-device` draws a free one unless you pass `electronPort`, so read the note before relaunching there rather than counting on the next connect. If you already relaunched, the record is not lost — ask `debugger-log-registry` with the OLD `chromium-cdp-<port>` id: it cannot reach that endpoint any more, and the `cdp_unreachable` answer it returns instead carries the note. Keep reconnecting with the `device_id` the connect accepted; switch to the `logicalDeviceId` only where `reason: "device_mismatch"` tells you to, since connecting with it when nothing refused your id forwards back to the same session while that session lives, and opens a second one, with its own log file, for one device once it has ended. Where two devices shared the port and one died, the survivor answers to the dead one's id in every debugger tool — one device left is one `selectTarget` stops disambiguating — so `debugger-status` reports `connected` for the device that went away. Compare the answer's `logicalDeviceId` against the one that device's last `debugger-connect` returned; `deviceName` names a device class, so two clones of one simulator model do not differ by it. A legacy-inspector device has no `logicalDeviceId` to compare, which is why `selectTarget` says such a device cannot be singled out of a shared Metro at all.
