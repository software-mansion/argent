# Failure Scenarios: Recovery Steps

When a debugger tool fails, use **`debugger-status`** first to diagnose. Note: `debugger-status` and `debugger-log-registry` do **not** fail when the debugger is simply unreachable — they return `{ status: "not_connected", reason, detail, guidance }` (the `detail` field carries the same error text other tools throw), and `debugger-log-registry`'s answer may add a `note` about the console history a dead session left. Match the error, `reason`, or situation below and act as specified. Do not retry the same failing tool repeatedly without following the recovery steps.

| Scenario                           | Error or situation                                                                                                                                 | What to do                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Metro not running**              | Error (or `not_connected` `detail`) contains: `Metro at port 8081 is not running (got: ...)`                                                       | `debugger-status` / `debugger-log-registry` return `{ status: "not_connected", reason: "metro_not_running", guidance }` here instead of erroring; other debugger tools still throw. **Start Metro yourself** unless the user asked you not to: scan the workspace configuration and run the appropriate command to start Metro in the background (by default `npx react-native start` or `npx expo start`). Wait for Metro to be ready, then retry `debugger-connect` or `debugger-status` once — not in a loop. If you cannot determine the project root, ask the user. A non-Metro server occupying the port lands here too — the `got:` text shows what answered.                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **No source locations**            | `projectRoot` is `""` and source lookups report no file:line                                                                                       | Not a failure. Legacy Metro (RN 0.72 and older, e.g. Vega) sends no `X-React-Native-Project-Root` header, so paths cannot be resolved against a project root. `debugger-evaluate`, console logs and the network inspector work regardless — do not restart Metro to "fix" it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **App not connected**              | Error (or `not_connected` `detail`) contains: `Metro at port 8081 has no CDP targets — is a React Native app connected?`                           | `debugger-status` / `debugger-log-registry` return `{ status: "not_connected", reason: "no_app_connected", guidance }` here instead of erroring; other debugger tools still throw. 1) Confirm the app is running on the device. 2) If an app was connected and has since died, read the `note` before you relaunch — see **Reading the note**. 3) Use `restart-app` with the app's device id and bundleId to relaunch so it connects to Metro. 4) Wait a few seconds for the bundle to load. 5) Retry `debugger-status` once. Do **not** use `debugger-reload-metro` to fix this — it also requires at least one target.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Wrong device id**                | `debugger-status` / `debugger-log-registry` return `reason: "device_mismatch"`, or `debugger-connect` fails with `DEBUGGER_TARGET_DEVICE_MISMATCH` | Only a `logicalDeviceId` matches a target, so while two or more devices share this Metro a `list-devices` udid or serial is refused every time, crash or no crash. Retrying it unchanged is worse than useless: it keeps failing until the port is down to one device, and then it succeeds by resolving to whatever is left. Read the `note` under the id you asked with first — that is where a crashed session's record is filed, and a re-targeted call asks under a different one. Then re-target with a `logicalDeviceId` from the `detail` / error message, but those are the ids still connected, so after a crash they belong to other apps: take one only when it is the device you meant. To reach the device you lost, `restart-app` it by its `list-devices` id — that tool takes no `logicalDeviceId` — then connect with the `logicalDeviceId` your last `debugger-connect` on it returned, which the app re-derives unchanged. Or give it its own Metro port, where a udid resolves again.                                                                              |
| **Stale connection**               | `debugger-status` returns `reason: "stale_connection"`                                                                                             | The cached debugger connection was no longer open; `debugger-status` has already discarded it. That discard keeps the session's log file, so if it had captured anything a `note` names it — read it from `debugger-log-registry` before you go further, since `debugger-connect` resolves the runtime before it can report anything. Use `restart-app` if the app is not running, then call `debugger-connect` — the next call reconnects fresh.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Reconnecting**                   | `debugger-status` / `debugger-log-registry` return `reason: "reconnecting"`                                                                        | A reconnect is in flight — the previous connection was just torn down, or (Chromium) a tab switch is in progress. Transient: wait a moment and retry once. Do **not** restart the app for this, and do not read a missing `note` here as an answer — this is the one reason that holds a dead session's record back, unspent, for that retry.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Runtime unresponsive**           | `reason: "runtime_unresponsive"`, or another debugger tool fails with `DEBUGGER_CDP_REQUEST_TIMEOUT`                                               | Follow the `guidance` / error text — it explains the state and the recovery. Each attempt waits out the full CDP timeout, so never retry in a loop.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **CDP endpoint unreachable**       | `debugger-status` / `debugger-log-registry` return `reason: "cdp_unreachable"`                                                                     | The runtime's CDP endpoint did not answer. On Chromium this is what a crashed renderer reads as, so read the `note` first — see **Reading the note** — then relaunch: `boot-device` with `electronAppPath` for an Electron app, or restart the browser with `--remote-debugging-port`. On Metro, confirm the app is running (`launch-app` / `restart-app`) and call `debugger-connect`, then retry once.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Was connected, then tool fails** | Any debugger tool fails with a connection or disconnect error after it was working                                                                 | The app may have crashed or been closed — or still be running, with another debugger having taken it: Metro's inspector proxy allows one per device and closes the incumbent when React Native DevTools, Radon IDE or `chrome://inspect` attaches. There is no tool that reports who holds the debugger, and any debugger call you make takes it back — the same eviction, pointed the other way — so ask the user before you `restart-app`, which on a live app someone is using force-quits it. A session whose runtime died holding console logs keeps its log file: call `debugger-log-registry` **first** and read the `note`, which names it — see **Reading the note**. Then relaunch — `restart-app` on iOS / Android / Vega, or `boot-device` with `electronAppPath` for a Chromium target, which `restart-app` declares no platform for — and call `debugger-connect` again, which carries the note if nothing read it earlier. **If you connected with a `logicalDeviceId`** (which `debugger-connect` asks for once two devices share a port), reconnect with that same id. |

## Reading the note

A crashed session's console log is named by the `note` `debugger-log-registry` and `debugger-connect` hand out, and the first read spends it. The file outlives the note: kept logs sit in `~/.argent/tmp` as `argent-logs-<port>-<start-ms>-<pid>-<n>.log` until a debugger session finds them a day old. So if the record was already spent, list that directory and grep the newest file whose start time predates the death of the session you want. Only the port in the name says whose session one is, and two devices on one port share it, so check the contents before believing one is the crashed app's — a live session's file sits there too.

- **Read it before relaunching.** The next crash on this device and Metro port can reclaim the kept file of any earlier one it replaces, not only the one just before it.
- **The answer may still carry the dead session's own entries**, if the teardown has not landed yet — then just read `file`.
- **No note is weak evidence.** A record is filed only for a session that ended holding console history; whoever reads it first spends it, so a concurrent agent's `debugger-connect` may have taken it; on iOS / Android / Vega it is keyed by Metro port, so ask with the port that session used, while on Chromium it is keyed by device id alone, and a `not_connected` answer with no note says which of the two it looked under. On `reason: "reconnecting"` it means neither: the record is held for the retry that guidance asks for, so ask again before concluding anything.
- **A note saying no log file was left behind** (an explicit teardown deletes it, and a writer that never opened one — an unwritable `~/.argent/tmp` — leaves none to keep), **or that a kept one has since been reclaimed**, means that session's entries are gone, and settles that session only. Where a session before it went unread, the note says so in a sentence of its own — how many, whether one of their files went with it, and whether anything they left is still in `~/.argent/tmp` under no name. Where that sentence sends you there, or is absent altogether, fall back to the listing this section opens with before concluding the output is unrecoverable.
- **Once the app is back and logging**, `debugger-log-registry` reports the new session instead, and the note moves to the next `debugger-connect`. That connect reports one for a session whose runtime went away — the app itself, or the route to it — and for a teardown whose record replaced an earlier one nobody read, since nothing else ever reports that loss.
- **A Metro relaunch does not reissue the ids.** The app re-derives the same `logicalDeviceId`, so a record filed under it stays reachable. A Chromium relaunch does reissue: the device id is the CDP port and `boot-device` draws a free one unless you pass `electronPort`, so read the note before relaunching there. If you already relaunched, ask `debugger-log-registry` with the OLD `chromium-cdp-<port>` id — it cannot reach that endpoint any more, and the `cdp_unreachable` answer carries the note. Keep reconnecting with the `device_id` the connect accepted; switch to the `logicalDeviceId` only where `reason: "device_mismatch"` tells you to, since connecting with it otherwise opens a second session, with its own log file, for one device once the first has ended.
