Argent records the HTTP requests of the running app in a network log. The agent reads this log. The agent tells you which request the app sent, which response came back, and what the payload contains.

## Capture layers

Argent captures traffic in four layers.

| Layer                    | Platforms             | Content                                                                                       |
| ------------------------ | --------------------- | --------------------------------------------------------------------------------------------- |
| JS runtime               | iOS, Android, Vega    | The `XMLHttpRequest` calls, also from axios, and the `fetch()` calls of React Native and Expo |
| Native `NSURLProtocol`   | iOS, Mac apps         | The `URLSession` requests, also from native modules. See the Limits section                   |
| Native OkHttp            | Android               | OkHttp requests from a debuggable app                                                         |
| Chrome DevTools Protocol | Chromium and Electron | All request types of the active tab, also documents and assets                                |

Each layer captures the traffic in the process of the app. Argent does not use a proxy. Thus you do not install a certificate, and you can read HTTPS traffic directly.

The native layer does not change the cookies of the app. Each request sends and stores cookies with the cookie settings of the app session that sent it.

In React Native, the JS runtime layer records each request where the request leaves the JavaScript code. The JS runtime layer records the requests in these functions:

- `XMLHttpRequest`. Axios and the `fetch()` function of React Native use `XMLHttpRequest`.
- The `fetch()` function of Expo (`expo/fetch`), also when the app imports it directly. Expo SDK 56 and later use this function as the global `fetch()`.
- The network module of React Native, when a library sends its requests there itself. An example is react-native-fetch-api, which replaces the global `fetch()`.

Argent records each request one time. A function of the app that wraps `fetch()` does not change the number of records. An app can keep a reference to `fetch()` from before the capture started. Argent also records the requests through this reference. Argent also records the requests of a library that the app installs after the capture started.

The type of a record is `Fetch` for the `fetch()` functions of React Native and Expo, and for a library that sends its requests to the network module of React Native. The type is `XHR` for the `XMLHttpRequest` calls of the app, also from axios. An `XMLHttpRequest` call that the app sends through a copy of `send()` from before the capture started has the type `Fetch`.

For the `fetch()` function of Expo, Argent records the body of a response when the app reads the body. Expo gives the body to one reader only. Thus Argent does not read a body while the request runs. After the request ends, Argent takes the body of an error response that the app did not read. Argent gives this body to the app when the app reads it.

Native code does not use these functions. For native code, use a native layer. In a react-native-macos app, the native `NSURLProtocol` layer also records the `fetch()` calls.

## Start and stop the capture

On iOS and Android, the agent starts and stops the network capture of an app. One start covers the JS runtime layer and the native layer of the app. The start waits until each layer is ready, for at most a few seconds. The result tells the agent which layers are ready. For a layer that is not ready, the result gives the reason.

Before a start, a read of the network log tells the agent that the capture is not started. The read does nothing else. Thus the agent starts the capture before the action that sends the requests.

The native layer follows the app until the agent stops the capture. When the agent launches or restarts the app, the native layer captures the requests of the new process. A reload or a restart of the app ends the capture of the JS runtime layer. The native layer keeps its capture. A read does not start the capture of the JS runtime layer again. The read tells the agent that the capture stopped recording at the reload. Then the agent starts the capture again.

The agent stops the capture when it has the requests that it needs, or before a profile. The capture of a different app continues. After the stop, Argent records no new request of the app. If the app runs but the stop cannot reach its JS runtime, the capture there can still record. Then the result tells the agent to stop the capture again later. Argent keeps the network log, and the IDs of the requests stay valid. Stopped capture does not follow the app. It stays off across reloads and restarts. A launch, a restart or a read does not start it again. Only a new start does.

A request that runs at the stop completes in the list on iOS and in the JS runtime layer. On Android, the list shows the request as failed. The request in the app continues. After the stop, an Android request body or response body is available only if the agent read it before the stop.

On Chromium and Electron, Argent starts the capture when it attaches to the page. Argent attaches when the agent uses a Chromium tool for the first time. On Vega, a read of the network log starts the capture of the JS runtime layer. On a Mac app, a read of the native network log starts the native capture. The agent cannot stop the capture of a Mac app.

## Native network capture on Android

Argent calls the native OkHttp layer native network capture. Use a debuggable app on Android 9 or later. The app must run as `arm64-v8a` or `x86_64`.

The start of the capture attaches an in-app agent to the running app. The in-app agent connects to Argent a short time later. The start waits for this connection, for at most 5 seconds. Then repeat the action that sends the request. Argent captures OkHttp traffic, including React Native requests, Fresco images, and Expo `fetch()`.

Native network capture follows the app until the agent stops it. When the agent launches or restarts the app, Argent attaches the in-app agent to the new process. The launch steps of an e2e test do the same. The launch waits until the capture is ready, for at most 5 seconds. If the capture is not ready after this time, Argent reads the reason from the log of the device. This step can add 3 seconds when adb does not answer. The result of the launch tells the agent if Argent attached the in-app agent. A process can also start in a different way, for example from a launcher tap, from a link, or after a crash. Argent does not attach the in-app agent to this process. If an earlier process had the in-app agent, the network log tells the agent that the process is not attached. If the app did not run at the start, the network log tells the agent that the app was not running. To attach the in-app agent, the agent restarts the app or starts the capture again.

Native network capture stays on until the agent stops it for the app. The capture of a different app continues. `stop-all-simulator-servers` also stops it for all apps of the device. After the capture stops, restart the app to remove the in-app agent from the app.

Each request has an ID such as `android-3f9a-12`. The agent uses this ID to read headers and request or response bodies. An ID is valid only in the tool-server that listed it. An ID stays valid after the capture stops. An ID is not valid after `stop-all-simulator-servers` stops the services of the device, or after the tool-server stops.

Only the in-app agent that Argent attached can report requests to Argent.

If native network capture is unavailable, use the JS runtime layer for the requests of the JavaScript code.

## Native `NSURLProtocol` layer on iOS

The native `NSURLProtocol` layer captures the `URLSession` requests of an app on an iOS simulator. On a simulator without a [device provider](/docs/reference/device-providers), the start of the capture waits until the app acknowledges the capture, for at most 5 seconds. Thus the start for a connected app usually reports that the capture is ready. Argent does not capture the requests from before the start. Repeat the action that sends the request.

On a simulator without a device provider, the app can run before the capture starts. Then the header line of the first result tells that Argent did not record the launch. To capture the launch, ask the agent to restart the app.

On a simulator without a device provider, the capture follows the app until the agent stops it. Argent starts the capture in each new process of the app when the process connects. If the simulator is local, the result of a launch or a restart tells the agent if the capture is ready in the new process. The launch steps of an e2e test do the same.

On a simulator where Argent uses the socket of a device provider, the provider controls the capture in the app. The start and the stop of the capture do not change the capture setting of the provider. If the provider has the capture off, the header line says so. Then turn on the capture in the provider. Argent records the requests from the time that Argent connects to the in-app agent of the provider. This time can be before the start. Thus the network log can show requests from before the start.

If the app was already running when Argent connected, the header line of the first result tells that Argent did not record the earlier requests. On this simulator, a relaunch ends the capture. Thus Argent cannot record the launch. Do not ask the agent to restart the app for the launch.

The network log of this layer keeps the requests of the earlier processes of the app. On a simulator where Argent uses the socket of a device provider, a relaunch of the app clears the network log of this layer. A request that runs when the connection of the app closes shows as failed. The error of the request tells if the app process ended.

Each request has an ID such as `ios-3f9a-12`. The agent uses this ID to read headers and request or response bodies. An ID is valid only in the tool-server that listed it. An ID stays valid after the capture stops. An ID is not valid after `stop-all-simulator-servers` stops the services of the simulator, or after the tool-server stops.

If the app still sends a request body, the details tell the agent to read the body again later. Then the agent reads the details again after the upload ends.

The capture stays on until the agent stops it for the app. The capture of a different app continues. `stop-all-simulator-servers` also stops it for all apps of the simulator. On a simulator where Argent uses the socket of a device provider, the provider keeps its own capture setting after the stop. Argent records no new request of the app there.

## The request record

First the agent reads the list of records in the network log. The content of the list depends on the layer:

| Layer                                  | List                                                                                                                   |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| JS runtime, Chrome DevTools Protocol   | One line for each record                                                                                               |
| Native `NSURLProtocol`                 | On iOS, a header line, then one entry for each request. On a Mac app, one entry for each event, with headers and times |
| Native OkHttp (native network capture) | A header line, then one entry for each request                                                                         |

In the JS runtime layer and in the Chrome DevTools Protocol layer, a line has this format:

```
{id: rn-net-4} "GET /v1/users" 200 OK Fetch 12.4 kB 143 ms
```

In the JS runtime layer, the text after the status is the standard reason phrase of the status code, for example `OK` or `Not Found`. A request that a redirect sent to a different URL ends with that URL, for example `→ /v2/users`.

A size with `~`, for example `~1.2 MB`, is approximate. The JS runtime layer shows this size when the size in bytes of a body is not known: for a large text body, or for a binary body that the app reads as text. This size is the length of the body in characters. The size in bytes is equal to this length or larger.

In the two native layers, the header line tells the state of the capture, the number of requests and the process ID of the app. The state tells if the capture is ready, stopped or not started. On Android, the state also tells when the current process of the app has no in-app agent, or when the last start found that Argent cannot capture the app. In the second case, the header line gives the reason. On iOS, the header line also gives the reason when the capture is not ready. In native network capture, the header line also tells if the capture is active, waits for the app to load OkHttp, or is unavailable. For an unavailable capture, the header line gives the reason. Sometimes an active capture gets only some requests of the app. Then the header line tells which requests Argent captures.

Then the agent reads the details of one record by its ID. On a Mac app, the native `NSURLProtocol` layer has no details, because each entry of its list is complete. The details contain these items:

- The URL, the method and the status. In the JS runtime layer and in the two native layers, the details also give the final URL after a redirect.
- The headers of the request and of the response. In native network capture, the request headers are the headers sent on the wire. They include headers that the app code did not set, for example `Cookie` and `User-Agent`. The response headers are the headers that the app received. After OkHttp decodes a gzip response, these headers do not contain `Content-Encoding` and `Content-Length`. In the native `NSURLProtocol` layer, the request headers are the headers that the app set. They do not include the headers that iOS adds on the wire, for example `Cookie` and `User-Agent`.
- In native network capture, each redirect before the final response
- The duration and the size
- The bodies of the request and of the response
- For Chromium, the initiator of the request

For the JS runtime layer, the two native layers and the Chrome DevTools Protocol layer, Argent replaces the values of secret headers with `[REDACTED]`. A header is secret if its name contains `authorization`, `cookie`, `token`, `api-key` or a related word. On a Mac app, the native `NSURLProtocol` layer does not replace these values. See the Limits section.

Argent also shortens a body that is longer than 1000 characters. A message before the shortened body gives the size of the full body. The JS runtime layer can keep only the start of a large body. For such a body, the message gives the full size in bytes, the full length in characters or a minimum length. The two native layers can also keep only the start of a large body. For such a body, the message gives the full size in bytes if Argent knows it, and the number of bytes that the layer kept.

Argent removes the bundle traffic and the HMR traffic of Metro from the network log. Thus the network log contains the requests of your app only. This removal applies only when the app connects to Metro on a local address. If a physical Android device connects to Metro on a network address, for example `192.168.1.20:8081`, the network log also contains the requests to Metro. On iOS and Android, the native layers remove all requests to the Metro port on a local address, for example `localhost:8081`.

## Example instructions

- "The list screen is empty. Examine the response of the API."
- "Compare the payload of the request before and after my change."
- "Show the requests that this screen sends at mount. Show their durations."
- "Make sure that the app sends the second request after the error 500."
- "Show the requests from the analytics SDK in my Android app."
- "Start the network capture, sign in, then stop the capture and show the sign-in requests."

## Limits

- Argent does not capture the requests that the app sends before the capture starts. Do the operation again after the capture starts. Argent starts the capture at these moments:
  - JS runtime layer and native `NSURLProtocol` layer on iOS: the agent starts the capture.
  - Native network capture: the in-app agent connects to Argent. This occurs a short time after the agent starts the capture.
  - JS runtime layer on Vega: the agent reads the network log for the first time.
  - Chrome DevTools Protocol layer: Argent attaches to the page.
  - Native `NSURLProtocol` layer on a Mac app: the agent reads the network log of this layer for the first time. The native capture stays on when the app restarts after the first read. The native capture stops when the tool-server disconnects from the app. The next read of the network log starts the capture again.
- A reload or a restart of the app clears the network log of the JS runtime layer and ends its capture. See [Start and stop the capture](#start-and-stop-the-capture). On Vega, Argent starts the capture again when the agent reads the network log.
- After an upgrade of Argent, the network capture of the earlier version stays in the app until the app reloads. The earlier network capture keeps no records, but it still reads each response. Reload the app to remove the earlier network capture.
- Expo `fetch()` does not always report a connection that breaks in the middle of the response body. The app then gets a part of the body, or its read of the body does not end. The record shows the same: that part of the body, or a pending request. If the app does not read the body, the record shows a finished request.
- If the app aborts an `XMLHttpRequest` while the response body streams, the record shows a failed request with the error `aborted`. The record contains the part of the text body that the app received before the abort. For example, `react-native-sse` aborts its request to close the connection. The same applies to a library request that streams text, for example a react-native-fetch-api request with `textStreaming`. If the app aborts an Expo `fetch()` while it streams the body, the record has no body.
- A `fetch()` call that fails before it sends the request has no record. An example is a call with a signal that is already aborted.
- If the app aborts a library request before the network module of React Native gives the request its ID, the request still runs. The app gets an abort error, but the record shows the finished request and its response.
- If the app does not read the body of a successful Expo `fetch()` response, the record has no body and no size. A response that cannot have a body, for example the response to a `HEAD` request, has the size 0.
- Argent finds the network module of React Native in the list of modules that Metro adds to a development build. Without this list, Argent does not record the requests that a library sends to the network module itself.
- The network log keeps the most recent records only:
  - The JS runtime layer keeps 2000 records.
  - Native network capture keeps 2000 records. It keeps fewer records when the requests have very large headers or URLs.
  - The Chrome DevTools Protocol layer keeps 1000 records.
  - The native `NSURLProtocol` layer keeps 2000 records for each app on iOS. It keeps fewer records when the requests have very large headers or URLs. On a Mac app, it keeps 1000 protocol events. A request produces several events, so a Mac app keeps fewer than 1000 requests.
- The JS runtime layer does not read a binary response body, for example an image, a font, a PDF file or an `application/octet-stream` body. The record gives the type and the size of the body only. For Chromium, Argent does not show a response body that is not UTF-8 text. The details give the type and the size of this body only.
- The JS runtime layer keeps approximately the first 1 MB of each body. The JS runtime layer also removes the oldest records when their bodies contain more than 50 MB of text.
- For Chromium, Argent reads the active tab. If you change the tab, Argent attaches to the new tab. If the page changed after the request, the body of the response can be unavailable.
- The `NSURLProtocol` layer records the requests of `URLSession` sessions with the default configuration or the ephemeral configuration, and of `URLSession.shared`. The layer does not record these requests:
  - The transfers of a background `URLSession`. The system does not use a custom `NSURLProtocol` for background sessions.
  - The connections of `Network.framework`, for example `nw_connection`.
  - The requests of a `WKWebView`, also the `fetch()` calls in the web page.
  - The requests of an HTTP client that does not use `URLSession`, for example the `HttpClient` of Flutter (`dart:io`).
- An empty native network log does not prove that the app sent no requests. The app can send requests that the `NSURLProtocol` layer does not record.
- On Android 9 or later, native network capture records each OkHttp request that the app starts after Argent attaches the in-app agent. Native network capture does not record these requests:
  - A request that is already running when Argent attaches the in-app agent.
  - The requests of an OkHttp copy in a different class loader, for example a separate plugin loader.
  - In OkHttp 3, the requests of a custom subclass of `OkHttpClient`.
  - The requests of an HTTP client that does not use OkHttp, for example `HttpURLConnection` or Cronet. A native module can use such a client.
- On Android 8.0 and 8.1, native network capture records only a part of the requests. The header line gives the reason. Earlier Android versions do not have native network capture.
  - In a React Native app, it records only the requests of the React Native networking client and of Fresco. It does not record `fetch()` of Expo, WebSockets, or the OkHttp clients of native modules.
  - In an app without React Native, it records no requests.
- If R8 fully minifies the OkHttp code of the app, native network capture is unavailable. The header line gives the reason. The requests of the app continue to work.
- When native network capture records only a part of the requests of the app, the header line says so after `capture active:`.
- For WebSockets, native network capture records only the connection request.
- Native network capture attaches the in-app agent to the main process of the app only. It does not record the requests of a component that runs in its own process, for example a service with `android:process=":remote"`. If the `<application>` element sets `android:process`, Argent does not find the app and reads it as not running.
- The two native layers read each body from the app process that sent the request. A relaunch or a crash of the app ends that process. On Android, an emulator snapshot load also ends it. After that, a request body or a response body is available only if the agent read it before. Argent keeps a copy of only the 64 most recent bodies that the agent read. On iOS, these copies also contain a maximum of approximately 64 MB together.
- If a physical Android device loses its USB connection, the device removes each `adb reverse`. Argent tries to set the `adb reverse` of the capture again for approximately 15 seconds. After this time, Argent sets it again at the next app launch or at the next start of the capture. A read of the network log does not set it. Until then, the in-app agent cannot connect.
- While the in-app agent has no connection, it keeps the events of the requests for a maximum of 60 seconds. After 60 seconds, it turns off the capture and deletes these events. The list then does not contain these requests, and the header line does not say that they are missing. The capture starts again when the in-app agent connects.
- Native network capture and the native `NSURLProtocol` layer can slow the app. The launch results, the e2e test reports and the profiler start results tell the agent when one of them is on. Before you profile, ask the agent to stop the capture. Then restart the app.
- When the agent stops native network capture, Argent turns off the capture in the app. Argent keeps the session file, the files of the in-app agent and the `adb reverse` of the capture. Two other stops remove them: `stop-all-simulator-servers`, and a stop of the tool-server, for example at the idle timeout. These stops turn off the capture. They remove the session file and the files of the in-app agent from the app. They also remove the `adb reverse` of the capture. The copies of these files in `/data/local/tmp/.argent-inspector` stay on the device. A crash or a `kill -9` of the tool-server skips these steps. After a crash or a `kill -9`, these items stay on the device:
  - The in-app agent stays in the app process until the process ends. The in-app agent tries to connect again every few seconds until then. After 60 seconds, it turns off the capture in the app, but it continues to try to connect. Thus when the agent starts the capture in a new tool-server, the capture of this process comes back without a restart of the app.
  - The session file and the files of the in-app agent stay in the app. They stay until a new tool-server starts the capture and then stops the services of the device. An installation of the app also removes them.
  - The `adb reverse` stays until you remove it with `adb reverse --remove`, until the adb server or the device restarts, or until the USB connection of the device stops. A restart of the adb server also removes the other reverses, for example the reverse of Metro. Each `adb reverse` that stays holds one device port from 20000 to 29999.
- Argent does not replace the data in the URLs and in the bodies of the requests and of the responses. Protect a network log as you protect other data of the app.
- On a Mac app, Argent does not replace the values of secret headers on the native `NSURLProtocol` layer. The agent sees headers such as `Authorization` and `Cookie` in full. Protect a network log of this layer as you protect other data of the app.

Argent does this with these tools: `network-capture-start`, `network-capture-stop`, `view-network-logs`, `view-network-request-details` and `native-network-logs`. The [tools reference](/docs/reference/tools) contains all tools.
