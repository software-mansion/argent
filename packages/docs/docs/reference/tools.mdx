Argent exposes its capabilities to the coding agent as MCP tools. You rarely call these by hand, but knowing what exists tells you what you can ask for.

Run `argent tools` to list them from the terminal, `argent tools describe <name>` for the full schema of one, and `argent run <name>` to invoke one directly.

## Devices and apps

| Tool                         | Description                                                                                                                             |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `list-devices`               | List iOS simulators, Android emulators and devices, Chromium apps, Mac apps, Vega (Fire TV) devices, and HarmonyOS phones and emulators |
| `boot-device`                | Boot a simulator, emulator, Vega Virtual Device, or HarmonyOS emulator, spawn an Electron app, or start a Mac app                       |
| `launch-app`                 | Open an app by bundle id (iOS) or package name (Android)                                                                                |
| `restart-app`                | Terminate then relaunch an app                                                                                                          |
| `reinstall-app`              | Install or reinstall an app, clearing app data and runtime permissions                                                                  |
| `open-url`                   | Open a URL or URL scheme on the device                                                                                                  |
| `settings-permissions`       | Grant, deny, or reset a runtime permission without navigating the Settings UI                                                           |
| `rotate`                     | Set the device orientation to portrait or either landscape                                                                              |
| `fold`                       | Fold or unfold a foldable iOS simulator or Android emulator to a posture or a hinge angle                                               |
| `shake`                      | Shake the device                                                                                                                        |
| `network-conditions`         | Add latency, limit the download and upload speed, or set the network offline                                                            |
| `button`                     | Press a hardware button: home, back, power, volume, app switch, action button                                                           |
| `tv-remote`                  | Press a TV remote or D-pad button on Apple TV, Android TV, or Vega                                                                      |
| `stop-simulator-server`      | Stop the transport session for one device and free its resources                                                                        |
| `stop-all-simulator-servers` | Stop every service a device owns: simulator servers, native devtools, TV daemons, network capture and its requests (not on Vega)        |
| `stop-metro`                 | Stop the Metro bundler listening on a given port                                                                                        |

Through the MCP server, `list-devices` returns a shorter text than the SDK and `argent run`:

- Each device is one line of compact JSON.
- The text does not include `isEmulator`, which repeats `kind`. It also does not include fields without a value or `runtimeKind: "mobile"`.
- An iOS runtime is shortened, for example to `iOS 27.0`.
- The iOS simulators that are shut down come after the JSON object, one line for each simulator. A line gives the platform, the udid, the name, the runtime, the state and the tags, for example `foldable` or `runtimeKind=tv`. A simulator in another state, for example `Booting`, stays in the JSON object.

The SDK and `argent run` return the full JSON object.

`launch-app` and `restart-app` accept `launchArgs`, a list of arguments that Argent passes to the app process at launch. For example, `["-FeatureFlag", "YES"]` overrides a UserDefaults value. `launchArgs` works on Apple simulators, physical iPhones and Mac apps. Other targets ignore it. If the app already runs, `launch-app` terminates it first, so that the app gets the arguments. On a local iOS simulator, the tool fails if that termination does not finish within 15 seconds. On a remote simulator, `launch-app` and `restart-app` fail if the termination fails for a reason other than the app not running, and launch nothing. On a physical iPhone, the app sees `--` before the arguments. UserDefaults overrides still apply. On a Mac app, `launch-app` applies `launchArgs` only when it starts the app. See [Mac apps](#mac-apps).

`reinstall-app` uninstalls the app first, so Argent checks the app at `appPath` before the uninstall. The tool fails and keeps the installed app when one of these checks fails:

- `appPath` does not exist, or it is not a `.app` directory (iOS), an `.apk` file (Android), a `.vpkg` file (Vega) or a `.hap` file (HarmonyOS).
- `bundleId` does not match the bundle id in the `.app`, the package name in the `.apk` or the bundle name in the `.hap`. On a remote simulator, Argent does not compare the bundle id.

On Android, Argent also checks the device after the uninstall. If the package is still on the device, the tool fails and does not install the `.apk`. These packages stay after the uninstall:

- A system app. The app data stays on the device.
- An app that is an active device admin. The app data stays on the device.
- An updated system app. The uninstall removes only the update. If the update has a newer version than the system app, Android also removes the app data.

If Argent cannot check the device after the uninstall, the tool also fails and does not install the `.apk`. The app may already be uninstalled.

On a local iOS simulator, the tool fails and does not install the `.app` if the uninstall does not finish within 30 seconds.

On a local iOS simulator, `boot-device`, `launch-app`, `restart-app`, `reinstall-app` and `open-url` give `error_kind: "timeout"` when a `simctl` step does not finish within its time limit. The message names the step and the limit. On a remote simulator, `launch-app` and `restart-app` do the same for a `sim-remote` step that does not finish within 30 seconds.

On a local iOS simulator, `boot-device` fails if `simctl list` does not answer within 10 seconds, because Argent cannot read the state of the simulator. In that case, `list-devices` returns a `hint` that says that the list can be incomplete.

On Chromium, `open-url` fails when the URL does not load a page, start a download or run as a `javascript:` URL. Examples are a URL with no scheme, an unknown scheme, `tel:`, `mailto:`, a host that does not resolve, a response with no content and a navigation that a `beforeunload` handler on the current page cancels. An HTTP error status, for example 404, does not make the tool fail, also when Chromium shows its own error page for it. In headless Chrome, a 401 that asks for credentials makes the tool fail.

`stop-metro` returns `stopped: true` when it sends SIGTERM to every listening process it finds, or the process has already exited, and `stopped: false` when it finds none. The tool fails if it cannot read the port, if it finds a listener but not the process that owns it, or if it cannot signal a listener it found, for example with EPERM. On macOS, the tool detects a listener that belongs to another user only when it sees no other listener on the port, so that listener can still hold the port after `stopped: true`.

Argent drives a foldable iOS simulator, for example the iPhone Duo, and a foldable Android emulator, for example a Pixel Fold or a generic foldable AVD. `list-devices` marks a foldable device and a foldable AVD with `foldable: true`. `fold` moves the hinge to a posture (`closed`, `half-open` or `open`) or to an angle from 0 to 180 degrees.

- Closed, the cover panel shows the UI. Half-open and open, the inner panel shows the UI. The panel that shows the UI is the active panel.
- All tools use the active panel. This is also true after a fold made outside Argent.
- The coordinates and the screenshot size change with the panel.
- `fold` returns when the device accepts input again.

On an iOS simulator:

- A video keeps the size of the panel where the recording started. Argent keeps the proportions of the other panel and adds black bars.
- A fold between two angles that are not 0 or 180 can keep the current panel. To change panels, fold to `closed` or `open`.
- Unfolded, the UI is landscape. `rotate` sets the orientation of the device, not of the UI. `Portrait` gives a landscape UI.
- If Argent cannot find the active panel, it uses the cover panel. The tool result then has a warning.

To move a full-screen app into Split View on an open iPhone Duo simulator, use one `gesture-custom` call:

1. Start with the app full screen and the UI in landscape.
2. Set `edge: "bottom"` and `interpolate: 12`. Send `Down` at (0.5, 1).
3. Move to (0.5, 0.5) over 280 ms. Hold there with a second `Move` after 300 ms.
4. Move to x = 0.14 for the left half or x = 0.86 for the right half over 320 ms.
5. Keep y = 0.5. Send `Up` at the same point after 200 ms.
6. Check that the app occupies the requested half and the Home Screen occupies the other half.

On an Android emulator:

- The result gives `deviceState` (`CLOSED`, `HALF_OPENED` or `OPENED`) and the matching `posture`.
- Argent dismisses a lock screen that the fold to closed shows, if it has no PIN or password.
- The result has a warning if the screen is off or the lock screen shows after the fold.
- On a generic foldable profile, closed shows only the left part of the display, and `describe` frames do not match taps. Use a Pixel Fold profile to test the cover panel.
- A physical device and an emulator without a hinge reject the call.

Argent supports physical iPhones. Physical iPads are not supported. `list-devices` shows a physical iPhone as an iOS entry with kind `device`. The state is `connected` when the device is reachable over USB or the network. The state is `paired` when the device is remembered but unreachable. Argent never selects a physical device automatically. Specify its UDID.

For network access, CoreDevice must report `transportType: localNetwork`. Argent brings the tunnel up on the first call and needs its IPv6 address in `fc00::/7`. Argent binds its runner to this address. Processes that can reach the tunnel endpoint can send runner commands. If the runner stops answering on its tunnel address, for example after the address changes, Argent restarts it on the current address and retries the call once.

See [Physical iOS devices](/docs/features/physical-ios-devices) for signing requirements and the app-scoped interaction contract.

With `macos-apps` enabled, `list-devices` includes Mac apps that Argent started and that are still running. See [Mac app IDs and kinds](#start-and-restart-an-app).

### Network conditions

`network-conditions` sets the network conditions of an iOS simulator app, an Android emulator or a Chromium tab. Each call replaces the conditions of the previous call.

| Parameter      | Description                                                                                               |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| `udid`         | The device                                                                                                |
| `bundleId`     | iOS only, and required on iOS: the app to throttle                                                        |
| `port`         | iOS only: the Metro port that Argent does not throttle. The default is the Metro port of the device.      |
| `latencyMs`    | The minimum time from a request to its response, in milliseconds, from 0 to 60000                         |
| `downloadKbps` | Download limit in kilobits per second. Omit it for no limit.                                              |
| `uploadKbps`   | Upload limit in kilobits per second. Omit it for no limit.                                                |
| `offline`      | `true` makes requests fail as if no network is available. On Android, `adb reverse` ports stay reachable. |

A call without `latencyMs`, `downloadKbps`, `uploadKbps` and `offline` removes the throttle, also when it has `port`. An unknown parameter fails the call. The result contains `scope` and `conditions`. `conditions` is `null` after a removal. `scope` tells which traffic Argent changes:

| `scope`  | Target             | Traffic                                                                                  |
| -------- | ------------------ | ---------------------------------------------------------------------------------------- |
| `app`    | iOS simulator      | The `http` and `https` requests of the app through the URL loading system (`URLSession`) |
| `device` | Android emulator   | The traffic of the emulator network. Only `offline` is available.                        |
| `tab`    | Chromium, Electron | The requests of the page in the active tab                                               |

`latencyMs` sets a minimum. A response that takes longer than `latencyMs` gets no extra delay.

On iOS:

- The app must not be an Apple system app, and the native devtools must connect to it. If the result has a `status` field, follow its `message`, as for `native-network-logs`.
- Argent delays the data that the app receives. The server gets each request and each upload immediately. With `uploadKbps`, the app gets the response after the time that the upload would take.
- `downloadKbps` and `uploadKbps` are limits for the whole app. Requests that run at the same time share them. The app gets the response data at the download speed, as on a slow network.
- `offline: true` also fails the requests that are already running, with the error `-1009` ("The Internet connection appears to be offline.").
- While Argent shapes or inspects the requests of the app, the app does not use its HTTP cache. Each request goes to the server, and `offline` fails a request also when the cache has a response for it.
- Argent does not change WebSocket connections and requests to the Metro port. Set `port` when Metro does not use the default port of the device.
- After a restart of the app, Argent applies the conditions again when the native devtools connect. Requests before that time have no throttle.
- `network-capture-start` and `network-capture-stop` keep the conditions. Argent applies them again after each change of the capture.
- On a simulator from a [device provider](./device-providers.mdx), a removal leaves the network capture of the provider as it was. A restart of the app removes the conditions there. Call `network-conditions` again after it.
- When the tool-server stops or `stop-all-simulator-servers` stops the native devtools, the app removes the conditions.

On Android, the emulator console cannot shape the Wi-Fi network of current system images. Thus `latencyMs`, `downloadKbps` and `uploadKbps` fail on an Android emulator. `offline: true` turns off Wi-Fi and mobile data with `svc`. Argent reports offline only when Android confirms that the emulator has no default network. If Argent cannot confirm this within 15 seconds, it tries to turn both radios on again and fails the call. An Android TV emulator connects over Ethernet, so `offline` fails there with `error_kind: "unsupported"`. On other emulators the call fails with `error_kind: "timeout"`. Call `network-conditions` again after a timeout. A call without conditions does nothing when the emulator has a network. Otherwise it turns on Wi-Fi and mobile data, and fails with `error_kind: "timeout"` when no network comes up within 15 seconds. The emulator stays offline after the tool-server stops.

While the Android emulator is offline:

- Requests through `adb reverse` still work, because adb carries them.
- The emulator cannot reach the host at `10.0.2.2`. A React Native app that loads from Metro at `10.0.2.2` loses its connection to Metro. The debugger tools then cannot reach the app until the network comes back.

On Chromium, Argent applies the conditions to the page of the active tab. Argent applies them again after a tab switch with `chromium-tabs`, and before a tab that `chromium-tabs` opens loads its URL. When `chromium-tabs close` closes the active tab, Argent moves to another tab and applies the conditions there. Service workers, web workers and cross-site iframes keep the full speed. When the active tab closes outside Argent, or when another DevTools client detaches from the page, the conditions can go away. Call `network-conditions` again.

`network-conditions` fails on a physical iPhone and on a physical Android device.

## Inspecting the screen

| Tool                | Description                                                                      |
| ------------------- | -------------------------------------------------------------------------------- |
| `screenshot`        | Capture the device screen                                                        |
| `describe`          | Get the accessibility / DOM element tree for the current screen                  |
| `screenshot-diff`   | Compare two PNG screenshots and return a visual-diff summary                     |
| `await-screen-idle` | Block until the screen has rendered content and held it for `minStableMs`        |
| `await-ui-element`  | Block until a UI element reaches an expected state, instead of polling in a loop |

On Chromium, `describe` reports a zero-area frame when a rotated container fully clips an element along one axis.

On an iOS simulator, a line of `describe` can show:

- `[disabled]` for a control that is not enabled.
- `[selected]` for a selected control.
- `hint="..."` for an element that has a VoiceOver hint. `describe` omits a hint that is identical to the label. A physical iPhone does not report the VoiceOver hint.

On an iOS simulator, `describe` can show the placeholder of an empty text field as its value, with no label. Thus an empty text field looks like a text field that contains that text. `describe` can also omit a text field that has no accessibility label or identifier, such as the Settings search field. This can also occur when the text field contains text. In both cases, take a screenshot to examine the text field.

On a physical iPhone, `describe` includes a web sign-in sheet or an in-app Safari view that covers the app. The system alert that asks to sign in with a website shows only after `launch-app com.apple.springboard`.

## Interacting

| Tool                     | Description                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------- |
| `gesture-tap`            | Tap at normalized coordinates. Mac apps also take a right-click                    |
| `gesture-swipe`          | Smooth swipe or drag between two points                                            |
| `gesture-scroll`         | Scroll a Chromium app (mouse wheel) or the scroll view under a point in a Mac app  |
| `gesture-drag`           | Press, move, and release the mouse in a Chromium app or a Mac app                  |
| `gesture-pinch`          | Pinch to zoom around a center point                                                |
| `gesture-rotate`         | Two-finger circular arc that rotates on-screen content                             |
| `gesture-custom`         | Send an arbitrary sequence of touch events for complex gestures                    |
| `keyboard`               | Type text or press special keys                                                    |
| `paste`                  | Put text on the device clipboard and paste it (sim/emu), or insert it in a Mac app |
| `run-sequence`           | Execute several interaction steps in a single call                                 |
| `screen-recording-start` | Start recording the screen to an h264 mp4                                          |
| `screen-recording-stop`  | Stop the recording and retrieve the video                                          |

`gesture-tap`, `gesture-swipe`, `gesture-scroll`, `gesture-drag`, and `gesture-custom` require position coordinates from 0 to 1, inclusive, not pixels. Argent rejects coordinates outside this range before sending input and names the invalid coordinate. This also applies to calls in `run-sequence` and e2e steps. On a local iOS simulator, `gesture-custom` accepts `edge` for a system gesture. Use `top`, `right`, `bottom`, or `left` in upright screen coordinates. Send one finger with `Down`, optional `Move` events, and `Up`. After a simulator-server restart, the first `Down` can take up to 35 seconds. The `deltaX` and `deltaY` scroll distances can be negative or greater than 1.

Through the MCP server, an interaction tool and `await-ui-element` return a screenshot and the element tree after the screen stops changing. These limits apply:

- Argent waits at most 15 seconds for the screenshot and the element tree together. If a capture takes longer, the result does not include it.
- Argent does not send a capture call again after a timeout.

Argent does not repeat an element tree that the agent already has. Each full element tree starts with a `Tree id` line. Argent compares the element tree with the last full element tree that the MCP server returned for the same device. That element tree comes from an earlier action or from a `describe` call. When the two are identical, the result contains a note in place of the element tree. The note gives the id of the full element tree and the tool that returned it. The screenshot is not affected.

The note does not show that the action had no effect. The element tree does not contain all state. For example, text that the agent types in a field can be absent from it.

All agents on one MCP connection share this comparison. An agent that does not have the element tree with the id in the note calls `describe`.

Argent sends the full element tree again in these cases:

- The element tree or the hint of `describe` changed.
- Argent sent the note 3 times in a row.
- The last full element tree is more than 5 minutes old.
- The client cancelled the call that returned the last full element tree.

A `describe` call always returns the full element tree, with its `Tree id`. With the `disable-auto-describe` flag, a `describe` result has no `Tree id`.

Call `screenshot` or `describe` to read the screen again.

## Audio

| Tool          | Description                                                                               |
| ------------- | ----------------------------------------------------------------------------------------- |
| `audio-input` | Choose what apps in an iOS simulator hear as microphone input: a file, a tone, or the mic |

The audio tool needs an iOS simulator on the same Mac as the tool-server. These rules apply:

- Argent loads the audio hook into each app that starts after Argent arms the simulator. Restart an app that started before that.
- The `ios-audio-always-inserted` flag is on by default. When it is off, Argent loads the hook at the first `audio-input` call. See [feature flags](/docs/reference/configuration#available-flags).
- A remote (`remote:`) simulator, a tvOS simulator, a physical device, Android and Chromium fail before Argent starts a service.
- The simulator must be booted. For a shut-down or unknown simulator, `audio-input` fails with `AUDIO_SIMULATOR_NOT_BOOTED`. Boot it with `boot-device` first.
- Without `libArgentAudio.dylib` in the install, `audio-input` fails with `AUDIO_HOOK_UNAVAILABLE`. The other tools work.

### Network capture on iOS, Android and Mac apps

On iOS and Android, the network read tools only read. `view-network-logs`, `view-network-request-details` and `native-network-logs` never start capture. Call `network-capture-start` for the app before the action that sends the requests. On a Mac app, `native-network-logs` only reads, and `view-network-logs` and `view-network-request-details` start the capture of the JS runtime layer, as on Vega.

`native-network-logs` does not stop the capture. A call with `stop` fails with the error `TOOL_INPUT_INVALID`, and the message tells you to call `network-capture-stop`. Remove `stop` from the call, also `stop: false`.

To capture a request:

1. Call `network-capture-start` with `udid` and `bundleId`.
2. Do the action that sends the request.
3. Call `view-network-logs` or `native-network-logs` to read the list of requests.

`network-capture-start` and `network-capture-stop` work on iOS simulators, remote iOS simulators, Android emulators, Android devices and Mac apps. On iOS and Android, each call controls two layers of the app. On a Mac app, each call controls the `macos-native` layer only:

| Layer            | Platform     | Requests                                | Read with             |
| ---------------- | ------------ | --------------------------------------- | --------------------- |
| `js`             | iOS, Android | The requests of the JS runtime          | `view-network-logs`   |
| `ios-native`     | iOS          | The `URLSession` requests               | `native-network-logs` |
| `android-native` | Android      | The OkHttp requests of a debuggable app | `native-network-logs` |
| `macos-native`   | Mac apps     | The `URLSession` requests               | `native-network-logs` |

The two tools do not support Chromium, Vega, or the JS runtime layer of a Mac app. There, Argent starts the capture without them:

- Chromium: Argent starts the capture when it attaches to the page. Each Chromium tool attaches Argent to the page.
- Vega: a read starts the capture of the JS runtime layer. Each call of `view-network-logs` or `view-network-request-details` installs the capture in the JS runtime of the app, also after a reload.
- The JS runtime layer of a Mac app: as on Vega, each call of `view-network-logs` or `view-network-request-details` installs the capture in the JS runtime of the app. On a Mac app, the two tools act only on the `macos-native` layer.

| Parameter         | Effect                                                                                                                                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `udid`            | The UDID of the iOS simulator, the serial of the Android device, or the device ID of the Mac app (`macos-app-<bundle id>`)                                                                                                  |
| `bundleId`        | The bundle ID of the app on iOS and on a Mac app, or the package name of the app on Android                                                                                                                                 |
| `port`            | The Metro port of the app. Argent reaches the JS runtime of the app through this port. The native layers remove the requests to this port on a local address from their lists. The default is the Metro port of the device. |
| `logicalDeviceId` | Only for a Metro server that two or more devices use. The `logicalDeviceId` of the device on this Metro server. See [Several devices on one Metro server](#several-devices-on-one-metro-server).                            |

#### Start

`network-capture-start` starts the layers at the same time. Each layer waits until its capture is ready:

- JS runtime layer: Argent installs the capture in the JS runtime of the app. If the JS runtime does not answer within 5 seconds, Argent does not install the capture.
- iOS: Argent sends `Network.enable` to the app. Then Argent waits until the app acknowledges it, for at most 5 seconds. If the app still connects to Argent, these 5 seconds also include the connection.
- Mac app: Argent connects to the app if it is not connected, and sends `Network.enable`. Then Argent waits until the app acknowledges it, for at most 5 seconds. A late acknowledgement of the `Network.enable` of an earlier start also arms the app, unless `network-capture-stop` came after that start.
- Android: Argent attaches the in-app agent to the running process of the app. Then Argent waits until the capture is ready, for at most 5 seconds.

The result contains `status` and `layers`. Each entry of `layers` contains these fields:

| Field         | Content                                                                                                                               |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `layer`       | `js`, `ios-native`, `android-native` or `macos-native`                                                                                |
| `armed`       | `true` when the capture of the layer is ready                                                                                         |
| `reason`      | Why the layer is not armed. The field is present only when `armed` is `false`                                                         |
| `unavailable` | `true` when Argent cannot arm the layer without a change that you make, for example a debuggable build, or a Metro server on the port |

A native layer that is not armed often arms later without a new start. For example, Argent arms it when the app connects, or when `launch-app` or `restart-app` starts the app. The `reason` tells what to do. These are frequent reasons:

| Layer            | Reason                                                                                                                                       | `unavailable` |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| `js`             | Metro does not run on the port.                                                                                                              | `true`        |
| `js`             | The JS runtime on the port belongs to a different app.                                                                                       | `true`        |
| `js`             | Two or more devices use the Metro server on the port, and the call has no `logicalDeviceId` of a device on it.                               | `true`        |
| `js`             | The device provider did not grant `js-debugger` for the device, or does not offer the device.                                                | `true`        |
| `js`             | Argent did not reach the JS runtime of the app, but the capture that an earlier start installed there can still record.                      | absent        |
| `js`             | No app is connected to Metro yet, or the JS runtime did not answer.                                                                          | absent        |
| `js`             | The JavaScript of the app did not load yet.                                                                                                  | absent        |
| `ios-native`     | The app is an Apple system app.                                                                                                              | `true`        |
| `ios-native`     | The Xcode command-line tools are not installed. The `js` layer starts without them.                                                          | `true`        |
| `ios-native`     | The device provider has the capture off. Turn the capture on in the provider.                                                                | `true`        |
| `ios-native`     | Argent cannot arm the running process. Argent arms the next process. To capture now, call `restart-app`, then `network-capture-start` again. | absent        |
| `android-native` | Argent cannot attach the in-app agent to the app, for example because the app is not debuggable.                                             | `true`        |
| `android-native` | Argent cannot find `adb`. The `js` layer starts without it, for example for an app that connects to Metro over Wi-Fi.                        | `true`        |
| `android-native` | The app did not run at the start. `launch-app` or `restart-app` attaches the in-app agent to its next process.                               | absent        |
| `android-native` | The in-app agent captures no requests in this process, for example because R8 fully minified OkHttp.                                         | `true`        |
| `macos-native`   | The app is an Apple app. Argent does not load its library into an Apple app.                                                                 | `true`        |
| `macos-native`   | Argent does not start the app: an Electron app, or a build that the hardened runtime keeps the library out of.                               | `true`        |
| `macos-native`   | The app does not run. `boot-device`, `launch-app` or `restart-app` starts it, and Argent arms its process.                                   | absent        |
| `macos-native`   | A copy of the app that Argent did not start runs. The reason gives its process ID. Quit this copy, then start the app with Argent.           | absent        |
| `macos-native`   | No copy that Argent started runs. Argent cannot find the app build, so it cannot find other copies. Use `boot-device` with `macosAppPath`.   | absent        |

On iOS, Argent cannot tell an app that does not run from an app that is not installed. Thus the `ios-native` reason that tells you to call `restart-app` also says this: if `restart-app` cannot start the app, the bundle ID is not installed on the simulator.

#### Several devices on one Metro server

When two or more devices use one Metro server, Argent cannot find the JS runtime of a device from its `udid`. Then the `js` layer is unavailable. Its `reason` lists each device on the Metro server, with its `logicalDeviceId` in parentheses. The native layer is not affected. To capture on the `js` layer:

1. Call `network-capture-start` with `udid`, `bundleId` and the `logicalDeviceId` of the device.
2. Call `view-network-logs` and `view-network-request-details` with this `logicalDeviceId` as `device_id`. Without `port`, a read finds the capture of a device of a device provider on the Metro port that the provider gives for the `udid` of the start. Otherwise, a read without `port` uses the default port of the device. If the start used a different port, give that `port` to the reads.
3. Call `network-capture-stop` with the same `udid`, `bundleId` and `logicalDeviceId`.

The `js` layer uses `logicalDeviceId`. The native layer always uses `udid`. A stop without `logicalDeviceId` does not stop the `js` layer that a start with `logicalDeviceId` started. `stop-all-simulator-servers` with `udid` in `devices` does not stop it either: also put the `logicalDeviceId` in `devices`. Alternatively, give each device its own Metro port.

When all layers are unavailable, `network-capture-start` fails with the error `NETWORK_CAPTURE_UNAVAILABLE`. The message gives the reason of each layer. An Apple system app runs no React Native JS, so both of its layers are unavailable, and a start for it always fails. When the native layer is unavailable because Argent cannot find `adb` or the Xcode command-line tools, the error is `TOOL_DEPENDENCY_MISSING`. On a remote iOS simulator, both layers use `sim-remote`. Without `sim-remote`, the start fails with the error `TOOL_DEPENDENCY_MISSING` before it starts a layer.

A second call of `network-capture-start` keeps the requests that Argent recorded.

The JS runtime capture of an app is on one Metro port of the device. A start or a stop on a different port moves it to that port only when Argent reaches the JS runtime of the app there. Otherwise, the capture on the earlier port stays as it is, and the `reason` of the `js` entry names that port.

The native layer follows the app into each new process that `launch-app` or `restart-app` starts, until `network-capture-stop`. On a Mac app, `boot-device` also starts such a process. On iOS, it also follows a process that starts in a different way. On a simulator where Argent uses the socket of a device provider, a relaunch of the app ends the native capture. Then `native-network-logs` says that the capture is not started. The `reason` of `network-capture-stop` is `capture was not started for this app`. Call `network-capture-start` again after the relaunch. The JS runtime layer arms only at a call of `network-capture-start`. A new JS runtime of the app has no capture. Thus call `network-capture-start` again after each of these events:

- A reload of the JavaScript, for example with `debugger-reload-metro`.
- `restart-app`, or a `launch-app` that starts a new process.
- A start of the capture before the JavaScript of the app loaded.

Until then, `view-network-logs` says that the capture stopped recording at the reload, or that the JS runtime was not ready at the start. The native layer keeps its capture across these events.

#### Stop

`network-capture-stop` stops the capture of the app on each layer. The capture of a different app continues. Argent keeps the requests that it recorded. Their IDs stay valid in `view-network-request-details` until the JS runtime of the app reloads or restarts. Until the next `network-capture-start`, `view-network-request-details` says for an ID of the JS runtime layer that the reload cleared the requests. After the next `network-capture-start`, the new JS runtime numbers its requests from `rn-net-1` again. Then an earlier ID of the JS runtime layer can name a new request. A reload or a restart does not change the IDs of the native layers.

The result contains `status` and `layers`. Each entry of `layers` contains these fields:

| Field    | Content                                                                                                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `layer`  | `js`, `ios-native`, `android-native` or `macos-native`                                                                                                                                     |
| `armed`  | `false` when the layer confirmed the stop. `true` when the layer did not confirm the stop. The `reason` tells why                                                                          |
| `total`  | The number of requests that the layer keeps for the app. `0` when the stop cannot count the requests, for example when it does not reach the JS runtime of the app. The `reason` tells why |
| `reason` | Why the stop did not reach the layer, what the stop did not change, or `capture was not started for this app`                                                                              |

If a layer has no started capture, the stop does not start it. A layer that Argent cannot reach does not make the tool fail. The `reason` of the layer tells why.

A stop can fail to reach the JS runtime of the app, for example when the app does not run. Then the `js` entry depends on the earlier start:

- An earlier start sent the capture to the JS runtime through this Metro port, no stop paused it since, and the app has a process on the device: `armed` is `true`. This is also true when the JS runtime did not answer the install, because the install can take effect without an answer. The capture can still record in the JS runtime of the app. The `reason` tells you to call `network-capture-stop` again when the app answers. When the device does not answer, `armed` is also `true`.
- An earlier start sent the capture to the JS runtime through this Metro port, no stop paused it since, and the app has no process on the device: `armed` is `false`. The capture ended with the process of the app.
- A start stored the capture but sent none to the JS runtime, or the JS runtime answered that it installed none, or an earlier stop paused it: `armed` is `false`. Argent installs no capture in the JS runtime of the app while the capture is stopped.
- No start stored a capture for the app: `armed` is `false`, and the `reason` ends with `capture was not started for this app`. Argent stores nothing, and a later read says that the capture is not started.

A stop changes nothing on the JS runtime layer when the Metro port has the capture of a different app. A stop of an Apple system app changes nothing on the JS runtime layer, because the app runs no React Native JS.

At the stop:

- A request that runs at the stop completes in the list on iOS, on a Mac app and in the JS runtime layer. On Android, Argent marks the request as `failed` with the error `capture stopped before the request finished`. The request in the app continues.
- On Android, a body is available after the stop only if `view-network-request-details` read it before the stop. Argent keeps a copy of the 64 bodies that it read most recently.
- On Android, Argent keeps the files and the `adb reverse` of the capture. See [Native network capture on Android](#native-network-capture-on-android).
- On Android, the connection of the in-app agent can be down at the stop, for example while adb does not answer. Then `armed` is `true` for the `android-native` layer, unless Argent finds that the process of the app ended. The in-app agent gets the stop when it connects again. Argent records no request that the app sends after the stop.
- On a simulator where Argent uses the socket of a device provider, Argent sends no command to the agent of the app. The provider keeps its own capture setting. Argent records no new request of the app. When the app is connected, the `reason` of the `ios-native` entry says so.

The capture stays stopped, also across reloads and relaunches. A read, `launch-app` and `restart-app` do not start it again. Only `network-capture-start` starts it again. After a stop, the tools give these results:

| Tool                                            | After a stop                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `native-network-logs`                           | Lists the requests that Argent kept. The header state is `stopped`, for example `android-native: stopped, 12 requests (capture stopped by network-capture-stop; network-capture-start turns it on again)`. The result contains `stopped: true` and `armed: false`. The call does not connect to the app and runs no adb command. If the process of the app did not confirm the stop, the header also says that this process can still capture its requests.                                                                                               |
| `view-network-logs`                             | Lists the requests in the network log of the JS runtime layer, with the first line `=== NETWORK LOGS (page 1/1, 14 total; capture stopped) ===`. Argent installs no capture, also after a reload. An empty list gives `No network traffic captured: network capture is stopped for <bundleId> (network-capture-stop). Call network-capture-start to capture again, then repeat the action.` After a reload, the text starts with `Network capture is stopped for <bundleId> (network-capture-stop)` and says that the reload cleared the requests.        |
| `view-network-request-details`                  | Gives the details of each ID, also of the IDs from before the stop. The list above gives the limit for Android bodies.                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `launch-app`, `restart-app`                     | Do not attach or arm the capture. On Android and on a local iOS simulator, the `networkCapture` field is `native network capture is stopped for <bundleId> (network-capture-stop); this process runs without it until network-capture-start`. On Android and on a local iOS simulator, a process of the app that did not confirm the stop can still capture its requests. When `launch-app` brings this process to the front, the field says so. On a remote simulator and on a simulator of a device provider, the result has no `networkCapture` field. |
| `e2e-execute`                                   | The first `launch` step of the app after the stop shows the `networkCapture` note as a `warning`.                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `react-profiler-start`, `native-profiler-start` | The warning does not name the app. If the process of the app did not confirm the stop, the warning names the app until that process ends or confirms a later stop.                                                                                                                                                                                                                                                                                                                                                                                        |

`stop-all-simulator-servers` ends the capture of all apps on the device. Argent removes the requests of the native layers and of the JS runtime layer, and their IDs are not valid after it. The JS runtime layer stops recording. After it, a read gives the result from before a start. If `stop-all-simulator-servers` cannot reach the JS runtime of the app, the capture there can still record, and its requests stay. Then the capture of the JS runtime layer stays stopped, and a read gives the result after a stop. A later `network-capture-stop` that reaches the JS runtime stops the recording. For the files on Android, see [Native network capture on Android](#native-network-capture-on-android).

A stop of the tool-server, for example at the idle timeout, also stops the recording of the JS runtime layer and removes its requests. This applies to each JS runtime that the tool-server is still connected to and that answers within 1 second. The tool-server does not connect again for this. `stop-all-simulator-servers` does not connect again either. The connection can be down, for example after Metro stopped or restarted, or after React Native DevTools took the JS runtime. Then the JS runtime keeps its capture and its requests until the app reloads or restarts. After the first `network-capture-start` of the next tool-server, `view-network-logs` lists these requests too. A different tool-server can also start the capture in the same JS runtime. Then the capture and its requests stay until the last of these tool-servers stops.

#### Results before a start

Before `network-capture-start`, a read does no work in the app. It does not connect to the app, runs no adb command and sends no `Network.enable`. For an Apple system app, `native-network-logs` fails with the error `NATIVE_DEVTOOLS_NOT_INJECTABLE`. Otherwise, a read gives these results:

| Tool                           | Result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `native-network-logs`          | `status: "ok"`, `started: false`, `armed: false`, `count: 0`, `total: 0` and an empty `requests`. The header is `ios-native: not started, 0 requests (network capture is off for <bundleId>; call network-capture-start for it, then repeat the action)`, or the same text after `android-native:` or `macos-native:`.                                                                                                                                                                                                                                                                                  |
| `view-network-logs`            | `Network capture is not started for this app, so no requests are recorded. Call network-capture-start with udid and bundleId, repeat the action, then call view-network-logs again.` The JS runtime of a different app on the port gives the same text.                                                                                                                                                                                                                                                                                                                                                 |
| `view-network-request-details` | For an ID from `view-network-logs`: `Request <id> not found. Network capture is not started for this app, so no requests are recorded. Call network-capture-start with udid and bundleId, repeat the action, then list the requests with view-network-logs.` For an `ios-`, `android-` or `macos-` ID, when no capture of that platform is started or stopped in this tool-server: `Request <id> not found. Native network capture is not started, so no requests are recorded. Call network-capture-start with udid and bundleId, repeat the action, then list the requests with native-network-logs.` |

The device can have a JS runtime capture for an app on a different Metro port. Then the text that says that capture is not started also gives that port: `This device has network capture for <bundleId> on Metro port <port>: pass port <port> to read it.`

After a `network-capture-start` that found the JS runtime layer unavailable, for example because Metro did not run on the port, `view-network-logs` gives the reason of that start: `Network capture is not started on the JS layer: network-capture-start for <bundleId> found it unavailable (<reason>). native-network-logs lists the requests of the native layer. Once the JS layer can start, call network-capture-start again, repeat the action, then call view-network-logs again.` For an ID from `view-network-logs`, `view-network-request-details` gives `Request <id> not found.` and the same text. `stop-all-simulator-servers` removes the reason. A later start or stop that stores a capture on the port also removes it.

After a `network-capture-start` that found the `ios-native` layer unavailable, for example because native devtools failed to initialize, `native-network-logs` gives the reason of that start. The result contains `status: "ok"` and `started: false`, and the header is `ios-native: unavailable, 0 requests (<reason>)`. After a stop, the header state stays `stopped`, and the header also gives the reason. `stop-all-simulator-servers` removes the reason. A later start that turns on the capture also removes it.

#### A started capture that lost the app

A read does not start the capture again, also when the capture lost the app. The read tells the state instead:

| Case                                                                                                                                                                                                                                         | Result                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The app reloaded its JavaScript or restarted after the start                                                                                                                                                                                 | `view-network-logs` gives `The JS layer of network capture for this app stopped recording at a JavaScript reload, so it recorded no requests since the reload. native-network-logs lists the requests of the native layer. To record the app's JavaScript requests again, call network-capture-start, repeat the action, then read again.`                                                |
| The JS runtime of the app was not ready at the start                                                                                                                                                                                         | `view-network-logs` gives `Network capture for this app is started, but the app's JavaScript runtime was not ready at the start, so the JS layer recorded no requests. native-network-logs lists the requests of the native layer. To record the app's JavaScript requests, call network-capture-start again, repeat the action, then read again.`                                        |
| A start did not reach the JS runtime of the app, for example because no app was connected to Metro. The JS runtime still has the pause of an earlier stop: `network-capture-stop`, `stop-all-simulator-servers` or the stop of a tool-server | `view-network-logs` gives `No network traffic captured. The app's JS runtime does not record new requests: an earlier stop paused it (network-capture-stop, stop-all-simulator-servers or the exit of a tool-server), and no network-capture-start reached it since. Call network-capture-start, then repeat the action.` When the list has requests, its first line gives the same note. |
| Android: a process of the app had the in-app agent and ended. The next process started without `launch-app` or `restart-app`                                                                                                                 | The header state of `native-network-logs` is `not attached`. See [Native network capture on Android](#native-network-capture-on-android).                                                                                                                                                                                                                                                 |
| Android: the app did not run at the start, and then started without `launch-app` or `restart-app`                                                                                                                                            | The header state of `native-network-logs` is `not armed`. The `header` line gives the reason `<bundleId> was not running at network-capture-start; launch-app or restart-app attaches the agent to its next process, or call network-capture-start once it runs`.                                                                                                                         |

In the first two cases, for an ID from `view-network-logs`, `view-network-request-details` gives `Request <id> not found.` and the same text.

The `header` line of `native-network-logs` gives one of these states after the name of the layer:

| State          | Meaning                                                                                                                                                                                                        |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `armed`        | The capture is ready in the current process of the app.                                                                                                                                                        |
| `not armed`    | The capture is started, but it is not ready. The `header` line gives the reason.                                                                                                                               |
| `not attached` | Android only. A process of the app with the in-app agent ended. The current process has no in-app agent, or the app exited.                                                                                    |
| `stopped`      | `network-capture-stop` stopped the capture. The list contains the requests from before the stop.                                                                                                               |
| `not started`  | No capture is started for the app, or `stop-all-simulator-servers` ended it. On a Mac app, `stop-simulator-server` also ends it. The list is empty.                                                            |
| `unavailable`  | Android only. The last start found that Argent cannot capture the app, for example in a build that is not debuggable, or when Argent cannot find `adb`. The `header` line gives the reason. The list is empty. |

When the expression of `debugger-evaluate` returns a Promise, Argent waits up to 10 seconds and returns the value it resolves to. A rejection fails the call with the reason. On Vega and on React Native 0.75 and older, the result is the internal fields of the Promise.

When two or more devices share one Metro, Metro does not list the device IDs from `list-devices`. For a booted local iOS simulator, Argent selects the app on the Metro device with the same name as the simulator. Argent does this only when exactly one booted local simulator and exactly one Metro device have that name. A simulator name with `&` or `+` never matches, because Metro lists it differently. For any other simulator, emulator or physical device ID, the debugger tools return `DEBUGGER_TARGET_DEVICE_MISMATCH` with the `logicalDeviceId` of each device on Metro, and `debugger-status` and `debugger-log-registry` return `not_connected` with the same list. Pass that `logicalDeviceId` as `device_id` in the next calls.

For react-native-macos and Mac Catalyst apps, see [JavaScript debugging on a Mac app](#javascript-debugging-on-a-mac-app).

## Native devtools

On a Mac app, these tools read the app through the Argent library:

- `native-describe-screen` reads the accessibility tree of the app, plus the views with an identifier that the tree does not contain. It does not take `skipClasses` or `skipClassPrefixes`.
- `native-full-hierarchy`, `native-find-views`, `native-view-at-point`, and `native-user-interactable-view-at-point` inspect AppKit views.
  - SwiftUI puts the identifier and the label of a control on an accessibility element, not on a view. Thus a `native-find-views` search by `identifier` or `label` does not find SwiftUI controls. `describe` shows them.
  - When a search by `identifier` or `label` finds no view, its result has a `note` that refers to `describe`.
  - For Mac Catalyst, use [`describe`](#mac-catalyst-apps) to inspect UIKit controls.
- `native-network-logs` reads the requests that the app sends through `NSURLSession`. As on iOS, a read never starts the capture: `network-capture-start` starts it, and `network-capture-stop` stops it. `view-network-request-details` reads the headers of a request by its `macos-` ID. The details contain a request body only when the app gives the body with the request, for example through `NSURLConnection`. The details contain no response body, and no other request body, for example the body of a `URLSession` request.

The [Mac apps](#mac-apps) section contains the details.

| Tool                    | Description                                                                                                                |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `native-full-hierarchy` | Get the complete UIKit view tree                                                                                           |
| `native-find-views`     | Search views by class, accessibility id, label, tag, or `nativeID`                                                         |
| `native-view-at-point`  | Inspect the deepest visible view at a native window point, or with `hitTest: true` the view that would receive touch input |
| `native-network-logs`   | Read native HTTP requests on iOS, Android and Mac apps. A read never starts capture                                        |

### Native network capture on Android

On Android, `native-network-logs` reads the OkHttp traffic of a debuggable app. The device must run Android 8.0 or later. Argent captures all OkHttp requests only on Android 9 or later. On Android 8.0 and 8.1, Argent captures only the requests of the React Native networking client and of Fresco. In an app without React Native, Argent captures no requests, and the capture state is `unavailable`. The app must run as `arm64-v8a` or `x86_64`. `network-capture-start` attaches an in-app agent to the running app.

To capture a request:

1. Call `network-capture-start` with the serial of the device and the package name of the app. The `android-native` entry of the result tells if the capture is armed.
2. Do the action that sends the request.
3. Call `native-network-logs` to read the list of requests.

| Parameter  | Effect on Android                                                                                                                                                                                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `udid`     | The serial of the device                                                                                                                                                                                                                                                             |
| `bundleId` | The package name of the app                                                                                                                                                                                                                                                          |
| `port`     | The Metro port. Argent removes the requests to this port on a local address from the list: `localhost`, `127.0.0.1`, `[::1]` or `10.0.2.2`. A request to this port on a different host stays in the list. The default is the Metro port of the device.                               |
| `limit`    | The maximum number of requests in the list, an integer of 0 or more. Argent returns the most recent requests, oldest first. With 0, `requests` is empty, and the result still gives the `header` and the `total`. Argent refuses a negative number or a fraction. The default is 50. |
| `clear`    | Remove the current requests from the later lists. Their IDs stay valid.                                                                                                                                                                                                              |

The result contains `header`, `armed`, `capture`, `captureDetail`, `count`, `total` and `requests`. After a stop, it also contains `stopped: true`. Before a start, it contains `started: false`. After a start that found the layer unavailable, it contains `started: false`, `capture: "unavailable"` and the reason of the start in `captureDetail`. The `header` line starts with `android-native: `, then the header state, for example `armed` or `not attached`. See [Network capture on iOS, Android and Mac apps](#network-capture-on-ios-android-and-mac-apps) for the header states. The `capture` field and the `header` line also show what the in-app agent captures. The `capture` field is absent when `armed` is `false`, except after a start that found the layer unavailable. The `captureDetail` field contains the detail that the in-app agent sent with the state. The `header` line shows this detail too. These are the values of `capture`:

| State       | Meaning                                                                                                                            |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| active      | Argent captures the OkHttp requests of the app. If Argent captures only some requests, the `header` line gives the reason.         |
| waiting     | The app did not load OkHttp yet. The capture starts when the app loads it.                                                         |
| unavailable | The in-app agent cannot capture in this process, for example because R8 fully minified OkHttp. The `header` line gives the reason. |

Each request has an ID with the format `android-<4 hex digits>-<number>`, for example `android-3f9a-12`. An ID is valid only in the tool-server that listed it. An ID stays valid after `network-capture-stop`. An ID is not valid after `stop-all-simulator-servers` stops the services of the device, or after the tool-server stops. Give the ID to `view-network-request-details` together with an id of the same device. This needs no debugger connection. The details contain these items:

- The request headers that went on the wire, for example `Cookie` and `User-Agent`. When Argent knows only the headers that the app set, the details say so.
- Each redirect with the request headers that went on the wire for it and the headers of its response, for example `Location`.
- The final URL of the response.
- The request body and the response body.

The details do not contain an initiator.

Only the in-app agent that Argent attached can report requests to Argent.

While native network capture is started for an app, these tools tell you:

| Tool                                            | What it reports                                                                                                                                                                                                                                                                                                                                                                                |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `launch-app`, `restart-app`                     | Argent attaches the in-app agent to the new process. The tool waits until the capture is ready, for at most 5 seconds. If the capture is not ready after this time, Argent reads the reason from the log of the device. This step can add 3 seconds when adb does not answer. The `networkCapture` field tells if Argent attached it. If Argent did not attach it, the field gives the reason. |
| `e2e-execute`                                   | A `launch` step uses `restart-app`. The report shows the `networkCapture` note as a `warning` on the first launch of the app, and again when the note changes. A new pid alone is not a change.                                                                                                                                                                                                |
| `react-profiler-start`, `native-profiler-start` | The result contains a `warning` that names the apps on the device with native network capture on. To profile without it, the warning tells you to call `network-capture-stop` for the app, then `restart-app`.                                                                                                                                                                                 |

A process of the app can also start in a different way, for example from a launcher tap, from a link or after a crash. Argent does not attach the in-app agent to this process. The header state of `native-network-logs` then depends on the earlier process:

- An earlier process had the in-app agent. When its connection closes, Argent checks the processes of the app. If the earlier process ended, the state is `not attached`.
- The app did not run at the start. The state is `not armed`, and the `header` line says that the app was not running at the start.

With `not attached`, the `header` line gives the pid of the new process when Argent saw it. An example is `android-native: not attached, 12 requests (the app restarted as pid 4711, and this tool-server did not attach capture to that process; call network-capture-start to attach it)`. If no process of the app runs, the `header` line says that the app exited. To attach the in-app agent, call `restart-app` or `network-capture-start`.

Native network capture stays on until `network-capture-stop` stops it for the app, or until Argent stops the services of the device. These stops are different:

| Stop                                                                                     | Effect on Android                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `network-capture-stop`                                                                   | Argent turns off the capture in the app. Argent keeps the requests, the session file, the files of the in-app agent and the `adb reverse` of the app. `network-capture-start` starts the capture again in the same process.                                                                                                                            |
| `stop-all-simulator-servers`                                                             | Argent turns off the capture in the app and removes the requests. Argent also removes the session file and the files of the in-app agent from the data directory of the app. Argent removes the `adb reverse` of the app too.                                                                                                                          |
| A stop of the tool-server: `argent server stop`, `SIGINT`, `SIGTERM` or the idle timeout | The same as `stop-all-simulator-servers`, for all devices. An uncaught exception or an unhandled rejection in the tool-server also runs these steps. A `kill -9`, a native abort such as an out-of-memory kill, a `SIGHUP` and `argent server stop` on Windows skip them. Closing the terminal of a foreground `argent server start` sends a `SIGHUP`. |

After each stop, the in-app agent stays in the current process of the app until this process ends. `launch-app` and `restart-app` do not attach the in-app agent. Call `restart-app` to start the app without the in-app agent. See [Network inspection](/docs/features/network) for the limits.

### Native `NSURLProtocol` layer on iOS

On iOS, `native-network-logs` reads the `URLSession` requests of an app on an iOS simulator. `network-capture-start` starts the capture with `Network.enable`. The start waits until the app acknowledges `Network.enable`, for at most 5 seconds. Thus a start for a connected app usually returns `armed: true` for the `ios-native` layer. Argent does not capture the requests from before the start.

On a simulator where Argent uses the socket of a device provider, the provider controls the capture. Argent does not send `Network.enable` there, because `Network.enable` resets the network settings of the provider, for example its throttling. Instead, `network-capture-start` asks the agent of the app if the capture is on. The start waits for the answer, for at most 5 seconds. If the app still connects to Argent, these 5 seconds also include the connection. While the capture is started, each call of `native-network-logs` asks again. After a stop, Argent does not ask. `armed` is `true` when the capture of the provider is on.

To capture a request:

1. Call `network-capture-start` with the UDID of the simulator and the bundle ID of the app.
2. Do the action that sends the request.
3. Call `native-network-logs` to read the list of requests.

| Parameter  | Effect on iOS                                                                                                                                                                                                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `udid`     | The UDID of the simulator                                                                                                                                                                                                                                                            |
| `bundleId` | The bundle ID of the app                                                                                                                                                                                                                                                             |
| `port`     | The Metro port. Argent removes the requests to this port on a local address from the list: `localhost`, `127.0.0.1` or `[::1]`. A request to this port on a different host stays in the list. This includes a request to `10.0.2.2`. The default is the Metro port of the device.    |
| `limit`    | The maximum number of requests in the list, an integer of 0 or more. Argent returns the most recent requests, oldest first. With 0, `requests` is empty, and the result still gives the `header` and the `total`. Argent refuses a negative number or a fraction. The default is 50. |
| `clear`    | Remove the current requests from the later lists. Their IDs stay valid. A request that runs at the time of the clear comes back in the list when it ends.                                                                                                                            |

The result contains `header`, `armed`, `count`, `total` and `requests`. After a stop, it also contains `stopped: true`. Before a start, it contains `started: false`. `count` is the number of entries in `requests`. `total` is the number of requests in the full list. The `header` line shows the header state, the number of requests and, when Argent knows it, the process ID of the app, for example `ios-native: armed, 12 requests (pid 4711)`. On a local simulator without a device provider, Argent reads the process ID when the app connects. A result from before the end of this read has no process ID. On a remote simulator, and on a simulator where Argent uses the socket of a device provider, Argent does not get the process ID. There, the `header` line has no process ID. See [Network capture on iOS, Android and Mac apps](#network-capture-on-ios-android-and-mac-apps) for the header states. When the state is `not armed`, the `header` line gives one of these reasons:

- Argent waits for the app to acknowledge `Network.enable`.
- The app did not acknowledge `Network.enable` within 5 seconds. `network-capture-start` and the next `launch-app` or `restart-app` ask the app again.
- `Network.enable` failed. The `header` line gives the error. `network-capture-start` and the next `launch-app` or `restart-app` ask the app again.
- The app is not connected. Argent arms the next process of the app when the process connects.

On a simulator of a device provider, Argent does not send `Network.enable`. Argent asks the agent of the app if the capture is on. When the state is `not armed`, the `header` line gives one of these reasons:

- The agent did not tell within 5 seconds if the capture is on. The next call of `native-network-logs` asks the agent again.
- The request to the agent failed. The `header` line gives the error. The next call of `native-network-logs` asks the agent again.
- The provider has the capture off. Turn the capture on in the provider.

On a simulator of a device provider, while the capture is started for the app, a call for an app that is not connected fails with the error `NATIVE_DEVTOOLS_NOT_CONNECTED`.

If the capture started while the app was already running, the `header` line of the first result says that Argent did not record the launch of the app. To capture the launch, call `restart-app`, then call `network-capture-start` again, because a relaunch ends the capture of the JS runtime layer. Then call `native-network-logs` again. On a simulator where Argent uses the socket of a device provider, Argent records the requests from the time that it connects to the agent of the app. This time can be before the call of `network-capture-start`. If the app already ran when Argent connected, the `header` line of the first result says that Argent did not record the requests from before this time. It also says that a relaunch ends the capture there, and it tells you not to restart the app.

Each entry of `requests` contains these fields:

| Field                | Content                                                                                                                                                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`                 | The ID of the request, with the format `ios-<4 hex digits>-<number>`, for example `ios-3f9a-12`                                                                                                                                                        |
| `method`, `url`      | The method and the URL that the app requested                                                                                                                                                                                                          |
| `state`              | `pending`, `headers`, `complete` or `failed`                                                                                                                                                                                                           |
| `status`, `mimeType` | The status and the MIME type of the response, after the response headers arrive                                                                                                                                                                        |
| `durationMs`         | The duration of the request on the network, as the in-app agent measured it, when Argent knows it. On a simulator where Argent uses the socket of a device provider, this duration does not include the delay that the throttling of the provider adds |
| `errorText`          | The error of a failed request                                                                                                                                                                                                                          |

An ID is valid only in the tool-server that listed it. An ID stays valid after `network-capture-stop`. An ID is not valid after `stop-all-simulator-servers` stops the services of the device, or after the tool-server stops. Give the ID to `view-network-request-details` together with an id of the same device. This needs no debugger connection. The details contain these items:

- The request headers that the app set. The headers that iOS adds on the wire, for example `Cookie` and `User-Agent`, are not in the details. The `headersNote` field of the request says so.
- The headers of the response.
- The final URL of the response, after all redirects, in `response.url`.
- The request body and the response body. Argent reads them from the app process. The `HTTPBody` of an `NSURLConnection` request comes with the request when this body is UTF-8 text, so Argent does not read it from the app process. Argent reads an `HTTPBody` that is not UTF-8 text from the app process, for example a body in ISO-8859-1.

As in the other layers, Argent replaces the values of secret headers with `[REDACTED]`. Argent does not replace the data in the URLs and in the bodies. Argent shortens a body that is longer than 1000 characters. A `[TRUNCATED: ...]` line before the shortened body gives the size of the full body. Argent omits a binary body, and gives its MIME type and its size. The `NSURLProtocol` layer can keep only the start of a large body. For such a body, Argent gives the full size in bytes if Argent knows it, and the number of bytes that the layer kept. The app can end the upload of a body stream before the stream reaches its end, for example when the app cancels the task or the task times out. Then the request body contains only the bytes that the app wrote before that time. A `[TRUNCATED: ...]` line before this body tells that the upload ended, and gives the number of these bytes. It gives the full size as `unknown`.

The details do not contain redirects, `fromCache` or an initiator.

A body that Argent cannot read shows `[unavailable: <reason>]`, for example when the response has no body. The table gives three of the reasons:

| Body                                                                                                  | Cause and action                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[unavailable: the app may still be sending this request body; read it again after the request ends]` | The request has no response yet. The app did not send all of the request body yet, or the agent no longer holds the request body. Argent gives this answer within about 5 seconds, or later while Argent reads another body of the app. Call `view-network-request-details` again after the request ends. |
| `[unavailable: the app did not answer within 5 s; read it again later]`                               | The request has a response, but the app did not send the request body within about 5 seconds. For example, the app is busy or sends a large body. Call `view-network-request-details` again.                                                                                                              |
| `[unavailable: the app process that made the request is gone]`                                        | The app process ended, for example after a relaunch or a crash, and Argent has no copy of the body.                                                                                                                                                                                                       |

For each app on each device, Argent keeps a copy of the 64 bodies that the agent read most recently. These copies contain a maximum of 67,108,864 characters together. If one body is longer, Argent keeps a copy of only that body until the agent reads the next body. A later read of a body with a copy uses the copy. After the app process ends, a body is available only if Argent has a copy of it. The `HTTPBody` of an `NSURLConnection` request is an exception when this body is UTF-8 text. Argent keeps this body with the request. It stays available after the app process ends, and it does not count toward these limits. An `HTTPBody` that is not UTF-8 text is not an exception. If the app process ends before the agent reads this body, the body is not available. If the agent reads this body, its copy counts toward these limits.

On a simulator without a device provider, when the connection of the app closes, Argent marks each request that still runs as `failed`. The `errorText` field gives one of these errors:

| `errorText`                                                                                              | Cause                                                                             |
| -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `the app process ended before the request finished`                                                      | The app process ended, or the app relaunched.                                     |
| `the agent did not reconnect after its connection dropped, so this request's final events never arrived` | The connection closed, and Argent did not find a sign that the app process ended. |

The list also contains the requests of the earlier processes of the app. On a simulator where Argent uses the socket of a device provider, a relaunch of the app clears the list. Argent keeps the 2000 most recent requests of each app. Argent keeps fewer requests when the requests have very large headers or URLs. Large UTF-8 request bodies that the app sends with `NSURLConnection` also make Argent keep fewer requests. Argent keeps the list until `stop-all-simulator-servers` stops the services of the device, a local simulator shuts down, or the tool-server stops. `network-capture-stop` keeps the list.

While the capture is started for an app, Argent arms each new process of the app when the process connects. This is also true for a process that starts from a tap on the home screen or from a link. While the capture is started, these tools tell you:

| Tool                                            | What it reports                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `launch-app`, `restart-app`                     | On a local simulator, the tool waits until the new process is armed, for at most 5 seconds. The `networkCapture` field tells that the capture is armed, with the process ID. If the capture is not armed yet, the field tells that the new process did not connect or did not acknowledge `Network.enable` yet. Then `native-network-logs` shows when the capture is armed. When the last `Network.enable` to the process failed, the tool sends `Network.enable` again. If `Network.enable` fails, or the app does not acknowledge it within 5 seconds, the field gives the reason. If the process of the app stops before it is armed, for example after a crash at the start, the tool does not wait for the full 5 seconds. Then the field tells that no process of the app runs. If the process stops before it connects to Argent, the tool finds this only at the end of the 5 seconds. Then the field also tells that no process of the app runs. Without `launchArgs`, `launch-app` does not start a new process when the app already runs. If that process does not have the injection of Argent, or started before the tool-server started the services of the device, the tool does not wait. The field tells you to call `restart-app`. On a remote simulator and on a simulator of a device provider, the result has no `networkCapture` field. |
| `e2e-execute`                                   | A `launch` step uses `restart-app`. The report shows the `networkCapture` note as a `warning`, with the same rules as on Android.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `react-profiler-start`, `native-profiler-start` | The result contains a `warning` that names the apps on the simulator with the capture on. The warning names only the apps that connected to Argent at least once. To profile without it, the warning tells you to call `network-capture-stop` for the app, then `restart-app`. On a simulator of a device provider, the result has no warning, because the capture there is the capture of the provider.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

The capture stays on for the app until `network-capture-stop` stops it for the app, Argent stops the services of the device, or a local simulator shuts down. Argent stops the services of the device at `stop-all-simulator-servers` and at a stop of the tool-server. On a device of a device provider, Argent also stops them when the provider changes the grant of the device. `network-capture-stop` sends `Network.disable` to the connected app and waits for the acknowledgement, for at most 5 seconds. On a Mac app, a late acknowledgement of the `Network.disable` of an earlier stop also confirms the stop, unless `network-capture-start` came after that stop. After the stop, Argent records no new request of the app. Argent does not arm a new process of the app. A request that runs at the stop completes in the list. `stop-all-simulator-servers` and a stop of the tool-server also send `Network.disable` to each connected app with a started or stopped capture. Then they remove the list. On a simulator of a device provider, Argent sends no `Network.disable`, because the provider owns the capture setting.

## Mac apps

Use these tools for native Mac apps, including [Mac Catalyst](#mac-catalyst-apps). See [Mac apps](/docs/features/mac-apps) for setup and supported workflows.

The `macos-apps` [feature flag](/docs/reference/configuration#feature-flags) is on by default. When disabled, Mac apps disappear from `list-devices`, and tools reject Mac app IDs. The `file-panel` and `menu-bar` tools are available only on a macOS host with the flag enabled.

### Start and restart an app

Call `boot-device` with the path to your built app:

```json
{ "macosAppPath": "/Users/anna/Projects/Notes/build/Notes.app" }
```

Argent returns a device ID such as `macos-app-com.example.notes`. Pass that ID as `udid` to subsequent tools. Each bundle identifier represents one device.

| `boot-device` parameter | Description                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------------- |
| `macosAppPath`          | Path to the `.app` bundle. Argent launches the app in the background.                                   |
| `macosAppArgs`          | Executable arguments. Defaults to no arguments.                                                         |
| `udid`                  | Device ID instead of a path. Reuses the last app path, or the newest matching build found by Spotlight. |
| `force`                 | Restart the same build, including a copy started outside Argent. Never replaces a different build.      |

The result contains `platform: "macos"`, `id`, `kind`, `bundleId`, `pid`, `appPath`, `sandboxed`, `logPath`, `args`, and `booted: true`. A running app returns `alreadyRunning: true` without restarting. Check `appPath` to confirm which build runs and `logPath` for app output.

`boot-device`, `list-devices`, `launch-app`, and `restart-app` report `kind: "catalyst"` for Mac Catalyst and `kind: "app"` for other native Mac apps. The kind follows the last build Argent started for that bundle identifier and persists across tool-server restarts.

A `note` reports conditions that need attention, such as no open window or arguments that differ from the request. Launch tools wait up to 10 seconds for a window. Use `force` to apply changed arguments to an already running app.

| Tool                                                  | macOS behavior                                                                                                                                        |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list-devices`                                        | Lists running apps started by Argent under `platform: "macos"`.                                                                                       |
| `launch-app`                                          | Starts the app if needed. Leaves a running app unchanged.                                                                                             |
| `restart-app`                                         | Quits the app and starts the same bundle again. Rebuild first to test code changes.                                                                   |
| `open-url`                                            | Delivers the URL to the running app. Web URLs go to the app, not a browser.                                                                           |
| `reinstall-app`                                       | Unsupported. Rebuild and use `restart-app`.                                                                                                           |
| `stop-simulator-server`, `stop-all-simulator-servers` | Disconnect Argent. The app keeps running; network capture stops and its recorded requests are lost. `network-capture-start` starts the capture again. |

For `launch-app` and `restart-app`, `bundleId` must match the device. Both accept `launchArgs` and otherwise reuse the previous arguments. Both report `appPath` and `args`.

`open-url` accepts `http`, `https`, and `file` URLs. Other schemes must appear in the app's `CFBundleURLTypes`.

The app starts with `/` as its working directory and basic login variables such as `HOME`, `USER`, `PATH`, and `LANG`. It does not inherit custom environment variables from the tool-server.

#### Handle running copies and save prompts

Argent cannot attach to a copy launched outside Argent. Save your work and quit that copy, or use `boot-device` with `force: true`. **A forced launch can lose unsaved changes.**

Argent refuses to replace a different build with the same bundle identifier, even with `force`. Quit that build or use [distinct bundle identifiers](#run-builds-from-separate-worktrees).

Restarts, e2e `launch` steps, and `native-profiler-start` with `malloc_stack_logging: true` stop if the app asks whether to save changes. Answer the prompt before retrying or restarting the tool-server. Use [`file-panel`](#file-panel) for a new document's Delete or Don't Save prompt.

An unresponsive app can be force-quit after five seconds. Check the result's `note` for possible loss of unsaved changes.

#### Resolve launch and connection failures

| Problem                                                  | Action                                                                                                 |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Code signing blocks launch                               | Follow [Configure code signing](#configure-code-signing).                                              |
| The saved app path no longer exists                      | Call `boot-device` with the current `macosAppPath`.                                                    |
| The app does not connect during launch                   | Check the log in the error. Make sure startup does not block the app's main thread.                    |
| The app uses a launcher script                           | Point Argent at a bundle whose executable is the native app.                                           |
| The app is a "Designed for iPad" app                     | Build the Mac Catalyst target of the app and start that build, or test the app on an iOS simulator.    |
| The app has no supported window                          | Open a standard window. Apps with only panels, borderless windows, or a menu bar icon are unsupported. |
| The launch result warns that reconnection is unavailable | After disconnecting, use `restart-app`. This can occur in sandboxed apps with long bundle identifiers. |
| The Argent library files are missing                     | Update Argent and retry.                                                                               |

If the app does not connect within 20 seconds, Argent stops it and includes recent app output in the error.

### Configure code signing

Argent loads a library into the app at launch. Code signing must permit that library. Use a Debug build; the standard Xcode macOS App and react-native-macos templates work without changes.

For a Mac Catalyst Debug build, Xcode's **Sign to Run Locally** setting normally works as is. Development-team signing enables the hardened runtime by default. If library validation blocks launch, use one of the options below. Signing the Argent library with your team needs no provisioning profile.

For a Debug build with the hardened runtime, choose one option:

| Option                                                                           | When to use it                                                                                        |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Set `ENABLE_HARDENED_RUNTIME = NO` for Debug                                     | Use this when your test build does not require the hardened runtime. Keep Release settings unchanged. |
| Add `com.apple.security.cs.disable-library-validation` to the Debug entitlements | Use this when your test build needs the hardened runtime.                                             |
| Sign the Argent library with your app's team                                     | Use this when your development-signed build must retain library validation.                           |

To sign the library with your team:

1. Try to start the app. The launch error provides the `codesign` command.
2. Run `security find-identity -v -p codesigning` to find your team's Apple Development identity.
3. Substitute that identity into the provided command and run it yourself. Signing requires access to your keychain.
4. Start the app again. Repeat signing if an Argent update changes the library.

Ad hoc signed builds have no signing team and cannot use the team-signing option.

A separate code-signing flag, `--options library`, blocks Argent even when the app disables library validation through an entitlement. Remove that flag from the test build's signing options, such as `OTHER_CODE_SIGN_FLAGS`.

Exported builds with the hardened runtime need `com.apple.security.cs.allow-dyld-environment-variables`. They also need `com.apple.security.cs.disable-library-validation` or an Argent library signed by the app's team. A Release configuration signed for development can work without the first entitlement because development signing permits debugging.

**Keep these signing changes out of distributed builds.** Use a development build for testing. Argent is tested with apps you build; other apps may have incomplete inspection or input support even when their signatures permit launch.

### Run builds from separate worktrees

Give each build a unique bundle identifier to run worktrees in parallel:

1. In the app target, set `PRODUCT_BUNDLE_IDENTIFIER` to `com.example.notes$(ARGENT_ID_SUFFIX)`.
2. Build each worktree with a different suffix and output directory. For a scheme named `Notes`:

   ```bash
   xcodebuild -scheme Notes -configuration Debug \
     -derivedDataPath ./build ARGENT_ID_SUFFIX=.login build
   ```

3. Give the agent the resulting `.app` path and bundle identifier, such as `com.example.notes.login`.
4. Use that identifier in the e2e test's `launch` step.

Builds without `ARGENT_ID_SUFFIX` keep the original identifier. Set the suffix on the command line, not `PRODUCT_BUNDLE_IDENTIFIER` itself: a global override also changes CocoaPods bundle identifiers.

If you copy and re-sign an existing bundle instead, preserve its entitlements. Removing entitlements can disable the App Sandbox. Ad hoc signed copies cannot retain team-dependent features such as iCloud, keychain sharing, or app groups.

### Inspection and input

Coordinates use the app window, including its title bar, with the origin at the top left. Sheets, popovers, alerts, and menus can extend that area. Use the frames returned by `describe` for input coordinates.

Other app windows are excluded.                                                                                                                                                                         |
| `screenshot-diff`                       | Captures at `scale: 1.0`. Save baselines at the same scale. No top band is masked.                                                                                                                                                                                                |
| `gesture-tap`                           | Click, double-click (`clickCount: 2`), open a context menu (`button: "right"`), or [hold keys](#clicks-with-modifier-keys).                                                                                                                                                       |
| `gesture-drag`                          | Drags with the left button. Equal start and end points produce a long press.                                                                                                                                                                                                      |
| `gesture-scroll`                        | Scrolls the content under the point, like a mouse wheel. `durationMs` has no effect.                                                                                                                                                                                              |

| `paste`                                 | Inserts text into the focused editable control. Leaves the clipboard unchanged and does not invoke app paste handlers.                                                                                                                                                            |

The list keeps the requests of earlier processes of the app. |

#### Clicks with modifier keys

On a Mac app, pass `modifiers` to `gesture-tap` as a list of keys from `control`, `option`, `shift`, and `command`. For example, `["command"]` can toggle a row in a selection. The effect depends on the control. The keys are held for the entire gesture, including both clicks of a double-click. An empty list leaves the click unmodified. Other targets reject nonempty lists.

`MACOS_APP_LIBRARY_OUTDATED` means the app's loaded Argent library lacks modifier-click support. The tool stops before clicking. Run `restart-app` to reload the library, then retry. If the error persists, use an Argent build that includes modifier-click support.

#### Screenshots and scrolling

Use `scale: 1.0` for one pixel per point. By default, screenshots downscale windows larger than 768 points on the longest side, to at least 0.6 pixels per point. The minimum explicit scale is `0.1`. Mac apps ignore `ARGENT_SCREENSHOT_SCALE` and `rotation`.

#### Rotated devices

All coordinates use the UI as the user sees it, also when the UI is landscape or upside down. On an iOS simulator, Argent turns these surfaces to the orientation of the UI:

- Screenshots
- `describe` frames
- The points of the native view tools
- The tap points of `debugger-component-tree`
- The coordinates of the gesture tools

Argent reads the orientation of the UI from the device for each action. Argent uses a reading for at most one second, and reads again after `rotate`, `fold`, `button`, `launch-app`, `restart-app`, `open-url`, `terminate-app` and `reinstall-app`. All touches of one gesture use one reading. The orientation follows the app, not the device. Thus a portrait-only app on a rotated device stays portrait.

If Argent cannot read the orientation, the tool result has a note. For a live capture of `screenshot-diff`, the note is in the summary. Then Argent uses the portrait axes of the screen. The `rotation` parameter of `screenshot` overrides the orientation of the image only. With it, the image can disagree with the coordinates.

Scrolling targets the nearest scrollable content under the point. Web content scrolls first; an enclosing native scroll view can take over at the page boundary. The call fails if no eligible content can scroll.

`scrolled: true` does not prove movement. Compare the tree before and after scrolling to detect the end of a list.

#### Text checks

A `text` check on a field reads its entered text, not its placeholder. A container check includes descendant text but skips subtrees with their own identifiers. Web elements and non-accessibility views expose the text they display.

When several elements match, text checks prefer an open menu or combo box list, then the uppermost alert, sheet, or popover, then the window. A matching paragraph takes precedence over the text area that contains it.

### `describe` on a Mac app

| Identifier     | A stable identifier supplied by your app. See the examples below.                                                 |
| Label          | The control's label, associated text, or placeholder when no label exists.                                        |
| Value          | Current text or state. Date pickers use ISO 8601 in the Mac's time zone; token fields use comma-separated tokens. |
| `[clickable]`  | A control that responds to clicks.                                                                                |

Set identifiers in your app:

| App type                    | Identifier source                                                     |

| React Native (Mac Catalyst) | `testID="save-button"`                                                |

Argent omits identifiers generated by AppKit or SwiftUI, such as `ListRow`. A view with an identifier can appear even if it is not an accessibility element.

The tree excludes hidden, scrolled-out, or out-of-bounds elements. Native controls covered by sheets, popovers, or other app windows can also be excluded. The menu bar is separate: use [`menu-bar`](#menu-bar).

Web inspection includes open shadow roots and same-origin iframes. Closed shadow roots and cross-origin iframes are unavailable. A JavaScript alert, confirmation, or prompt replaces the page content in the tree until dismissed.

Read the result's hint when elements are missing. A minimized window produces an empty tree. Reads can also be incomplete because of unresponsive elements or size limits: 3000 elements and 40 levels of depth. While the Mac is locked, inspection can miss context menus, and `hidden` checks cannot pass reliably. Unlock the Mac and retry.

### `file-panel`

Use `file-panel` to answer open and save dialogs by path. The system file list is unavailable to `describe` and `gesture-tap`.

After opening a save dialog, choose a destination:

```json
{
  "udid": "macos-app-com.example.notes",
  "action": "choose",
  "path": "~/Desktop/report.pdf"
}
```

:::caution Existing files can be overwritten

`choose` and prepared save answers bypass overwrite confirmation. The result does not indicate whether the destination already existed. Check the destination before saving.

:::

| Parameter   | Description                                                                                                                             |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `udid`      | Mac app device ID.                                                                                                                      |
| `action`    | `list`, `choose`, `cancel`, `discard`, or `stub`.                                                                                       |
| `path`      | For `choose` or a `stub` answer: absolute path or `~/` path. Open targets must exist; save destinations need an existing parent folder. |
| `paths`     | Multiple open targets, if the dialog allows multiple selection. Use `path` or `paths`, not both.                                        |
| `panel`     | Panel number from `list`. Required when more than one panel is open.                                                                    |
| `timeoutMs` | Wait for a panel before `choose`, `cancel`, or `discard`. Default `5000`; maximum `30000`.                                              |
| `stubMode`  | For `stub`: `answer` (default), `cancel`, or `off`.                                                                                     |
| `panelKind` | For a prepared answer: `open` or `save`. Set this explicitly for repeatable tests.                                                      |

| Action    | Result                                                                                                |
| --------- | ----------------------------------------------------------------------------------------------------- |
| `list`    | `{ panels }` with each panel's number, kind, title, folder, and options.                              |
| `choose`  | `{ chosen, panel, kind, paths }`. Closes the dialog and delivers the paths to the app.                |
| `cancel`  | `{ cancelled, panel }`.                                                                               |
| `discard` | `{ discarded, panel }`. Closes a new document without saving. Requires a Delete or Don't Save button. |
| `stub`    | `{ armed, mode, panelKind }`. Prepares an answer for the next matching dialog, without showing it.    |

Set visible app-specific controls, such as a format selector, before `choose`. Controls hidden behind the system's Show Options button are unavailable.

#### Prepare an answer before a dialog opens

Use `stub` before an action that opens a dialog. A prepared answer waits for a matching `panelKind`; other dialogs open normally. For example, a prepared open answer does not dismiss an intervening save dialog.

Without `panelKind`, existing paths imply `open`; a single new path implies `save`. A prepared cancel applies to the next dialog of either kind. Use `stubMode: "off"` to remove a prepared answer. Disconnecting Argent also removes it.

If a dialog rejects a prepared answer, it opens normally. Call `list` and read `stubRefused` for the reason.

#### File types and sandbox access

- A save dialog accepts one file path. An open dialog accepts multiple paths only when configured for multiple selection.
- The path must match the dialog's file or folder selection mode. A document package counts as a file.
- Save extensions must match an allowed format unless the app allows other file types. Formats `public.data` and `public.item` accept any extension.
- With multiple save formats, the extension selects the format on macOS 15 and later. On macOS 14, the dialog keeps its initially selected format.
- Open paths are not checked against the dialog's allowed file types.
- Sandboxed apps receive access only to the selected paths. A save answer grants access to the file, not its entire folder.

### `menu-bar`

Use `menu-bar` for commands outside the app window. The app stays in the background, and the pointer does not move.

Read the available commands with `action: "list"`, then choose one by its current titles:

```json
{
  "udid": "macos-app-com.example.notes",
  "action": "choose",
  "path": ["File", "Export..."]
}
```

| Parameter    | Description                                                           |
| ------------ | --------------------------------------------------------------------- |
| `udid`       | Mac app device ID.                                                    |
| `action`     | `list` or `choose`.                                                   |
| `path`       | One to nine titles from the top-level menu to the command.            |
| `identifier` | Command identifier from `list`. Use `path` or `identifier`, not both. |

`list` returns `{ menuBar, items }`: an indented menu tree and item count. Disabled and checked items are marked. `choose` returns `{ chosen }` with the selected path, plus `identifier` when used.

Title matching ignores case and treats `...` and `…` as equivalent. Use the title currently shown, such as `Undo Delete Task`. Window-menu identifiers distinguish windows with the same title but change when a window reopens.

If a command is disabled, focus the relevant control or dismiss the current alert. If a pop-up or context menu is open, press Escape before choosing a menu-bar command. Missing items, ambiguous identifiers, and submenu titles produce errors with available choices.

The menu list stops at 2000 items or eight submenu levels. Check `truncated` and `hint` if the result is incomplete.

### Mac Catalyst apps

Use `describe` or `native-describe-screen` to inspect UIKit controls through the accessibility tree. The four [AppKit inspection tools](#native-devtools) return an unsupported-tool error on Mac Catalyst.

- **Windows.** `describe` and `screenshot` show the front window. Use the Window menu with [`menu-bar`](#menu-bar) to switch windows. Tap the target field before typing so it has focus.
- **Text and alerts.** Typed text replaces an active input method composition. Tap fields if SwiftUI's Tab order differs from the visible order. Tap the alert button if Return has no default action or Escape leaves a UIKit text-field alert open.
- **Toolbar menus.** With **Optimize Interface for Mac**, some UIKit toolbar menu buttons have no identifier. Select them by label.
- **Drag and drop.** Pan and drag gestures work. UIKit drag and drop between views is unsupported.
- **File dialogs.** [`file-panel`](#file-panel) works with the UIKit document picker and SwiftUI's `fileImporter` and `fileExporter`.
- **Web views.** `describe` includes `WKWebView` content. Typing, paste, scrolling, and text selection work in it. `network-capture-start` and `native-network-logs` capture the app's `URLSession` requests only. They do not capture `WKWebView` traffic.
- **Password fields.** Focusing an empty password field can show the macOS Passwords AutoFill pop-up. Input still works.
- **Modifier clicks.** UIKit controls can respond to modifier clicks. React Native `Pressable` handlers receive the press without modifier keys. SwiftUI `List` row selection stays single-select with Command-click or Shift-click.

If typing, paste, or scrolling reports success without changing the app, check that your Argent build includes the native library with Mac Catalyst input support.

### Profiling a Mac app

Pass the Mac app's `device_id` to `native-profiler-start`, `native-profiler-stop`, `native-profiler-analyze`, and `profiler-stack-query`. Use `profiler-load` with `mode: "load_native"` to reopen a saved native session. See [Profiling](#profiling) for shared behavior.

- **Start.** Launch the app through Argent first and omit `app_process`. The bundled Instruments template captures CPU samples, UI hangs, and memory leaks. In a desktop session, Argent requires `com.apple.security.get-task-allow` on signed builds to avoid an administrator prompt that blocks recording. If you get `NATIVE_PROFILER_APP_NOT_DEBUGGABLE`, use a development-signed build. In a background session such as SSH, pass `template_path: "Time Profiler"` to profile CPU and hangs on a signed build without that entitlement.
- **WebKit and leak checks.** With malloc stack logging off, Argent refuses the bundled template if it detects a WebKit heap (`NATIVE_PROFILER_APP_HAS_WEBKIT_HEAP`) or the check fails (`NATIVE_PROFILER_APP_HEAP_CHECK_FAILED`). The check applies only to the bundled template. With logging off, any template that uses the Allocations instrument, including `Leaks` and `Allocations`, can freeze an affected app until you force-quit it.

  To record CPU and hangs without restarting or checking for leaks, use `template_path: "Time Profiler"`. To record leaks, keep the bundled template and set `malloc_stack_logging: true`.

- **Trace older allocations.** The bundled template can capture allocation stacks for objects allocated during recording. To trace allocations from launch, set `malloc_stack_logging: true`. This restarts the app and clears its current state. If start reports that it restarted the app, malloc stack logging stays active even if Instruments fails to attach. Use `restart-app` to remove the overhead before measuring CPU or hangs.
- **Stop and recover.** Check `warning` and `exportDiagnostics` for an incomplete trace or skipped exports. If Instruments failed to attach or exited during startup, confirm the app is running and start a new recording. If the app ended or Instruments stalled during stop, repeat the scenario when you need a complete trace.

#### Interpret pauses and leak results

During capture, Argent can wait up to 25 seconds before sending an action to a suspended app. If an action times out with `MACOS_APP_RPC_TIMEOUT`, check the app with `describe` before retrying. An action that was already sent may have taken effect.

When suspension timing is available, the report keeps the duration Instruments recorded and shows how much of the hang overlapped a pause. The overlap can extend a hang when the app has work to finish. A wait for something like a timer or I/O can continue through the pause. Repeat the same actions with `template_path: "Time Profiler"` to measure hangs without leak checks.

A short recording may end before a leak check finishes. Follow the report's warning and [allow time for a leak check](/docs/features/profiling#limits). With `Time Profiler`, the report says that memory leaks were not checked.

#### React profiler on a Mac app

Start a [supported Debug build](/docs/features/mac-apps#profile-a-react-native-app) through Argent.
Pass `id` from the app's `list-devices` entry as `device_id`, even on a shared Metro. The profiler
connects directly to Metro. The [JavaScript debugger tools](#javascript-debugging-on-a-mac-app) use
the same `device_id` and `port`.

Use the same `device_id` and Metro `port` for the React profiler and query tools. The default port
is 8081. To reopen a saved React profile, use `profiler-load` with `mode: "load_react"`. To compare
React commits with native hangs, record both profiles during the same interaction. Analyze both
profiles before calling `profiler-combined-report`.

If Metro lists other runtimes but cannot find the Mac app, tools that need the runtime return
`DEBUGGER_TARGET_DEVICE_MISMATCH` and list the available targets. If Metro lists no runtimes, they
return `DEBUGGER_METRO_NO_TARGETS`. In either case, `react-profiler-status` returns
`session_status: "no_react_runtime"` with the reason in `note`. Check that the app is running,
wait for it to load its JavaScript, and verify the Metro port before retrying.

If a Mac Catalyst error mentions a missing `identifierForVendor`, run `restart-app` and retry. If
the error persists, update Argent. The profiler needs this value to identify the app on a shared
Metro server.

For `react-profiler-analyze` on a react-native-macos app, pass `platform: "macos"` if the recording
lacks platform information. The report prefers `.macos.*` source files, then `.native.*` files, then
files without a platform suffix. If the recording lacks architecture information, the tool checks
`macos/Podfile`. A Mac Catalyst app runs the iOS bundle, so its report uses `.ios.*` files and
`ios/Podfile`.

### JavaScript debugging on a Mac app

The `debugger-*` tools, `view-network-logs`, and `view-network-request-details` accept a Mac app ID. They need the same [Debug build](/docs/features/mac-apps#profile-a-react-native-app) as the React profiler. Start Metro before you start the app.

- **Device ID.** Pass the Mac app ID (`macos-app-<bundle id>`) as `device_id`. Pass `port` if Metro does not use port 8081. Keep the Mac app ID for all calls. Do not use the `logicalDeviceId` that `debugger-connect` returns.
- **Start.** The tools connect through Metro and do not use the Argent library. A react-native-macos Debug build that `boot-device` refuses with `MACOS_APP_HARDENED_RUNTIME` works when you start it yourself. `describe` and the gesture tools do not work on that build. Start a Mac Catalyst app through Argent: React Native puts the vendor ID of the app in its runtime ID, and the Argent library reports this ID.
- **Target.** The tools connect only to the runtime of the Mac app. They do not use another runtime on the same Metro. If Metro cannot find the Mac app, the tools return `DEBUGGER_TARGET_DEVICE_MISMATCH` and list the available targets. `debugger-status` returns `reason: "device_mismatch"`.
- **Component tree.** The tap points of `debugger-component-tree` are fractions of the app window, title bar included. `describe` and `gesture-tap` use the same coordinates.
- **Several windows.** `debugger-component-tree` and `debugger-inspect-element` read one React Native root: the root with the most components. If the app shows React Native in more than one window, this root can be in another window than the window that `describe` and `gesture-tap` use. Close the other windows, or compare the results with `describe`.
- **Inspect element.** `debugger-inspect-element` takes `x` and `y` in points from the top-left corner of the window, title bar included. To convert a tap point, multiply it by the `Screen: WxH` size that `debugger-component-tree` prints.
- **Old architecture.** On react-native-macos with the old architecture (Paper), `debugger-component-tree` and `debugger-inspect-element` convert window coordinates on the assumption that the React Native root view fills the content view of the window. If the app puts native views around the root, for example a footer below it, the tap points and inspected points are off by the size of those views. In that case, use the frames that `describe` returns for tap coordinates.
- **Reload.** `debugger-reload-metro` reloads a Mac app only through its debugger connection. If that reload fails, the tool returns `DEBUGGER_RELOAD_FAILED`. It does not use the `/reload` endpoint of Metro, because that endpoint reloads every app on that Metro.
- **Network.** `view-network-logs` records the `XMLHttpRequest` and `fetch()` requests of the JavaScript code. `native-network-logs` records the same `fetch()` requests from `URLSession`. Thus the two lists overlap. Use `view-network-logs` for the JavaScript view.

| `react-profiler-stop`             | Stop profiling and collect the CPU profile and commit tree                         |
| `react-profiler-status`           | Check if a React profiler run records, was saved, was lost or taken over           |
| `react-profiler-analyze`          | Analyze stored profiling data into a markdown performance report                   |
| `react-profiler-fiber-tree`       | Inspect the React fiber tree as JSON                                               |
| `native-profiler-start`           | Start native profiling: Instruments on iOS and Mac apps, Perfetto on Android       |
| `native-profiler-stop`            | Stop native profiling and export the trace                                         |
| `native-profiler-analyze`         | Analyze an exported native trace into a markdown report                            |
| `native-profiler-launch-analysis` | Measure iOS app launch times with XCTest or record a launch with Xcode Instruments |
| `profiler-combined-report`        | Cross-correlate React Profiler and native profiler data                            |
| `profiler-load`                   | Restore a previously captured session from disk so query tools can use it          |
| `profiler-commit-query`           | Query React commit data, or the render counts of each component                    |
| `profiler-cpu-query`              | Query Hermes CPU profile data with targeted modes                                  |
| `profiler-stack-query`            | Query native trace data for iterative native investigation                         |

If Argent cannot read the UI hangs table from an Instruments trace, `profiler-load`, `profiler-stack-query`, and `profiler-combined-report` report missing hang data. An empty table gives a count of zero hangs.

Argent caps Instruments recordings at 10 minutes on iOS simulators and [Mac apps](#profiling-a-mac-app). Call `native-profiler-stop` to recover the available trace after the cap or an unexpected exit.

While stop is saving and exporting on the same target, a second stop joins the first. Start and analyze wait for it to finish. Retry `profiler-load` or `profiler-combined-report` after stop completes if the tool reports that the capture is still in progress.

Instruments reports exclude CPU time attributed to Argent and Instruments from app hotspots. Percentages still use all sampled CPU time with call stacks. Hang reports label suspect functions from either tool. If the report says the main thread likely waited, treat those functions as context for the wait.

In the `top_functions` and `time_window` modes, `profiler-cpu-query` gives the self time of each call-tree node as a share of the sampled time. A function that runs on several call paths has one row for each path, and `top_n` counts rows. With `react_only`, `profiler-cpu-query` lists only the functions with a PascalCase name, which is the name format of a React component.

`react-profiler-stop` stores the data of each component only for the hot commits and the commits next to them. A commit is hot when it takes 16 ms or more. `react-profiler-stop` also stores the render count and the render time of each component over all commits. `profiler-commit-query` with `mode: "render_counts"` returns these counts. A session that an older version of Argent stored does not have them.

The report of `react-profiler-analyze` contains these items:

- The `React render time` line: total render time, session length, share of the session, largest share in one second, and number of commits. These values are approximate. React DevTools gives only the largest rendered subtree of each commit as the commit duration. Argent uses the sum of the component render times of a commit when that sum is larger. The values do not include effects or native work. A development build is slower than a production build.
- "No commit reached 16ms" when no commit takes 16 ms or more. The report does not say that the session is good or bad.
- A warning when no commit is hot but a commit takes 16 ms or more. Argent can name no component of this commit, so Argent does not store it.
- A "Most Frequent Re-renders" table. A report with no hot commit contains the table only when a component meets the conditions below. A report with hot commits contains the table only when a component in it is not in the Top Components table. The table lists up to 5 app components, sorted by render time per second. Other components that meet the conditions are named in one line. In a report with hot commits, that line leaves out components already in the Top Components table. A component must re-render in 10 or more commits and use 1 ms or more of render time per second. A row shows what re-rendered. It does not show a problem. React Native components, list internals, animation wrappers, providers and development components are not in the table. When Argent cannot index the source in `project_root`, the table can also contain library components, and the text above the table says so.
- In the Top Components table, `Renders` shows two counts: the re-renders in the stored commits and the re-renders in all commits. An example is `6 / 50`.

When a session has no hot commits, the other modes of `profiler-commit-query` return a message that tells the agent to use `render_counts`.

While a profiler that `react-profiler-start` or `native-profiler-start` started records on a device, interaction tools on that device return no automatic screenshot or element tree. The tool-server sets `profiling: true` on the tool-call response, and the MCP server returns a note in place of the capture. An explicit `describe` call returns its tree and no note. Call `screenshot` or `describe` to see the screen. Through the MCP server, an interaction tool still waits until the screen stops changing before it returns, so a `screenshot` or `describe` called next shows the screen after the interaction. The skip ends when the profiler stops, when the 10-minute recording cap ends the capture, when the app reloads its JavaScript during a React profile, or when the profiler session ends. On an Android emulator or device, Argent also sets the simulator-server of the device to on-demand screenshots while a profiler records. On an emulator, a `screenshot` then takes one frame in about 100 ms. On a physical device, a `screenshot` takes about 150 ms to 200 ms. It starts the screen capture for a short time. Interaction tools do not start the screen capture. When the last profiler on the device stops, Argent sets the simulator-server back to the default mode. An older simulator-server ignores the setting and keeps the default mode.

On a shared Metro, `react-profiler-start` may ask for Metro's `logicalDeviceId` to select an iOS or Android target. Interaction tools still take the device ID. Argent matches a recording that uses a `logicalDeviceId` to a device in three steps.

1. The app writes a marker line to the device log.
2. Argent reads the logs of the connected Android devices and the booted iOS simulators.
3. The device whose log contains the marker is the device of the React profile.

When Argent finds no device, interaction tools on the device keep the automatic screenshot and element tree. `react-profiler-start` then returns a note. Argent cannot read the log of a physical iPhone or of a device from a provider.

For a Mac app, use the [Mac app ID](#react-profiler-on-a-mac-app) even when several devices share Metro.

One React profiler run at a time can record in an app. `react-profiler-status` returns one of these `session_status` values:

| Value              | Meaning                                                                                               |
| ------------------ | ----------------------------------------------------------------------------------------------------- |
| `active`           | A run that this tool-server started records, or `react-profiler-stop` collects the run                |
| `saved`            | No run records. `saved_session` names the files of the last run, or of a session from `profiler-load` |
| `lost`             | Argent did not save the last run of this tool-server. `lost_run.cause` gives the reason               |
| `taken_over`       | Another session records, or another session replaced the run of this tool-server                      |
| `not_started`      | No run records, and this tool-server has no run on record for the device                              |
| `no_react_runtime` | Argent cannot read the React runtime of the app                                                       |

The `lost_run.cause` values are `js_reload`, `cdp_disconnected`, `session_torn_down`, `taken_over`, `stop_failed` and `ended_in_app`. After `ended_in_app`, the data stays in the app. Call `react-profiler-stop` to collect the data. A `react-profiler-start` discards the data.

The tool-server keeps this record in memory only. The shutdown of the tool-server ends the run in the app first. `react-profiler-status` then returns `not_started`. The idle shutdown, SIGTERM, an update and an uncaught exception start this shutdown. The tool-server waits a short time for the app to answer. If the app does not answer, or if the shutdown does not run, the run continues in the app. The new tool-server then shows the run as `taken_over`.

Examples of an exit without the shutdown:

- A `kill -9`, or a native abort such as an out-of-memory kill.
- A SIGHUP. Closing the terminal of a foreground `argent server start` sends a SIGHUP.
- `argent server stop` or an update on Windows. On Windows, SIGTERM ends the process immediately.

A run is stale when its heartbeat is older than 5 minutes, also while you use the app during a long recording. `react-profiler-status`, `react-profiler-renders` and `react-profiler-fiber-tree` refresh the heartbeat of a run that their tool-server records. They do not refresh the heartbeat of a session that replaced this run.

For an `active` run, `react-profiler-status` returns `stale` and `heartbeat_age_seconds`. It reads these values before it refreshes the heartbeat. Only the first call after the heartbeat goes stale returns `stale: true`.

`react-profiler-start` handles a run that records:

- A run that this tool-server records: `react-profiler-start` returns `already_running` with `mine: true`, `stale` and `heartbeat_age_seconds`. The value of `mine` identifies the tool-server, not the agent. The run can belong to another agent on the same tool-server. Call `react-profiler-stop` to collect your run. If `stale` is `true` and you did not start the run, ask the user before you pass `force: true`.
- A fresh run of another session: `react-profiler-start` returns `already_running` with `mine: false`. Ask the user before you pass `force: true`.
- A stale run of another tool-server, a run without an owner record, or a lost run of this tool-server: `react-profiler-start` stops the run and starts a new one. It does the same for any run when you pass `force: true`. The result has `took_over` with the replaced session and the reason.

When another session replaced the run, `react-profiler-stop` fails with `REACT_PROFILER_SESSION_TAKEN_OVER`, also after that session stopped. It does not stop the other recording. If profiling stopped outside Argent and no session replaced the run, `react-profiler-stop` collects the data of the run.

On React Native 0.84 and older, Metro allows one debugger for each app. Any connection from a second tool-server, also a read-only `react-profiler-status`, disconnects the first tool-server. This happens before the second agent can ask the user. Argent records the run of the first tool-server as `cdp_disconnected`, and its `react-profiler-stop` fails with `REACT_PROFILER_NO_ACTIVE_SESSION`, not `REACT_PROFILER_SESSION_TAKEN_OVER`. On 0.85 and newer, Metro disconnects the earlier debugger only for a page without the `supportsMultipleDebuggers` capability.

While `react-profiler-stop` collects a run, wait for its result:

- `react-profiler-status` returns `active`.
- `react-profiler-start` returns `already_running` with `mine: true`, also when you pass `force: true`.
- A second `react-profiler-stop` fails with `REACT_PROFILER_STOP_IN_PROGRESS`.

### iOS launch analysis

| `duration_seconds` | `profile` only. Recording length from 5 to 60 seconds. Default `8`.                                                               |

#### Prerequisites

- A Mac with Xcode. For an iPhone, connect it by USB cable and follow the [physical device requirements](/docs/features/physical-ios-devices#requirements).
- A Release build installed on the selected device. Build and install it again after code changes; the tool does not build or install the app.
- For simulator use, boot the simulator and set `allow_simulator: true`.

#### Measure

Use `mode: "measure"` to establish a baseline or compare launch times after a change. Argent's UI test runner collects five launches with `XCTApplicationLaunchMetric`. The metric includes the first frame and any extended launch tasks registered by the app.

The result includes:

- `averageMs`, `medianMs` and `samplesMs`: launch times in milliseconds.
- `samplesCollected` and `samplesExpected`: how many measurements XCTest returned out of the five requested.
- `resultPath`, `metricsPath` and `logPath`: the XCTest result bundle, exported metrics and runner log.
- `warning`: notes about missing samples or simulator timings, or `null`.

#### Profile

Use `mode: "profile"` to find which phases and functions contribute to startup. Argent records one launch with the Instruments App Launch template and collects CPU samples up to the first frame.

The result includes:

- `launchMs`: on an iPhone, launch time through the first frame, excluding the Process Creation phase because it includes profiler attachment time. On a simulator, this is `null`; `simulatorLaunchEstimateMs` gives a rough estimate instead.
- `phases` and `firstFrameEndMs`: lifecycle phases and the end of the first frame, in milliseconds from the start of the trace. On a simulator, `phases` is empty.
- `tracePath` and `exports`: the Instruments trace and exported tables.
- `profilerSession`: the CPU session, including its `cpuXml` path and suggested `next` tool calls.
- `warning` and optional `exportErrors`: notes about the recording and unavailable exports.

If the trace has no first frame of the app, the tool fails with `LAUNCH_ANALYSIS_NO_FIRST_FRAME`. This occurs when the app stops before its first frame, or when the launch takes longer than `duration_seconds`.

Load the CPU session with `profiler-load` in `load_native` mode, then use `profiler-stack-query` to inspect functions and threads. The trace also opens in Instruments. See [iOS launch performance](/docs/features/ios-launch-performance).

## SDK-only tools

Argent hides these tools from MCP, so the agent does not see them. Call them with the [Argent SDK](./node-client.mdx), `argent run <name>`, or a `tool:` step in an e2e test. The SDK exports the `UiTree`, `ForegroundApp` and `FillResult` result types.

| Tool                                     | Description                                                              | Tool for the agent                               |
| ---------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------ |
| `terminate-app`                          | Stop an app without relaunching it                                       | `restart-app`                                    |
| `ui-tree`                                | Get the raw accessibility tree as nested JSON, iOS simulator and Android | `describe`                                       |
| `foreground-app`                         | Get the app in front, iOS simulator and Android                          | None                                             |
| `fill`                                   | Set the text of the focused text field                                   | `keyboard`                                       |
| `native-devtools-status`                 | Check whether native devtools are connected and injection is prepared    | Any other `native-*` tool                        |
| `native-describe-screen`                 | Read the app's native accessibility screen description                   | `describe`                                       |
| `native-user-interactable-view-at-point` | Inspect the deepest view at a point that would receive touch input       | `native-view-at-point` with `hitTest: true`      |
| `chromium-storage`                       | Read and write `localStorage` and `sessionStorage` of the active page    | `debugger-evaluate`                              |
| `react-profiler-cpu-summary`             | Return the top Hermes CPU hotspots by self-time                          | `profiler-cpu-query`, mode `top_functions`       |
| `react-profiler-component-source`        | Find a component's source file, line, and memoization status             | `react-profiler-analyze`                         |
| `react-profiler-renders`                 | Count mounted instances of each component in the live fiber tree         | `profiler-commit-query`, mode `render_counts`    |
| `e2e-read-prerequisite`                  | Read the execution prerequisite of an e2e test without running it        | `e2e-execute` without `prerequisiteAcknowledged` |
| `gather-workspace-data`                  | Fetch a structured snapshot of the app project's workspace               | None                                             |

Some agent tools do not always give the same result as the hidden tool:

- `restart-app` always relaunches the app. No agent tool leaves an app stopped. When the app is not installed, `restart-app` fails and `terminate-app` succeeds.
- `describe` returns pruned text with one line for each element, not the raw tree. On an iOS simulator, the text does not show which element contains which. `describe` does not give the `hidden`, `covered`, `alertVisible`, `keyboardVisible` or `foregroundApp` fields.
- `keyboard` types at the cursor and keeps the text that the field holds. `fill` replaces that text. With no focused field, `keyboard` drops the text and succeeds, and `fill` fails with `FILL_NO_FOCUSED_FIELD`. `fill` reads the field back, except on a physical iPhone. `keyboard` does not.
- `native-describe-screen`, `native-find-views`, `native-full-hierarchy`, `native-view-at-point`, `native-user-interactable-view-at-point` and, on iOS after `network-capture-start`, `native-network-logs` return the same `message` as `native-devtools-status` when native devtools are not connected. Their `status` names the remedy, where `native-devtools-status` gives `state`. They fail instead for an Apple system app and for an app that a device provider did not lend. `native-profiler-*` do not use native devtools.
- `describe` shows the disabled and selected states and the VoiceOver hint on an iOS simulator. `describe` does not show the frames in points, the view class or some traits, such as `toggleButton`. `native-describe-screen` returns them.
- `chromium-storage` with no key returns every entry. Through `debugger-evaluate`, a bare `localStorage` returns `{}`, so use `Object.fromEntries(Object.entries(localStorage))`.
- `profiler-cpu-query` measures each CPU sample with its own interval and does not list idle time as a function. Thus its times can be different from the times of `react-profiler-cpu-summary`. `react-profiler-cpu-summary` lists anonymous functions as `(anonymous)`. `profiler-cpu-query` counts them as idle.
- `react-profiler-analyze` gives the file and the line of the components in its table that it finds in the project. A library component has no file, and a component that is only in a commit cascade has no file. The report shows the source of the five components with the highest total render time. It can show fewer than five, because it needs the file of each component. For other components, the agent searches the source files. When several files define a name, the report selects one file for the platform of the recording and names up to three other files. The report can select the wrong file for a name that many components share, for example `Content`. The report marks a component that React DevTools records as `Memo(...)` with `[React.memo]`. It does not give `hasUseCallback` or `hasUseMemo`.
- `react-profiler-component-source` fails when `project_root` is not on the computer of the tool-server. `react-profiler-analyze` returns the report with a `warning`. When no component in the report table is in `project_root`, the `warning` says so. This can mean that all components in the table are library components, or that `project_root` is wrong. When `project_root` holds no components, `react-profiler-analyze` uses the project root that Metro reports, and the `warning` says so.
- `react-profiler-renders` reads only the top 30 levels of the React fiber tree and counts the mounted components, not the re-renders. For render counts, use `profiler-commit-query` with `mode: "render_counts"` after a profiling session.
- `e2e-execute` without `prerequisiteAcknowledged` returns the execution prerequisite and runs no step only when the e2e test has a prerequisite. When the e2e test has no prerequisite, `e2e-execute` runs the e2e test.

On Chromium, `fill` fails with `FILL_UNSUPPORTED_FIELD` and changes nothing for:

- text longer than the `maxlength` of the field
- text that a number input does not hold as a number
- whitespace around an address in an email input
- focus in a cross-origin frame, a closed shadow root or an `<embed>`

When a Chromium page does not answer for 10 seconds, for example while it shows a JavaScript dialog, `fill` fails with `FILL_NOT_VERIFIED`. If the page does not answer before the edit, `fill` changes nothing.

`terminate-app` works on iOS and tvOS simulators, Android emulators and devices, and Vega Virtual Devices. On an iOS simulator it succeeds with `terminated: false` when the app is not running or not installed. Android and Vega always report `terminated: true`. Physical iPhones and Mac apps are not supported yet.

In `ui-tree`, fields a platform cannot report yet are listed in `unsupportedFields`. A node is `hidden` when no part of it is on screen inside its ancestors. On iOS, while a system alert shows, `roots` holds the system app first and the app it covers second. On Android, `roots` holds one root per window, topmost first. A system dialog, such as a runtime permission prompt or a crash dialog, sets `alertVisible`, and every node of the app it covers is `covered`. When Android hides the app's window under the dialog, `foregroundApp` is unset. `foreground-app` returns the same `foregroundApp` and `alertVisible` without reading the tree, plus the app's `name` on iOS.

## Relative paths

The client resolves a relative path in a file input of a tool against its working directory, for example `appPath` of `reinstall-app`. `GET /tools` lists the file inputs of a tool in `fileInputs`. The MCP server refuses such a path in `project_root` or `e2e_test_path`.

On Windows, a path such as `\team\$archive` starts at the root of the client's current drive. For these MCP inputs, include the drive letter, for example `D:\team\$archive`.
