This page documents client services: the exchange between the argent client and the tool-server. Through this exchange, the tool-server asks the client for project files during a flow run. The tool-server also gives the client each new snapshot baseline. The argent CLI and the MCP adapter are clients. The runner stays on the tool-server. The project stays on the client. For the user-facing behavior, see [Flows over a link](/docs/reference/flow-yaml#flows-over-a-link).

The exchange has four messages:

| Message       | Direction             | Carrier                                            |
| ------------- | --------------------- | -------------------------------------------------- |
| Advertisement | Tool-server to client | The `clientServices` field of a `GET /tools` entry |
| Opt-in        | Client to tool-server | The `client_services` parameter of the call        |
| Request       | Tool-server to client | A `client-request` line on the NDJSON stream       |
| Answer        | Client to tool-server | `POST /invocations/<invocation>/client-responses`  |

Only the `flow-execute` tool advertises client services. Each side uses an op only when the other side lists the op.

## Advertisement: `clientServices` in `GET /tools`

The `GET /tools` listing holds one entry per tool. The entry of a tool that can use client services carries a `clientServices` field:

```json
{
  "name": "flow-execute",
  "clientServices": { "ops": ["resolve-file", "read-file", "write-file"] }
}
```

| Field | Value                                         |
| ----- | --------------------------------------------- |
| `ops` | The ops the tool-server can send requests for |

An entry without the field belongs to a tool that does not use client services, or to a tool-server without client services.

## Opt-in: the `client_services` parameter

The client adds a `client_services` parameter to the arguments of a call when all three conditions hold:

1. A link routes the call to a tool-server (`argent link` or `ARGENT_TOOLS_URL`). A link to a tool-server on the same computer counts.
2. The `GET /tools` entry of the tool carries `clientServices`.
3. The arguments carry a string `project_root`.

```json
{
  "name": "withrun",
  "project_root": "/work/proj",
  "device": "chromium-cdp-9471",
  "client_services": {
    "ops": ["resolve-file", "read-file"],
    "roots": ["/work/proj"]
  }
}
```

| Field   | Value                                                                                                                                                                                                                                                                                                                                             |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ops`   | The ops the client serves: the ops that the tool-server advertised and that the client implements. The client offers `write-file` only when the arguments set `updateBaselines: true`                                                                                                                                                             |
| `roots` | Absolute client directories, by their real location: `project_root`, its `.argent/flows` directory, the directory of `flow_path` when the arguments carry one, and the directory of the real file behind the root flow when that file is a YAML file. A root inside another root is not sent. A `name` that is not a valid flow name adds no root |

The client also sends `Accept: application/x-ndjson`, because the requests travel on the NDJSON stream of the call. The tool-server answers 400 with `HTTP_ZOD_VALIDATION_FAILED` to a call that carries `client_services` without that header, or with a malformed `client_services`. A proxy that rewrites `Accept` therefore gets this 400. The tool-server takes `client_services` off the arguments before it validates them, so the input schema of `flow-execute` does not list the parameter. The tool-server sends a request for an op only when the client listed the op in `ops`.

Each request line must reach the client at once, because the run waits for the answer. For this reason, the client sends `Accept-Encoding: identity` with the call, and the tool-server sends the stream with `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no`. Each reverse proxy between the client and the tool-server must:

- pass the stream through as the tool-server writes it, without compression or buffering
- forward `POST /invocations/<invocation>/client-responses` while the stream of the call is open
- accept a request body of up to 48 MB on `POST /invocations/<invocation>/client-responses`, because an answer to `read-file` carries the baseline

`X-Accel-Buffering: no` turns off buffering only in the nginx that receives the header. nginx does not forward the header. When an nginx that terminates TLS sits in front of a second nginx, set `proxy_buffering off` in each nginx. A proxy that holds the stream keeps the request line from the client. The tool-server then reports a timeout after 30 s. A flow without `run:` and `snapshot:` steps sends no request, so such a proxy does not stop it.

nginx accepts a request body of up to 1 MB by default. A full-screen baseline is often larger. Set `client_max_body_size 48m` in each nginx. When a proxy refuses an answer with an error status, the client sends a refusal for the same request. The step then reports `error` at once. See [Timeouts and failures](#timeouts-and-failures).

When one condition does not hold, the client sends no `client_services`. The client also sends no `client_services` when no root exists on the client, or when the advertised `ops` hold no op that the client serves. The tool-server then keeps the behavior of a call without client services.

## Request: the `client-request` line

The tool-server writes one line on the NDJSON stream of the call for each request:

```json
{
  "event": "client-request",
  "invocation": "4f4a1c1e-2b0e-4b7f-9d2a-8c3e0b1f6a21",
  "id": "9b2d7c0a-6f1e-4d3b-a5c8-0e7f2b4d9a13",
  "op": "resolve-file",
  "args": { "anchorDir": "/work/proj/.argent/flows", "target": "frag.yaml", "kind": "flow" }
}
```

| Field        | Value                                                 |
| ------------ | ----------------------------------------------------- |
| `event`      | `client-request`                                      |
| `invocation` | The id of the tool call. It names the answer endpoint |
| `id`         | The id of the request. The answer carries the same id |
| `op`         | One of the ops the client listed                      |
| `args`       | The arguments of the op. See [Ops](#ops)              |

The line sits between the step progress lines. When the flow has a `run:` or `snapshot:` step, the first request comes before the first step and asks for the root flow itself. For a flow with an `echo` step and a `run:` step, the lines come in this order:

```text
{"event":"client-request","invocation":"...","id":"...","op":"resolve-file","args":{"target":"withrun.yaml",...}}
{"event":"progress","data":{"kind":"echo","status":"pass",...}}
{"event":"client-request","invocation":"...","id":"...","op":"resolve-file","args":{"target":"frag.yaml",...}}
{"event":"progress","data":{"kind":"run","status":"pass",...}}
{"event":"result","data":{...}}
```

A client that sent no `client_services` never receives the line.

## Answer: `POST /invocations/<invocation>/client-responses`

The client answers each request with a separate HTTP request. `<invocation>` is the `invocation` of the request line.

```text
POST /invocations/<invocation>/client-responses
Host: 127.0.0.1:4731
Authorization: Bearer <token>
Content-Type: application/json
```

The body has one of two shapes. When the client serves the request, the body carries the answer fields of the op:

```json
{ "id": "9b2d7c0a-6f1e-4d3b-a5c8-0e7f2b4d9a13", "ok": true, "canonical": "...", "exists": true }
```

When the client refuses the request, the body carries the reason:

```json
{ "id": "9b2d7c0a-6f1e-4d3b-a5c8-0e7f2b4d9a13", "ok": false, "error": "<text>" }
```

| Status | Body                    | Meaning                                                 |
| ------ | ----------------------- | ------------------------------------------------------- |
| 200    | `{ "accepted": true }`  | The tool-server delivered the answer to the waiting run |
| 404    | `{ "error": "<text>" }` | Unknown invocation, or unknown or expired request id    |
| 409    | `{ "error": "<text>" }` | The request already has an answer                       |
| 413    | `{ "error": "<text>" }` | `content` decodes to more than 32 MiB                   |

The endpoint sits behind the same bearer-token check and Host check as `/tools/<name>`. The JSON body limit of 48 MB applies.

## Ops

### `resolve-file`

The tool-server sends `resolve-file` for each `run:` step. The client resolves the target on its own disk and returns the file. When the flow has a `run:` or `snapshot:` step, the tool-server also sends `resolve-file` for the root flow itself before the first step, to learn the real location of the file. The `run:` targets of the root flow and the snapshot baselines resolve beside that location, as they do on one computer. A refusal of that request fails the run before the first step.

Request `args`:

| Field       | Value                                                                           |
| ----------- | ------------------------------------------------------------------------------- |
| `anchorDir` | Absolute client path of the directory of the flow file that contains the step   |
| `target`    | The `run:` target as written, for example `frag.yaml` or `../shared/login.yaml` |
| `kind`      | `flow`. The protocol also defines `script`, which the client does not serve yet |

Answer:

| Field       | Value                                                                                    |
| ----------- | ---------------------------------------------------------------------------------------- |
| `canonical` | The realpath of `anchorDir` + `/` + `target` on the client                               |
| `spelling`  | How the directory on the client lists the basename of `target`. See the next table       |
| `exists`    | `true` when the client can stat `canonical` as a file                                    |
| `size`      | The size of the file in bytes. Present when `exists` is `true`                           |
| `mtimeMs`   | The modification time of the file in epoch milliseconds. Present when `exists` is `true` |
| `content`   | The file as base64. Present when `exists` is `true` and `kind` is `flow`                 |

`spelling` has one of three shapes:

| Shape                                                                   | Meaning                                                                                                                                          |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `{ "state": "listed" }`                                                 | The directory lists the basename as written. The client also answers `listed` when it cannot read the directory                                  |
| `{ "state": "case_folded", "actual": "<name>", "addressable": <bool> }` | The directory lists the name with a different case. `actual` is the listed name. `addressable` is `true` when `actual` is a valid flow file name |
| `{ "state": "absent" }`                                                 | The directory lists no name that matches, in any case                                                                                            |

The runner applies the same rules to the answer as to a file on its own disk: the cycle guard, the depth limit and the refusal of a `case_folded` spelling. The runner never opens `canonical`. It uses the path as a key and in messages.

### `read-file`

The tool-server sends `read-file` at each `snapshot:` step that compares, to get the baseline. The tool-server builds the path of the baseline beside the real file of the root flow on the client: `<dir>/__baselines__/<flow>/<key>.png`. `<flow>` is the name of that real file without `.yaml`. When that name is not a valid flow name, `<flow>` is the name of the flow. `<key>` is the baseline key of the snapshot. See [Snapshots](/docs/reference/flow-yaml#snapshots). A `snapshot:` step in a fragment uses the baselines of the root flow.

Request `args`:

| Field  | Value                                     |
| ------ | ----------------------------------------- |
| `path` | Absolute client path of the baseline file |

Answer:

| Field     | Value                                                                                    |
| --------- | ---------------------------------------------------------------------------------------- |
| `exists`  | `true` when the client can stat `path` as a file. `false` when no file is at `path`      |
| `size`    | The size of the file in bytes. Present when `exists` is `true`                           |
| `mtimeMs` | The modification time of the file in epoch milliseconds. Present when `exists` is `true` |
| `content` | The file as base64. Present when `exists` is `true`                                      |

An answer with `exists: false` is not a refusal. The step then fails with the reason of a missing baseline, as in a run without a link. The tool-server compares the images on its own computer. The tool-server returns the baseline, current and diff images of the step as artifacts, as in a run without a link.

### `write-file`

The tool-server sends `write-file` at each `snapshot:` step when the call sets `updateBaselines`. The request carries the new baseline. The tool-server sends no `read-file` for this step. The answer tells whether a baseline was at the path, so the step reason says `baseline written` or `baseline updated`.

Request `args`:

| Field     | Value                                                                                         |
| --------- | --------------------------------------------------------------------------------------------- |
| `path`    | Absolute client path of the baseline file, of the form `<dir>/__baselines__/<flow>/<key>.png` |
| `content` | The new baseline as base64                                                                    |

The content travels in the request line on the NDJSON stream, not in an answer. The client creates `__baselines__/<flow>/` when the directory does not exist. See [Client policy](#client-policy) for the paths that the client writes.

Answer:

| Field      | Value                                               |
| ---------- | --------------------------------------------------- |
| `written`  | The path that the client wrote                      |
| `replaced` | `true` when a file was at the path before the write |

### Reserved op names

The protocol also defines the op name `run-script`. No client serves it. The client lists only the ops it serves, so the tool-server never sends a request for it.

## Timeouts and failures

The tool-server waits 30 s for each answer.

| Event                                    | Effect on the run                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No answer within 30 s                    | Before the first step, the call fails with `FLOW_CLIENT_NOT_ANSWERING` and the error kind `timeout`. At a `run:` or `snapshot:` step, the step reports `error` and the later steps report `skip`. Every later request of the same call then fails at once                                                                                                                 |
| An answer with `ok: false`               | The step reports `error`. At a `run:` step, the reason starts with `could not load fragment "<target>":` and quotes the `error` text of the client. At a `snapshot:` step, the reason names the op and the path, and quotes the `error` text of the client. The later steps report `skip`. A refusal of the request for the root flow fails the run before the first step |
| An answer gets an error status           | Unless the status is 404 or 409, the client sends a refusal for the same request. The `error` text names the status. For a 413, the text also says that a proxy limits the size of a request body. The step reports `error`, as for an answer with `ok: false`. When the refusal also fails, the tool-server reports a timeout after 30 s                                 |
| The HTTP response of the call closes     | The tool-server rejects every pending request and aborts the run. A `run:` or `snapshot:` step that waits for an answer reports `skip` with the reason `run aborted`                                                                                                                                                                                                      |
| The client closes before the call starts | The tool-server does not run the call                                                                                                                                                                                                                                                                                                                                     |

The reason of a timeout names the op, and the target or the path of the request. It also names the usual causes:

- a paused or sleeping client
- a proxy that buffers the stream
- a proxy that does not forward the answer

## Client policy

The client enforces these rules. The tool-server checks only the shape of each answer and the 32 MiB cap. The tool-server already holds the bearer token, so the rules protect the files of the project, not the token.

1. The client reads and writes nothing outside the roots it sent. Before it reads a file, writes a file or lists a directory, it checks the real location against the roots. It refuses a symlink that points outside a root. It refuses a target that ends outside a root, for example through `..`.
2. The client refuses a path when it cannot find the real location of the path. For example, the real location can be longer than the path limit of the system, or a link on the path can be unreadable.
3. The refusal of a path outside the roots does not tell where the path leads or whether it exists.
4. `resolve-file` serves `.yaml` names only. The client refuses a `.yaml` name that links to a file that is not a YAML file (`.yaml` or `.yml`).
5. `read-file` and `write-file` take only an absolute path of the form `<dir>/__baselines__/<flow>/<key>.png`, in normal form: no `..`, no `.` and no double `/`. `<flow>` holds only letters, digits, `_` and `-`. The client refuses every other path.
6. The client refuses a `.png` name that links to a file that is not a PNG file (`.png`).
7. The client offers `write-file` only for a call that sets `updateBaselines: true`. A run that compares baselines cannot change them.
8. Before `write-file` creates `__baselines__/<flow>/`, the client checks the real location of that directory against the roots. Before it writes the file, the client checks the real location of the file again. The client follows a link to a file that does not exist to check where it leads, and then refuses it.
9. The client refuses a file above 32 MiB, for a read and for a write. The error names the cap.
10. The client refuses an op that it did not list in `ops`, and a `kind` it does not know.
11. The client answers a directory with the `EISDIR` error and an unreadable file with the error of the read, for example `EACCES`. It answers a target or a path in a directory that does not exist as a missing file.
12. By default, the client prints nothing for a request it serves. When the environment of the client has `ARGENT_CLIENT_SERVICES_LOG=1`, the client prints one line per served request to stderr. The line holds the op and the path, for example `[client-services] write-file <path>`. The client never prints the content. For `read-file` and `write-file`, the client prints the line only after the read or the write succeeds.

## A client or tool-server without client services

| Client                  | Tool-server             | Result for a `run:` step over a link                                                                                                                                                                                                  |
| ----------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| With client services    | With client services    | The tool-server reads the fragment through client services                                                                                                                                                                            |
| With client services    | Without client services | The listing has no `clientServices`. The client sends nothing. The tool-server rejects the flow before the first step                                                                                                                 |
| Without client services | With client services    | The call has no `client_services`. The tool-server rejects the flow before the first step and adds: "This tool-server serves run: steps for a client that sends client services. Update the argent CLI or MCP adapter on the client." |
| Without client services | Without client services | The tool-server rejects the flow before the first step                                                                                                                                                                                |

A `snapshot:` step that compares needs `resolve-file` and `read-file` on both sides. A `snapshot:` step that updates baselines needs `resolve-file` and `write-file`. A client or tool-server without client services has none of these ops.

| Client                             | Tool-server                          | Result for a `snapshot:` step over a link                                                                                                                                                                                                           |
| ---------------------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| With `read-file` and `write-file`  | With `read-file` and `write-file`    | The client serves the baseline and writes each new baseline through client services                                                                                                                                                                 |
| Without the op that the step needs | With `read-file` and `write-file`    | The tool-server rejects the flow before the first step and adds: "This tool-server serves snapshot: steps for a client that offers the resolve-file, read-file and write-file client services. Update the argent CLI or MCP adapter on the client." |
| Any                                | Without `read-file` and `write-file` | The tool-server rejects the flow before the first step                                                                                                                                                                                              |

`script:` steps, and `tool:` steps that take a file or record a flow, need a run without a link in every row. In the root flow, the tool-server rejects them before the first step and lists each one. In a fragment that the client serves, the tool-server rejects them when the `run:` step loads the fragment: that step reports `error` with the same list, and no step of the fragment runs. The tool-server rejects a `snapshot:` step that the client cannot serve at the same points.
