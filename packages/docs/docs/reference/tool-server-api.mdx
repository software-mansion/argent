This page documents client services: the exchange between the argent client and the tool-server. Through this exchange, the tool-server asks the client for project files during a flow run. The tool-server also gives the client each new snapshot baseline. The argent CLI and the MCP adapter are clients. The runner stays on the tool-server. The project stays on the client. For the user-facing behavior, see [Flows over a link](/docs/reference/flow-yaml#flows-over-a-link).

The exchange has four messages:

| Message       | Direction             | Carrier                                            |
| ------------- | --------------------- | -------------------------------------------------- |
| Advertisement | Tool-server to client | The `clientServices` field of a `GET /tools` entry |
| Opt-in        | Client to tool-server | The `client_services` parameter of the call        |
| Request       | Tool-server to client | A `client-request` line on the NDJSON stream       |
| Answer        | Client to tool-server | `POST /invocations/<invocation>/client-responses`  |

Only the `flow-execute` tool advertises client services. Each side uses an op only when the other side lists the op.

## Advertisement: `clientServices` in `GET /tools`

The `GET /tools` listing holds one entry per tool. The entry of a tool that can use client services carries a `clientServices` field:

```json
{
  "name": "flow-execute",
  "clientServices": { "ops": ["resolve-file", "read-file", "write-file"] }
}
```

| Field | Value                                         |
| ----- | --------------------------------------------- |
| `ops` | The ops the tool-server can send requests for |

An entry without the field belongs to a tool that does not use client services, or to a tool-server without client services.

## Opt-in: the `client_services` parameter

The client adds a `client_services` parameter to the arguments of a call when all these conditions hold:

1. A link routes the call to a tool-server (`argent link` or `ARGENT_TOOLS_URL`). A link to a tool-server on the same computer counts.
2. The `GET /tools` entry of the tool carries `clientServices`, and its `ops` hold an op that the client serves.
3. `project_root` is an absolute path without a `..` segment.
4. The arguments carry exactly one flow source: a `name` that is a valid flow name, or a `flow_path` that is an absolute path without a `..` segment to a valid flow file name.
5. The root flow file is on the client, under the roots, and has at least one `run:` step. A `snapshot:` step also counts when `ops` hold `read-file` or `write-file`.

```json
{
  "name": "withrun",
  "project_root": "/work/proj",
  "device": "chromium-cdp-9471",
  "client_services": {
    "ops": ["resolve-file", "read-file"],
    "roots": ["/work/proj"]
  }
}
```

| Field   | Value                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ops`   | The ops the client serves: the ops that the tool-server advertised and that the client implements. The client offers `write-file` only when the arguments set `updateBaselines: true`                                                                                                                                                                                                                      |
| `roots` | Absolute client directories, by their real location: `project_root`, its `.argent/flows` directory, the directory of the root flow file, and the directory of the real file behind the root flow when that real file is a YAML file (`.yaml` or `.yml`). When the root flow file or that real file is under `<P>/.argent/flows/`, the project `<P>` is also a root. A root inside another root is not sent |

The client also sends `Accept: application/x-ndjson`, because the requests travel on the NDJSON stream of the call. The tool-server answers 400 with `HTTP_ZOD_VALIDATION_FAILED` and the error kind `validation` to a call that carries `client_services` without that header, or with a malformed `client_services`. A proxy that rewrites `Accept` therefore gets this 400 for a flow with a `run:` or `snapshot:` step. A directory run of `argent flow run` reports that flow as rejected and continues with the next flow. The tool-server takes `client_services` off the arguments before it validates them, so the input schema of `flow-execute` does not list the parameter. The tool-server sends a request for an op only when the client listed the op in `ops`.

Each request line must reach the client at once, because the run waits for the answer. For this reason, the client sends `Accept-Encoding: identity` with the call, and the tool-server sends the stream with `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no`. Each reverse proxy between the client and the tool-server must:

- pass the stream through as the tool-server writes it, without compression or buffering
- forward `POST /invocations/<invocation>/client-responses` while the stream of the call is open
- accept a request body of up to 48 MB on `POST /invocations/<invocation>/client-responses`, because an answer to `read-file` carries the baseline

`X-Accel-Buffering: no` turns off buffering only in the nginx that receives the header. nginx does not forward the header. When an nginx that terminates TLS sits in front of a second nginx, set `proxy_buffering off` in each nginx. A proxy that holds the stream keeps the request line from the client. The tool-server then reports a timeout after 30 s. A flow without `run:` and `snapshot:` steps carries no `client_services` and sends no request, so such a proxy does not stop it.

nginx accepts a request body of up to 1 MB by default. A full-screen baseline is often larger. Set `client_max_body_size 48m` in each nginx. When a proxy refuses an answer with the status 413, the client sends a refusal for the same request. The step that waits for the answer then reports `error` at once. A refusal of the request for the root flow fails the run before the first step. See [Timeouts and failures](#timeouts-and-failures).

When one condition does not hold, the client sends no `client_services`, and the call is not a stream for client services. The tool-server then keeps the behavior of a call without client services.

## Request: the `client-request` line

The tool-server writes one line on the NDJSON stream of the call for each request:

```json
{
  "event": "client-request",
  "invocation": "4f4a1c1e-2b0e-4b7f-9d2a-8c3e0b1f6a21",
  "id": "9b2d7c0a-6f1e-4d3b-a5c8-0e7f2b4d9a13",
  "op": "resolve-file",
  "args": { "anchorDir": "/work/proj/.argent/flows", "target": "frag.yaml", "kind": "flow" }
}
```

| Field        | Value                                                 |
| ------------ | ----------------------------------------------------- |
| `event`      | `client-request`                                      |
| `invocation` | The id of the tool call. It names the answer endpoint |
| `id`         | The id of the request. The answer carries the same id |
| `op`         | One of the ops the client listed                      |
| `args`       | The arguments of the op. See [Ops](#ops)              |

The line sits between the step progress lines. When the flow has a `run:` or `snapshot:` step, the first request comes before the first step and asks for the root flow itself. For a flow with an `echo` step and then a `run: frag.yaml` step, called with a `device`, the lines come in this order:

```text
{"event":"client-request","invocation":"...","id":"...","op":"resolve-file","args":{"target":"withrun.yaml",...}}
{"event":"progress","data":{"kind":"echo","status":"pass",...}}
{"event":"client-request","invocation":"...","id":"...","op":"resolve-file","args":{"target":"frag.yaml",...}}
{"event":"progress","data":{"kind":"run","status":"pass",...}}
{"event":"result","data":{...}}
```

The tool-server asks once for each `run:` target in a call, and every later read of that target in the call uses the same answer. Without a `device`, the tool-server reads a leading `run:` chain before the first step to find its launch. Then the request for `frag.yaml` comes before the first progress line.

A client that sent no `client_services` never receives the line.

## Answer: `POST /invocations/<invocation>/client-responses`

The client answers each request with a separate HTTP request. `<invocation>` is the `invocation` of the request line.

```text
POST /invocations/<invocation>/client-responses
Host: 127.0.0.1:4731
Authorization: Bearer <token>
Content-Type: application/json
```

The body has one of two shapes. When the client serves the request, the body carries the answer fields of the op. For `resolve-file`, see [the answer fields](#resolve-file):

```json
{
  "id": "9b2d7c0a-6f1e-4d3b-a5c8-0e7f2b4d9a13",
  "ok": true,
  "canonical": "/work/proj/.argent/flows/frag.yaml",
  "spelling": { "state": "listed" },
  "exists": true,
  "size": 20,
  "mtimeMs": 1791300000000,
  "content": "c3RlcHM6CiAgLSBlY2hvOiBoaQo="
}
```

When the client refuses the request, the body carries the reason:

```json
{ "id": "9b2d7c0a-6f1e-4d3b-a5c8-0e7f2b4d9a13", "ok": false, "error": "<text>" }
```

| Status | Body                    | Meaning                                                 |
| ------ | ----------------------- | ------------------------------------------------------- |
| 200    | `{ "accepted": true }`  | The tool-server delivered the answer to the waiting run |
| 404    | `{ "error": "<text>" }` | Unknown invocation, or unknown or expired request id    |
| 409    | `{ "error": "<text>" }` | The request already has an answer                       |
| 413    | `{ "error": "<text>" }` | `content` decodes to more than 32 MiB                   |

The endpoint sits behind the same bearer-token check and Host check as `/tools/<name>`. The JSON body limit of 48 MB applies.

## Ops

### `resolve-file`

The tool-server sends `resolve-file` once for each `run:` target of a call. The client resolves the target on its own disk and returns the file. When the flow has a `run:` or `snapshot:` step, the tool-server also sends `resolve-file` for the root flow itself before the first step, to learn the real location of the file. The `run:` targets of the root flow and the snapshot baselines resolve beside that location, as they do on one computer. A refusal of that request fails the run before the first step.

Request `args`:

| Field       | Value                                                                           |
| ----------- | ------------------------------------------------------------------------------- |
| `anchorDir` | Absolute client path of the directory of the flow file that contains the step   |
| `target`    | The `run:` target as written, for example `frag.yaml` or `../shared/login.yaml` |
| `kind`      | `flow`. The protocol also defines `script`, which the client does not serve yet |

Answer:

| Field       | Required                                     | Value                                                                              |
| ----------- | -------------------------------------------- | ---------------------------------------------------------------------------------- |
| `canonical` | Yes                                          | The realpath of `anchorDir` + `/` + `target` on the client                         |
| `spelling`  | Yes                                          | How the directory on the client lists the basename of `target`. See the next table |
| `exists`    | Yes                                          | `true` when the client can stat `canonical` as a file                              |
| `content`   | When `exists` is `true` and `kind` is `flow` | The file as base64                                                                 |
| `size`      | No                                           | The size of the file in bytes                                                      |
| `mtimeMs`   | No                                           | The modification time of the file in epoch milliseconds                            |

The tool-server accepts the answer with 200 before the runner reads it. When a required field is missing, the runner fails the request: the step or the run reports that the client answered with an invalid payload.

`spelling` has one of three shapes:

| Shape                                                                   | Meaning                                                                                                                                          |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `{ "state": "listed" }`                                                 | The directory lists the basename as written. The client also answers `listed` when it cannot read the directory                                  |
| `{ "state": "case_folded", "actual": "<name>", "addressable": <bool> }` | The directory lists the name with a different case. `actual` is the listed name. `addressable` is `true` when `actual` is a valid flow file name |
| `{ "state": "absent" }`                                                 | The directory lists no name that matches, in any case                                                                                            |

The runner applies the same rules to the answer as to a file on its own disk: the cycle guard, the depth limit and the refusal of a `case_folded` spelling. The runner never opens `canonical`. It uses the path as a key and in messages.

### `read-file`

The tool-server sends `read-file` at each `snapshot:` step that compares, to get the baseline. The tool-server builds the path of the baseline beside the real file of the root flow on the client: `<dir>/__baselines__/<flow>/<key>.png`. `<flow>` is the name of that real file without `.yaml`. When that name is not a valid flow name, `<flow>` is the name of the flow. `<key>` is the baseline key of the snapshot. See [Snapshots](/docs/reference/flow-yaml#snapshots). A `snapshot:` step in a fragment uses the baselines of the root flow. The client serves only the baselines in this directory.

Request `args`:

| Field  | Value                                     |
| ------ | ----------------------------------------- |
| `path` | Absolute client path of the baseline file |

Answer:

| Field     | Value                                                                                    |
| --------- | ---------------------------------------------------------------------------------------- |
| `exists`  | `true` when the client can stat `path` as a file. `false` when no file is at `path`      |
| `size`    | The size of the file in bytes. Present when `exists` is `true`                           |
| `mtimeMs` | The modification time of the file in epoch milliseconds. Present when `exists` is `true` |
| `content` | The file as base64. Present when `exists` is `true`                                      |

An answer with `exists: false` is not a refusal. The step then fails with the reason of a missing baseline, as in a run without a link. The client also answers `exists: false` when a file stands where a directory of `path` should be, as a run without a link does. The tool-server compares the images on its own computer. The tool-server returns the baseline, current and diff images of the step as artifacts, as in a run without a link.

### `write-file`

The tool-server sends `write-file` at each `snapshot:` step when the call sets `updateBaselines`. The request carries the new baseline. The tool-server sends no `read-file` for this step. The answer tells whether a baseline was at the path, so the step reason says `baseline written` or `baseline updated`. The step reason also gives the client path of the baseline. The step returns no artifact, because the baseline is on the client. A run without a link gives the file name of the baseline in the step reason, and returns the baseline as an artifact.

Request `args`:

| Field     | Value                                                                                         |
| --------- | --------------------------------------------------------------------------------------------- |
| `path`    | Absolute client path of the baseline file, of the form `<dir>/__baselines__/<flow>/<key>.png` |
| `content` | The new baseline as base64                                                                    |

The content travels in the request line on the NDJSON stream, not in an answer. The tool-server does not send a baseline above the 32 MiB cap. The step then reports `error`, and the reason names the cap. The client writes only into the `__baselines__/<flow>/` directory of the root flow. The client creates `__baselines__/` and `__baselines__/<flow>/` beside the real file of the root flow when they do not exist. The client creates no other directory. The client writes the new baseline to a temporary file in the same directory, and then renames that file over the baseline. When the client stops during the write, the old baseline stays complete. The new baseline keeps the mode of the file that it replaces. When the baseline is a link to a file under the roots, the client replaces that file and keeps the link. See [Client policy](#client-policy) for the paths that the client writes.

Answer:

| Field      | Value                                               |
| ---------- | --------------------------------------------------- |
| `written`  | The path that the client wrote                      |
| `replaced` | `true` when a file was at the path before the write |

### Reserved op names

The protocol also defines the op name `run-script`. No client serves it. The client lists only the ops it serves, so the tool-server never sends a request for it.

## Timeouts and failures

The tool-server waits 30 s for each answer. For `read-file` and `write-file`, the 30 s include the time to move the file. The file travels as base64. A file at the 32 MiB cap therefore needs about 12 Mbit/s: from the client to the tool-server for `read-file`, and from the tool-server to the client for `write-file`.

| Event                                              | Effect on the run                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No answer within 30 s                              | Before the first step, the call fails with `FLOW_CLIENT_NOT_ANSWERING` and the error kind `timeout`. At a `run:` or `snapshot:` step, the step reports `error` and the later steps report `skip`. Every later request of the same call then fails at once. The client can still complete a `write-file` that it already received. `argent flow run` exits at the end of the call and stops such a write. The old baseline then stays complete |
| An answer with `ok: false`                         | The step reports `error`. At a `run:` step, the reason starts with `could not load fragment "<target>":` and quotes the `error` text of the client. At a `snapshot:` step, the reason names the op and the path, and quotes the `error` text of the client. The later steps report `skip`. A refusal of the request for the root flow fails the run before the first step                                                                     |
| A proxy refuses an answer with the status 413      | The client sends a refusal for the same request instead. The `error` text names the status. It also says that the proxy must accept a request body of up to 48 MB on the answer route. The effect is the same as for an answer with `ok: false`. When the tool-server does not accept the refusal either, the effect is the same as for an answer that does not reach the tool-server                                                         |
| The HTTP response of the call closes               | The tool-server rejects every pending request and aborts the run. A `run:` or `snapshot:` step that waits for an answer reports `skip` with the reason `run aborted`. Each step that did not run also reports `skip` with the reason `run aborted`. The client can still complete a `write-file` that it already received. `argent flow run` exits at the end of the call and stops such a write. The old baseline then stays complete        |
| The client closes before the call starts           | The tool-server does not run the call                                                                                                                                                                                                                                                                                                                                                                                                         |
| The answer does not reach the tool-server          | The client stops the call at once with `FLOW_CLIENT_NOT_ANSWERING` and the error kind `network`, and closes the response. The tool-server then aborts the run                                                                                                                                                                                                                                                                                 |
| The client cannot read or write a file within 30 s | The client sends no answer, and the tool-server reports the timeout                                                                                                                                                                                                                                                                                                                                                                           |

The reason of a timeout names the op, and the target or the path of the request. It also names the usual causes:

- a paused or sleeping client
- a proxy that buffers the stream
- a proxy that does not forward the answer
- for `read-file` and `write-file`, a connection that is too slow to move the file in 30 s

The answer does not reach the tool-server when the answer request fails, when it gets no reply within 30 s, or when its reply is not one that the tool-server sends. An example is a 502 from a proxy. The replies of the tool-server in the status table above do not stop the call. A 413 from a proxy also does not stop the call, because the client sends a refusal in place of the answer.

## Client policy

The client enforces these rules. The tool-server checks only the shape of each answer and the 32 MiB cap. The tool-server already holds the bearer token, so the rules protect the files of the project, not the token.

1. The client serves only the files that the flows of the call compose: the root flow, each `run:` target that a served file names, resolved beside that file, and the snapshot baselines of the run. The client refuses any other request before it reads the file. The refusal is the same whether the file exists or not.
2. The client reads and writes nothing outside the roots it sent. It resolves a requested path one segment at a time, as the operating system does. Before it looks at a place on the disk, it checks that the place is in a root or on the way to a root. It refuses a symlink that points outside a root. It refuses a target that passes through a place outside the roots, also when the target ends in a root.
3. The refusal of a path outside the roots does not tell where the path leads or whether it exists.
4. `resolve-file` serves `.yaml` names only. The client refuses a `.yaml` name that links to a file that is not a YAML file (`.yaml` or `.yml`).
5. `read-file` and `write-file` take only an absolute path of the form `<dir>/__baselines__/<flow>/<key>.png`, in normal form: no `..`, no `.` and no double `/`. `<flow>` holds only letters, digits, `_` and `-`. The client refuses every other path. The path must also be in the baseline directory of the run: `__baselines__/<flow>/` beside the real file of the root flow, with the `<flow>` that the tool-server uses. The client refuses a baseline of another flow and a `__baselines__` directory in another place. When the root flow is not a YAML file on the client, the client refuses every path.
6. The client refuses a `.png` name that links to a file that is not a PNG file (`.png`).
7. The client offers `write-file` only for a call that sets `updateBaselines: true`. A run that compares baselines cannot change them.
8. Before `write-file` creates `__baselines__/<flow>/`, the client checks the real location of that directory against the roots. Before it writes the file, the client checks the real location of the file again. The client follows a link to a file that does not exist to check where it leads, and then refuses it.
9. The client refuses a file above 32 MiB, for a read and for a write. The error names the cap.
10. The client refuses an op that it did not list in `ops`, and a `kind` it does not know.
11. For a read, the client answers a directory with the `EISDIR` error, and an unreadable file with the error of the read, for example `EACCES`. It answers a target or a path in a directory that does not exist as a missing file.
12. The client answers a loop of symlinks with `ELOOP`. When the client cannot look at a place on the path, it answers with the error of the system, for example `EACCES` for a directory that it cannot search. It answers a file that a path uses as a directory with `ENOTDIR`. `read-file` answers such a path as a missing file instead, as a run without a link does. `write-file` answers a file at `__baselines__/<flow>` with the `EEXIST` error of the directory creation.
13. `write-file` refuses a path where something other than a regular file is, for example a directory or a FIFO.
14. By default, the client prints a line only when it cannot answer a request, or when the tool-server or a proxy does not take the answer. When the environment of the client has `ARGENT_CLIENT_SERVICES_LOG=1`, the client prints one line for each request after it decides the answer: `[client-services] <op> <path>: served`, `: missing`, `: written` or `: refused (<reason>)`. For `resolve-file`, the path is the real path of the file after the client finds that the flows of the call compose the file. Before that point, the path is the target that the tool-server sent. For `read-file` and `write-file`, the path is the path that the tool-server sent. The client never prints the content. Under `argent flow run --json`, each line is a warning object on stderr.

## A client or tool-server without client services

| Client                  | Tool-server             | Result for a `run:` step over a link                                                                                                                                                                                                  |
| ----------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| With client services    | With client services    | The tool-server reads the fragment through client services                                                                                                                                                                            |
| With client services    | Without client services | The listing has no `clientServices`. The client sends nothing. The tool-server rejects the flow before the first step                                                                                                                 |
| Without client services | With client services    | The call has no `client_services`. The tool-server rejects the flow before the first step and adds: "This tool-server serves run: steps for a client that sends client services. Update the argent CLI or MCP adapter on the client." |
| Without client services | Without client services | The tool-server rejects the flow before the first step                                                                                                                                                                                |

A `snapshot:` step that compares needs `resolve-file` and `read-file` on both sides. A `snapshot:` step that updates baselines needs `resolve-file` and `write-file`. A client or tool-server without client services has none of these ops.

| Client                             | Tool-server                          | Result for a `snapshot:` step over a link                                                                                                                                                                                                           |
| ---------------------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| With `read-file` and `write-file`  | With `read-file` and `write-file`    | The client serves the baseline and writes each new baseline through client services                                                                                                                                                                 |
| Without the op that the step needs | With `read-file` and `write-file`    | The tool-server rejects the flow before the first step and adds: "This tool-server serves snapshot: steps for a client that offers the resolve-file, read-file and write-file client services. Update the argent CLI or MCP adapter on the client." |
| Any                                | Without `read-file` and `write-file` | The tool-server rejects the flow before the first step                                                                                                                                                                                              |

`script:` steps, and `tool:` steps that take a file or record a flow, need a run without a link in every row. In the root flow, the tool-server rejects them before the first step and lists each one. In a fragment that the client serves, the tool-server rejects them when the `run:` step loads the fragment: that step reports `error` with the same list, and no step of the fragment runs. The tool-server rejects a `snapshot:` step that the client cannot serve at the same points.
