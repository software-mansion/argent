This page documents client services: the exchange between the argent client and the tool-server. Through this exchange, the tool-server asks the client for project files during a flow run, and while it records a step. The tool-server also gives the client each new snapshot baseline. The argent CLI and the MCP adapter are clients. The runner stays on the tool-server. The project stays on the client. For the user-facing behavior, see [Flows over a link](/docs/reference/flow-yaml#flows-over-a-link).

The exchange has four messages:

| Message       | Direction             | Carrier                                            |
| ------------- | --------------------- | -------------------------------------------------- |
| Advertisement | Tool-server to client | The `clientServices` field of a `GET /tools` entry |
| Opt-in        | Client to tool-server | The `client_services` parameter of the call        |
| Request       | Tool-server to client | A `client-request` line on the NDJSON stream       |
| Answer        | Client to tool-server | `POST /invocations/<invocation>/client-responses`  |

The `flow-execute` and `flow-add-step` tools advertise client services, with the same ops. Each side uses an op only when the other side lists the op.

## Advertisement: `clientServices` in `GET /tools`

The `GET /tools` listing holds one entry per tool. The entry of a tool that can use client services carries a `clientServices` field:

```json
{
  "name": "flow-execute",
  "clientServices": { "ops": ["resolve-file", "read-file", "write-file"] }
}
```

| Field | Value                                         |
| ----- | --------------------------------------------- |
| `ops` | The ops the tool-server can send requests for |

An entry without the field belongs to a tool that does not use client services, or to a tool-server without client services.

## Opt-in: the `client_services` parameter

The client adds a `client_services` parameter to the arguments of a call when all these conditions hold:

1. A link routes the call to a tool-server (`argent link` or `ARGENT_TOOLS_URL`). A link to a tool-server on the same computer counts.
2. The `GET /tools` entry of the tool carries `clientServices`, and its `ops` hold an op that the client serves.
3. `project_root` is an absolute path without a `..` segment.
4. For `flow-add-step`, `name` is a valid flow name, `command` is a string, and `args` is absent or the JSON text of an object. For `flow-execute`, the arguments carry exactly one flow source:
   - a `name` that is a valid flow name
   - a `flow_path` that is an absolute path without a `..` segment, with a valid flow file name
5. For `flow-execute`, the root flow file is on the client and under the roots. The file has at least one of these steps:
   - a `run:` step
   - a `snapshot:` step, when `ops` hold `read-file` or `write-file`
   - a `tool: flow-execute` step with `name` and an absolute `project_root` without a `..` segment, when `ops` hold `resolve-file`
   - a `tool:` step with an argument that is an absolute path with an extension of [Client policy](#client-policy) rule 7, when `ops` hold `read-file`
6. For `flow-add-step`, the recorded step names a file. The recording file does not need to exist on the client. The step names a file in one of these forms:
   - a `flow-execute` step with `name` and an absolute `project_root` without a `..` segment, when `ops` hold `resolve-file`
   - a `flow-execute` step with an absolute `flow_path` without a `..` segment to a valid flow file name, when `ops` hold `resolve-file`
   - an argument that is an absolute path with an extension of rule 7, when `ops` hold `read-file`

```json
{
  "name": "withrun",
  "project_root": "/work/proj",
  "device": "chromium-cdp-9471",
  "client_services": {
    "ops": ["resolve-file", "read-file"],
    "roots": ["/work/proj"]
  }
}
```

| Field   | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ops`   | The ops the client serves: the ops that the tool-server advertised and that the client implements. The client offers `write-file` only when the arguments set `updateBaselines: true`. The client never offers `write-file` for a `flow-add-step` call                                                                                                                                                                                                                                                          |
| `roots` | Absolute client directories, by their real location: `project_root`, its `.argent/flows` directory, the directory of the root flow file, and the directory of the real file behind the root flow when that real file is a YAML file (`.yaml` or `.yml`). When the root flow file or that real file is under `<P>/.argent/flows/`, the project `<P>` is also a root. A root inside another root is not sent. For `flow-add-step`, the root flow is the recording file `<project_root>/.argent/flows/<name>.yaml` |

The client also sends `Accept: application/x-ndjson`, because the requests travel on the NDJSON stream of the call. The tool-server answers 400 with `HTTP_ZOD_VALIDATION_FAILED` and the error kind `validation` to a call that carries `client_services` without that header, or with a malformed `client_services`. A proxy that rewrites `Accept` therefore gets this 400 for each call that meets condition 5 or condition 6. A directory run of `argent flow run` reports such a flow as rejected and continues with the next flow. The tool-server takes `client_services` off the arguments before it validates them, so the input schemas of `flow-execute` and `flow-add-step` do not list the parameter. The tool-server sends a request for an op only when the client listed the op in `ops`.

Each request line must reach the client at once, because the run waits for the answer. For this reason, the client sends `Accept-Encoding: identity` with the call, and the tool-server sends the stream with `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no`. Each reverse proxy between the client and the tool-server must:

- pass the stream through as the tool-server writes it, without compression or buffering
- forward `POST /invocations/<invocation>/client-responses` while the stream of the call is open
- accept a request body of up to 48 MB on `POST /invocations/<invocation>/client-responses`, because an answer to `read-file` carries the file

`X-Accel-Buffering: no` turns off buffering only in the nginx that receives the header. nginx does not forward the header. When an nginx that terminates TLS sits in front of a second nginx, set `proxy_buffering off` in each nginx. A proxy that holds the stream keeps the request line from the client. The tool-server then reports a timeout after 30 s. A call that meets neither condition 5 nor condition 6 carries no `client_services`. The tool-server sends no request for such a call. Thus, such a proxy does not stop it.

nginx accepts a request body of up to 1 MB by default. A full-screen baseline is often larger. Set `client_max_body_size 48m` in each nginx. When a proxy refuses an answer with the status 413, the client sends a refusal for the same request. The step that waits for the answer then reports `error` at once. A refusal of the request for the root flow fails the run before the first step. See [Timeouts and failures](#timeouts-and-failures).

When a condition for the tool does not hold, the client sends no `client_services`, and the call is not a stream for client services. The tool-server then keeps the behavior of a call without client services.

## The `x-argent-linked` header

The client sends the header `x-argent-linked: 1` with each `POST /tools/<name>` call over a link. A link to `127.0.0.1` counts. The header does not depend on `client_services`. The flow recorder of the tool-server reads the header:

- A recording that `flow-start-recording` starts with the header keeps its file on the client. The tool-server writes nothing, and `savedTo` is a directive that the client applies. This is also true when the `project_root` path also exists on the computer of the tool-server.
- `flow-add-script` refuses the call, because a replay over a link rejects a `script:` step. No script runs, and the recorder records no step.
- `flow-add-step` refuses a step that a replay over a link rejects. An example is a `tool:` step that takes a directory, an app or an output directory. No tool runs, and the recorder records no step.
- `flow-add-step` refuses a `flow-execute` step when the nested flow does not pass. The recorder records no step.

`flow-add-step` uses the client services of a call only when the call carries the header. Without the header, the recorder reads no file from the client.

Without the header, `flow-start-recording` keeps the file on the client only when the `project_root` path does not exist on the computer of the tool-server. For such a recording, the recorder applies the three refusals of the list above also to a call without the header.

An argent client that is older than the tool-server sends no header. The result depends on the place of the recording file:

- The tool-server writes the file over a link to `127.0.0.1`, or when the `project_root` path also exists on its computer. The recorder then applies no refusal. Such a client can record steps that a replay over that link rejects, a `script:` step among them.
- The client keeps the file when the `project_root` path does not exist on the computer of the tool-server. The recorder applies the refusals. It also refuses each `flow-execute` step and each `tool:` step with a file argument, because it reads no file from such a client. The error tells you to update the argent CLI or the MCP adapter for these steps:
  - a `flow-execute` step with `name`
  - a `flow-execute` step with the `flow_path` of a flow beside the recording
  - a `tool:` step with a file argument

Keep the client and the tool-server at the same version.

## Request: the `client-request` line

The tool-server writes one line on the NDJSON stream of the call for each request:

```json
{
  "event": "client-request",
  "invocation": "4f4a1c1e-2b0e-4b7f-9d2a-8c3e0b1f6a21",
  "id": "9b2d7c0a-6f1e-4d3b-a5c8-0e7f2b4d9a13",
  "op": "resolve-file",
  "args": { "anchorDir": "/work/proj/.argent/flows", "target": "frag.yaml", "kind": "flow" }
}
```

| Field        | Value                                                 |
| ------------ | ----------------------------------------------------- |
| `event`      | `client-request`                                      |
| `invocation` | The id of the tool call. It names the answer endpoint |
| `id`         | The id of the request. The answer carries the same id |
| `op`         | One of the ops the client listed                      |
| `args`       | The arguments of the op. See [Ops](#ops)              |

The line sits between the step progress lines. When the flow has a `run:` or `snapshot:` step, the first request comes before the first step and asks for the root flow itself. For a flow with an `echo` step and then a `run: frag.yaml` step, called with a `device`, the lines come in this order:

```text
{"event":"client-request","invocation":"...","id":"...","op":"resolve-file","args":{"target":"withrun.yaml",...}}
{"event":"progress","data":{"kind":"echo","status":"pass",...}}
{"event":"client-request","invocation":"...","id":"...","op":"resolve-file","args":{"target":"frag.yaml",...}}
{"event":"progress","data":{"kind":"run","status":"pass",...}}
{"event":"result","data":{...}}
```

The tool-server asks once for each `run:` target of a run, and every later read of that target in the run uses the same answer. A nested run of a `tool: flow-execute` step asks again. Without a `device`, the tool-server reads a leading `run:` chain before the first step to find its launch. Then the request for `frag.yaml` comes before the first progress line.

A client that sent no `client_services` never receives the line.

## Answer: `POST /invocations/<invocation>/client-responses`

The client answers each request with a separate HTTP request. `<invocation>` is the `invocation` of the request line.

```text
POST /invocations/<invocation>/client-responses
Host: 127.0.0.1:4731
Authorization: Bearer <token>
Content-Type: application/json
```

The body has one of two shapes. When the client serves the request, the body carries the answer fields of the op. For `resolve-file`, see [the answer fields](#resolve-file):

```json
{
  "id": "9b2d7c0a-6f1e-4d3b-a5c8-0e7f2b4d9a13",
  "ok": true,
  "canonical": "/work/proj/.argent/flows/frag.yaml",
  "spelling": { "state": "listed" },
  "exists": true,
  "size": 20,
  "mtimeMs": 1791300000000,
  "content": "c3RlcHM6CiAgLSBlY2hvOiBoaQo="
}
```

When the client refuses the request, the body carries the reason:

```json
{ "id": "9b2d7c0a-6f1e-4d3b-a5c8-0e7f2b4d9a13", "ok": false, "error": "<text>" }
```

| Status | Body                    | Meaning                                                 |
| ------ | ----------------------- | ------------------------------------------------------- |
| 200    | `{ "accepted": true }`  | The tool-server delivered the answer to the waiting run |
| 404    | `{ "error": "<text>" }` | Unknown invocation, or unknown or expired request id    |
| 409    | `{ "error": "<text>" }` | The request already has an answer                       |
| 413    | `{ "error": "<text>" }` | `content` decodes to more than 32 MiB                   |

The endpoint sits behind the same bearer-token check and Host check as `/tools/<name>`. The JSON body limit of 48 MB applies.

## Ops

### `resolve-file`

The tool-server sends `resolve-file` once for each `run:` target of a run. A nested run of a `tool: flow-execute` step sends it again. The client resolves the target on its own disk and returns the file. When the flow has a `run:` or `snapshot:` step, the tool-server also sends `resolve-file` for the root flow itself before the first step. The answer gives the real location of the file. The `run:` targets of the root flow and the snapshot baselines resolve beside that location, as they do on one computer. A refusal of that request fails the run before the first step.

The tool-server also sends `resolve-file` once for each flow that a `tool: flow-execute` step names with `name`, in a run. A later step that names the same flow in the same run uses the same answer. A nested run asks again. `anchorDir` is `<project_root>/.argent/flows` of the step, and `target` is `<name>.yaml`. The nested run reads that flow, and resolves its own `run:` targets and snapshot baselines through the client services of the call. An answer with `exists: false` makes the step report `error`. So does an answer with a `case_folded` spelling, as in a run without a link. The reason then starts with `Invalid flow name`.

During a `flow-add-step` call for a `flow-execute` step, the tool-server sends `resolve-file` for the flow of the step before the nested flow runs. When the step has no `delayMs` and the nested flow passed, the tool-server also sends `resolve-file` for these files:

- the recording file
- the flow beside the recording with the same name as the flow of the step

The recorder uses the answers to record the step as `run: <name>.yaml` when the flow that ran is beside the recording, as without a link. For a step with `flow_path`, the recorder also asks for that file beside the recording file before the nested flow runs. It checks that the directory lists the file name as the step spells it.

Request `args`:

| Field       | Value                                                                           |
| ----------- | ------------------------------------------------------------------------------- |
| `anchorDir` | Absolute client path of a directory. See the next table                         |
| `target`    | A path relative to `anchorDir`. See the next table                              |
| `kind`      | `flow`. The protocol also defines `script`, which the client does not serve yet |

| Request for                               | `anchorDir`                                           | `target`                                                                        |
| ----------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------- |
| The root flow of a run                    | The directory of the root flow file                   | The file name of the root flow file                                             |
| A `run:` step                             | The directory of the flow file that contains the step | The `run:` target as written, for example `frag.yaml` or `../shared/login.yaml` |
| A `tool: flow-execute` step with `name`   | `<project_root>/.argent/flows` of the step            | `<name>.yaml`                                                                   |
| The recording file of `flow-add-step`     | The directory of the recording file                   | The file name of the recording file                                             |
| The flow beside the recording             | The directory of the real file of the recording       | `<name>.yaml`                                                                   |
| The `flow_path` of a `flow-add-step` call | The directory of the recording file                   | The file name of `flow_path`                                                    |

Answer:

| Field       | Required                                     | Value                                                                              |
| ----------- | -------------------------------------------- | ---------------------------------------------------------------------------------- |
| `canonical` | Yes                                          | The realpath of `anchorDir` + `/` + `target` on the client                         |
| `spelling`  | Yes                                          | How the directory on the client lists the basename of `target`. See the next table |
| `exists`    | Yes                                          | `true` when the client can stat `canonical` as a file                              |
| `content`   | When `exists` is `true` and `kind` is `flow` | The file as base64                                                                 |
| `size`      | No                                           | The size of the file in bytes                                                      |
| `mtimeMs`   | No                                           | The modification time of the file in epoch milliseconds                            |

The tool-server accepts the answer with 200 before the runner reads it. When a required field is missing, the runner fails the request: the step or the run reports that the client answered with an invalid payload.

`spelling` has one of three shapes:

| Shape                                                                   | Meaning                                                                                                                                          |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `{ "state": "listed" }`                                                 | The directory lists the basename as written. The client also answers `listed` when it cannot read the directory                                  |
| `{ "state": "case_folded", "actual": "<name>", "addressable": <bool> }` | The directory lists the name with a different case. `actual` is the listed name. `addressable` is `true` when `actual` is a valid flow file name |
| `{ "state": "absent" }`                                                 | The directory lists no name that matches, in any case                                                                                            |

The runner applies the same rules to the answer as to a file on its own disk: the cycle guard, the depth limit and the refusal of a `case_folded` spelling. The runner never opens `canonical`. It uses the path as a key and in messages.

### `read-file`

The tool-server sends `read-file` at each `snapshot:` step that compares, to get the baseline. The tool-server builds the path of the baseline beside the real file of the root flow on the client: `<dir>/__baselines__/<flow>/<key>.png`. `<flow>` is the name of that real file without `.yaml`. When that name is not a valid flow name, `<flow>` is the name of the flow. `<key>` is the baseline key of the snapshot. See [Snapshots](/docs/reference/flow-yaml#snapshots). A `snapshot:` step in a fragment uses the baselines of the root flow. A `snapshot:` step in a flow that a `tool: flow-execute` step runs uses the baselines of that flow. These baselines are in `__baselines__/<flow>/` beside the real file of that flow on the client. The client serves only the baselines in these directories, and the file arguments of `tool:` steps that this section describes below.

Request `args`:

| Field  | Value                                                             |
| ------ | ----------------------------------------------------------------- |
| `path` | Absolute client path of the baseline file or of the file argument |

Answer:

| Field     | Value                                                                                    |
| --------- | ---------------------------------------------------------------------------------------- |
| `exists`  | `true` when the client can stat `path` as a file. `false` when no file is at `path`      |
| `size`    | The size of the file in bytes. Present when `exists` is `true`                           |
| `mtimeMs` | The modification time of the file in epoch milliseconds. Present when `exists` is `true` |
| `content` | The file as base64. Present when `exists` is `true`                                      |

An answer with `exists: false` is not a refusal. The step then fails with the reason of a missing baseline, as in a run without a link. The client also answers `exists: false` when a file stands where a directory of `path` should be, as a run without a link does. The tool-server compares the images on its own computer. The tool-server returns the baseline, current and diff images of the step as artifacts, as in a run without a link.

The tool-server also sends `read-file` at each `tool:` step, once for each file argument of the step, before it starts the tool. The tool-server sends it only for a parameter that the tool declares as a client file. Examples are `baselinePath` and `currentPath` of `screenshot-diff`. `path` is the value of the argument in the flow. The tool-server writes the content to a temporary file. The tool gets that file, as in a direct call of the tool over a link. The tool-server deletes the file when the step ends. For an answer with `exists: false`, the step reports `error` with the reason `the client has no file at "<path>" (argument <parameter> of <tool>)`. The tool-server never uses a file at the same path on its own computer.

### `write-file`

The tool-server sends `write-file` at each `snapshot:` step when the call sets `updateBaselines`. A run that sets `updateBaselines` gives it to each nested run of a `tool: flow-execute` step, unless the step sets `updateBaselines` itself. A step that sets `updateBaselines: true` gets no `write-file` when the call does not set `updateBaselines`, because the client then does not offer the op. The nested run then rejects its `snapshot:` steps, and the step does not pass. The error does not tell you to update the client. It says that a nested flow updates its baselines only when the run that starts it updates baselines. The request carries the new baseline. The tool-server sends no `read-file` for this step. The answer tells whether a baseline was at the path, so the step reason says `baseline written` or `baseline updated`. The step reason also gives the client path of the baseline. The step returns no artifact, because the baseline is on the client. A run without a link gives the file name of the baseline in the step reason, and returns the baseline as an artifact.

Request `args`:

| Field     | Value                                                                                         |
| --------- | --------------------------------------------------------------------------------------------- |
| `path`    | Absolute client path of the baseline file, of the form `<dir>/__baselines__/<flow>/<key>.png` |
| `content` | The new baseline as base64                                                                    |

The content travels in the request line on the NDJSON stream, not in an answer. The tool-server does not send a baseline above the 32 MiB cap. The step then reports `error`, and the reason names the cap. The client writes only into the `__baselines__/<flow>/` directory of the root flow, and into that of each nested flow that the client served. The client creates `__baselines__/` and `__baselines__/<flow>/` beside the real file of that flow when they do not exist. The client creates no other directory. The client writes the new baseline to a temporary file in the same directory, and then renames that file over the baseline. When the client stops during the write, the old baseline stays complete. The new baseline keeps the mode of the file that it replaces. When the baseline is a link to a file under the roots, the client replaces that file and keeps the link. See [Client policy](#client-policy) for the paths that the client writes.

Answer:

| Field      | Value                                               |
| ---------- | --------------------------------------------------- |
| `written`  | The path that the client wrote                      |
| `replaced` | `true` when a file was at the path before the write |

### Reserved op names

The protocol also defines the op name `run-script`. No client serves it. The client lists only the ops it serves, so the tool-server never sends a request for it.

## Timeouts and failures

The tool-server waits 30 s for each answer. For `read-file` and `write-file`, the 30 s include the time to move the file. The file travels as base64. A file at the 32 MiB cap therefore needs about 12 Mbit/s: from the client to the tool-server for `read-file`, and from the tool-server to the client for `write-file`.

| Event                                              | Effect on the run                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No answer within 30 s                              | Before the first step, the call fails with `FLOW_CLIENT_NOT_ANSWERING` and the error kind `timeout`. At a `run:`, `snapshot:` or `tool:` step, the step reports `error` and the later steps report `skip`. Every later request of the same call then fails at once. The client can still complete a `write-file` that it already received. `argent flow run` exits at the end of the call and stops such a write. The old baseline then stays complete          |
| An answer with `ok: false`                         | The step reports `error`. At a `run:` step, the reason starts with `could not load fragment "<target>":` and quotes the `error` text of the client. At a `snapshot:` or `tool:` step, the reason names the op and the path, and quotes the `error` text of the client. The later steps report `skip`. A refusal of the request for the root flow fails the run before the first step                                                                            |
| A proxy refuses an answer with the status 413      | The client sends a refusal for the same request instead. The `error` text names the status. It also says that the proxy must accept a request body of up to 48 MB on the answer route. The effect is the same as for an answer with `ok: false`. When the refusal does not reach the tool-server either, the effect is the same as for an answer that does not reach the tool-server. A reply from the tool-server itself to the refusal does not stop the call |
| The HTTP response of the call closes               | The tool-server rejects every pending request and aborts the run. A `run:`, `snapshot:` or `tool:` step that waits for an answer reports `skip` with the reason `run aborted`. Each step that did not run also reports `skip` with the reason `run aborted`. The client can still complete a `write-file` that it already received. `argent flow run` exits at the end of the call and stops such a write. The old baseline then stays complete                 |
| The client closes before the call starts           | The tool-server does not run the call                                                                                                                                                                                                                                                                                                                                                                                                                           |
| The answer does not reach the tool-server          | The client stops the call at once with `FLOW_CLIENT_NOT_ANSWERING` and the error kind `network`, and closes the response. The tool-server then aborts the run                                                                                                                                                                                                                                                                                                   |
| The answer gets no reply within 30 s               | The call continues. The tool-server starts to count its 30 s when it sends the request, and the client starts to count later. So the tool-server stops to wait first, and the effect is the same as for no answer within 30 s. The client prints a line while the call continues                                                                                                                                                                                |
| The client cannot read or write a file within 30 s | The client sends no answer, and the tool-server reports the timeout                                                                                                                                                                                                                                                                                                                                                                                             |

The reason of a timeout names the op, and the target or the path of the request. It also names the usual causes:

- a paused or sleeping client
- a proxy that buffers the stream
- a proxy that does not forward the answer
- for `read-file` and `write-file`, a connection that is too slow to move the file in 30 s

The answer does not reach the tool-server when the answer request fails, or when its reply is not one that the tool-server sends. An example is a 502 from a proxy. The replies of the tool-server in the status table above do not stop the call. A 413 from a proxy also does not stop the call, because the client sends a refusal in place of the answer. An answer or a refusal that gets no reply within 30 s does not stop the call either.

## Client policy

The client enforces these rules. The tool-server checks only the shape of each answer and the 32 MiB cap. The tool-server already holds the bearer token, so the rules protect the files of the project, not the token.

1. The client serves only the files that the flows of the call compose. The client refuses any other request before it reads the file. The refusal is the same whether the file exists or not. The client serves these files:
   - For a `flow-execute` call:
     - the root flow
     - the `run:` targets of the served files. A `run:` target resolves beside the file that names it.
     - the flows that `tool: flow-execute` steps of the served files name with `name` and `project_root`. Such a nested flow is `<project_root>/.argent/flows/<name>.yaml`, as the step spells it.
     - the file arguments of the served files
     - the snapshot baselines of the run, and of each nested flow that the client served
   - For a `flow-add-step` call, the files that the recorded step names, not the files that the recording file names:
     - the flow that a `flow-execute` step names with `name` or `flow_path`, and the files that this flow composes
     - the file arguments of the step
     - the recording file itself, when it exists
2. The client reads and writes nothing outside the roots it sent. It resolves a requested path one segment at a time, as the operating system does. Before it looks at a place on the disk, it checks that the place is in a root or on the way to a root. It refuses a symlink that points outside a root. It refuses a target that passes through a place outside the roots, also when the target ends in a root.
3. The refusal of a path outside the roots does not tell where the path leads or whether it exists.
4. `resolve-file` serves `.yaml` names only. The client refuses a `.yaml` name that links to a file that is not a YAML file (`.yaml` or `.yml`).
5. Rule 7 gives the paths of file arguments. For any other path, `read-file` and `write-file` take only the form `<dir>/__baselines__/<flow>/<key>.png`. The client refuses a path that does not meet all these conditions:
   - The path is absolute and in normal form: no `..`, no `.` and no double `/`.
   - `<flow>` holds only letters, digits, `_` and `-`.
   - The path is in a baseline directory of the run, with the `<flow>` that the tool-server uses. A baseline directory is `__baselines__/<flow>/` beside the real file of the root flow or of a nested flow that the client served. Thus the client refuses a baseline of another flow and a `__baselines__` directory in another place.
   - For a baseline of the root flow, the root flow is a YAML file on the client.
6. For a baseline, the client refuses a `.png` name that links to a file that is not a PNG file (`.png`).
7. `read-file` serves a path when a `tool:` step of a served file has that path as the value of an argument. The value must be an absolute path with the extension `.png` or `.yaml`. The case of the letters does not matter. The client refuses a name that links to a file with another extension. The client resolves the path as rule 2 says. The tool-server can write a flow on the client when it records one, so the path gets no more trust than a request.
8. The client offers `write-file` only for a call that sets `updateBaselines: true`. A run that compares baselines cannot change them. A `tool: flow-execute` step that sets `updateBaselines: true` does not change this rule. The client also refuses to write the baselines of a nested flow when each step that names that flow sets `updateBaselines: false`.
9. Before `write-file` creates `__baselines__/<flow>/`, the client checks the real location of that directory against the roots. Before it writes the file, the client checks the real location of the file again. The client follows a link to a file that does not exist to check where it leads, and then refuses it.
10. The client refuses a file above 32 MiB, for a read and for a write. The error names the cap.
11. The client refuses an op that it did not list in `ops`, and a `kind` it does not know.
12. For a read, the client answers a directory with the `EISDIR` error, and an unreadable file with the error of the read, for example `EACCES`. It answers a target or a path in a directory that does not exist as a missing file.
13. The client answers a loop of symlinks with `ELOOP`. When the client cannot look at a place on the path, it answers with the error of the system, for example `EACCES` for a directory that it cannot search. It answers a file that a path uses as a directory with `ENOTDIR`. `read-file` answers such a path as a missing file instead, as a run without a link does. `write-file` answers a file at `__baselines__/<flow>` with the `EEXIST` error of the directory creation.
14. `write-file` refuses a path where something other than a regular file is, for example a directory or a FIFO.
15. By default, the client prints a line only in these cases: it cannot answer a request, the tool-server or a proxy does not take the answer, or an answer gets no reply within 30 s while the call continues. When the environment of the client has `ARGENT_CLIENT_SERVICES_LOG=1`, the client prints one line for each request after it decides the answer: `[client-services] <op> <path>: served`, `: missing`, `: written` or `: refused (<reason>)`. For `resolve-file`, the path is the real path of the file after the client finds that the flows of the call compose the file. Before that point, the path is the target that the tool-server sent. For `read-file` and `write-file`, the path is the path that the tool-server sent. The client never prints the content. Under `argent flow run --json`, each line is a warning object on stderr.

## A client or tool-server without client services

| Client                  | Tool-server             | Result for a `run:` step over a link                                                                                                                                                                                                  |
| ----------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| With client services    | With client services    | The tool-server reads the fragment through client services                                                                                                                                                                            |
| With client services    | Without client services | The listing has no `clientServices`. The client sends nothing. The tool-server rejects the flow before the first step                                                                                                                 |
| Without client services | With client services    | The call has no `client_services`. The tool-server rejects the flow before the first step and adds: "This tool-server serves run: steps for a client that sends client services. Update the argent CLI or MCP adapter on the client." |
| Without client services | Without client services | The tool-server rejects the flow before the first step                                                                                                                                                                                |

A `snapshot:` step that compares needs `resolve-file` and `read-file` on both sides. A `snapshot:` step that updates baselines needs `resolve-file` and `write-file`. A client or tool-server without client services has none of these ops.

| Client                             | Tool-server                          | Result for a `snapshot:` step over a link                                                                                                                                                                                                           |
| ---------------------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| With `read-file` and `write-file`  | With `read-file` and `write-file`    | The client serves the baseline and writes each new baseline through client services                                                                                                                                                                 |
| Without the op that the step needs | With `read-file` and `write-file`    | The tool-server rejects the flow before the first step and adds: "This tool-server serves snapshot: steps for a client that offers the resolve-file, read-file and write-file client services. Update the argent CLI or MCP adapter on the client." |
| Any                                | Without `read-file` and `write-file` | The tool-server rejects the flow before the first step                                                                                                                                                                                              |

A file argument needs `read-file` on both sides.

| Client              | Tool-server         | Result for a file argument over a link                                                                                                                                                                                                  |
| ------------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| With `read-file`    | With `read-file`    | The client serves the file through client services                                                                                                                                                                                      |
| Without `read-file` | With `read-file`    | The tool-server rejects the flow before the first step and adds: "This tool-server serves the file arguments of tool: steps for a client that offers the read-file client service. Update the argent CLI or MCP adapter on the client." |
| Any                 | Without `read-file` | The tool-server rejects the flow before the first step                                                                                                                                                                                  |

A `tool: flow-execute` step that names its flow with `name` needs these conditions:

- The client offers `resolve-file` and sends the [`x-argent-linked` header](#the-x-argent-linked-header).
- The tool-server runs nested flows over a link.

An older client sends no header and serves no nested flow. The tool-server then rejects the flow before the first step, also when the call has `client_services`. The error adds this text: "This tool-server serves tool: flow-execute steps that name a flow with name, for a client that serves those flows. Update the argent CLI or MCP adapter on the client."

An older tool-server can have client services but not run nested flows over a link. Such a tool-server rejects each `tool: flow-execute` step before the first step, also for a current client. Keep the client and the tool-server at the same version.

These steps need a run without a link in every row, or the fix that the error names:

- `script:` steps
- `tool:` steps that name a file by a relative path, or a file that does not end in `.png` or `.yaml`
- `tool:` steps that take a directory, an app or an output directory
- `tool:` steps that build a file path from two or more arguments
- `tool: flow-execute` steps that name a flow with `flow_path`, or with `name` and a `project_root` that is relative or has a `..` segment
- `tool:` steps that record a flow

The tool-server rejects these steps at these points, and lists each one:

- In the root flow, before the first step.
- In a fragment that the client serves, when the `run:` step loads the fragment. That step reports `error` with the same list, and no step of the fragment runs.
- In a flow that a `tool: flow-execute` step runs, when that step runs. That step reports `error` with the same list, and no step of that flow runs.

The tool-server rejects a `snapshot:` step that the client cannot serve at the same points.
